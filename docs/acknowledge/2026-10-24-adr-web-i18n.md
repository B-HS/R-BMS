# ADR: 웹 다국어 — next-intl 4.14.9, 쿠키 방식, 전 페이지 동적 렌더

> 최종 갱신 2026-10-24 · 대응 커밋 66b9e63
> 상태: 유효(next-intl 추가와 쿠키 방식·메시지 구조·AI 결과 언어는 사용자 확인 2026-10-24 "18번까지 전부 추천안대로". **전 페이지 동적 렌더**는 메인 결정이라 사용자 미확인) · 결정일 2026-10-24 · 결정자 사용자(결정 1 A, M11)와 메인(세부) · 커밋 `eb5ddbb`(기반). 문구 추출(WI1~WI4)은 이 ADR 을 쓰는 동안 같은 웨이브에서 진행 중이라 이 ADR 은 기반까지를 기록한다
> 관계: 클라이언트 다국어는 [UI 다국어 ADR](2026-10-24-adr-ui-language.md), 용어는 [용어집](../reference/2026-10-24-i18n-glossary.md). 프런트엔드 컨벤션 `frontend.md` 8.6절("i18n 라이브러리는 프로젝트 성격에 맞게 선택하고 선택과 사유를 `docs/acknowledge` 에 기록한다")의 선택 기록이다.

## 배경

- 사용자 요청(2026-10-24): "다국어 지원 (한글, 영어, 일본어)". 클라이언트(앱과 기본 스킨)를 먼저 하고 웹은 같은 체크리스트의 마지막 웨이브에 넣기로 했다(M1). 웹의 사용자 표시 문구는 거의 전부 한국어로 하드코딩돼 있다.
- 새 웹 의존성은 원칙적으로 금지이고(작업 규칙) next-intl 만 사용자가 결정 1 의 추천안 A 로 승인했다.
- 웹은 Next.js 16.3.4(App Router, Cache Components 사용: `read-cache.ts` 가 `'use cache'`·`cacheLife`·`cacheTag` 를 쓴다)이다.

## 결정

### 1) 라이브러리

next-intl 4.14.9(`web/package.json` 에 정확 고정). 선택 사유 셋: 사용자 승인, 같은 소유자의 `iidx-rank` 가 이미 쓰는 판, 경로 접두사 없는 쿠키 방식을 `getRequestConfig` + `cookies()` 로 공식 지원한다. npm 게시일 2026-10-02(22일 전)로 14일 기준을 넘고 그 시점의 `latest` 다. peerDependencies 가 `next ^16.0.0`, `react ^19.0.0` 이라 Next 16.3.4 와 맞는다.

간접 의존성도 14일 기준으로 맞췄다: 처음 `bun add` 가 `@swc/core 1.16.20`(10-22 게시)과 `@formatjs/icu-messageformat-parser 3.5.22`(10-19 게시)를 끌어와 14일이 안 돼 잠금 파일을 되돌리고 `bun add next-intl@4.14.9 --minimum-release-age=1209600` 로 다시 받았다(지금 `@swc/core 1.16.13`·parser `3.5.21`, 새로 들어온 패키지는 모두 14일을 넘겼다). next-intl 은 메시지 추출용 네이티브 패키지 `@swc/core`·`@parcel/watcher` 를 함께 끌고 온다(지금 빌드에는 문제 없다).

### 2) 쿠키 방식, 경로 접두사 없음(M11)

- 설정 `createNextIntlPlugin('./src/shared/i18n/request.ts')`(`next.config.ts`). URL 은 언어와 무관하다.
- 언어를 정하는 순서(`web/src/shared/i18n/locale.ts`): 올바른 `NEXT_LOCALE` 쿠키 → `Accept-Language`(q 값 순서, 주 부분만 맞춤: `en-US` 는 `en`, `q=0` 이나 잘못된 q 값은 제외) → 기본 `ko`. 첫 방문에는 쿠키를 쓰지 않고 매 요청의 헤더로 정하므로 `proxy.ts` 를 고치지 않았다. 쿠키·헤더가 없는 봇과 지원 밖 언어(`fr` 등)는 `ko` 다.
- 언어 선택 위젯 `web/src/widgets/locale-switcher/locale-switcher.tsx`: 사이드바 바닥의 아이콘 버튼과 라디오 메뉴, 고르면 쿠키(`Path=/`, 1년, `SameSite=Lax`)를 쓰고 `router.refresh()` 를 부른다. 언어 이름은 그 언어 자신으로(`한국어`, `English`, `日本語`. 용어집은 `ENGLISH` 이지만 웹 대소문자 관례를 따랐다). **이 단위는 위젯을 화면에 붙이지 않았다**: 붙일 `app-shell.tsx` 가 소유 밖이라 셸 단위(WI2)가 `SidebarMenu` 바닥에 `ShellThemeControl` 옆으로 붙이고 격자를 2열에서 3열로 바꾼다.
- `<html lang>` 은 루트 레이아웃이 `await getLocale()` 로 동적으로 정한다. `NextIntlClientProvider` 가 서버에서 locale 과 messages 를 그대로 물려준다.

### 3) 메시지

- 파일: `web/messages/{ko,en,ja}/{common,ai,settings,browse,pages,server}.json`. 네임스페이스는 이 여섯으로 고정하고(새로 만들려면 `MESSAGE_NAMESPACES` 와 `messages.ts` 의 import 를 함께 고쳐야 한다) 기반 단위는 `common` 만 채우고 나머지는 `{}` 로 비웠다. 최상위 키가 네임스페이스다(`useTranslations('browse.xxx')`, 서버는 `await getTranslations('pages.xxx')`).
- 한국어 카탈로그가 원본이고 en·ja 는 `Record<Locale, Messages>`(`next-intl.d.ts` 의 `AppConfig` 확장)라 키가 빠지면 `tsc` 가 막는다. `web/tests/lib/i18n-messages.test.ts` 가 세 언어의 키 집합·ICU 자리표 `{name}` 일치와 빈 문자열 금지를 검사하고, `i18n-locale.test.ts` 가 언어 결정(쿠키 우선, q 값, 봇, 지원 밖 언어)을, `locale-switcher.test.tsx` 가 위젯을 검사한다.
- 문구 추출 단위의 할당: 위젯 문구 A·B·C(`ai`·`settings`, `browse`, `pages`)는 WI1~WI3, 서버 오류 문구와 AI 결과 언어는 WI4. API 오류 응답의 형식은 바꾸지 않고 웹 화면이 오류 코드로 번역한다. AI 결과 문구의 언어는 UI 언어를 따른다(서버에서 `getLocale()` 로 받아 프롬프트 언어 인자로 넘긴다).
- 캐시 함수(`'use cache'`) 안에서 `getTranslations`·`getLocale`·`cookies()` 를 부르지 않는다. 캐시된 데이터는 언어 없이 받고 번역은 그 바깥 컴포넌트에서 한다.

### 4) 캐시 영향: 전 페이지 동적 렌더(메인 결정)

- Next 16 문서(`preventing-flash-before-hydration.md`): 루트 레이아웃에서 쿠키를 읽으면 앱 전체가 정적 prerender 에서 빠지고, Cache Components 에서는 그 아래 모든 segment 가 blocking 이 된다. 실제로 `bun run build` 가 `/guide` 에서 `blocking-prerender-dynamic` 오류로 멈췄고 오류가 제안한 해결책대로 루트 레이아웃에 `export const instant = false`(`route-segment-config/instant.md` "Disabling static shell validation")를 넣었다.
- 결과: 기존의 부분 정적(◐) 페이지 전부와 정적(○)이던 `/guide`·`/login`·`/signup` 이 모두 요청마다 렌더(ƒ)가 됐다. ○ 로 남은 것은 `robots`·`sitemap`·아이콘뿐이다. **데이터 캐시는 그대로**다(`read-cache.ts` 를 건드리지 않았고 `'use cache'` 함수들에는 locale 인자도 쿠키 읽기도 없다). 바뀐 것은 HTML 이 CDN 정적 셸 없이 요청마다 렌더된다는 점이다. 빌드는 78 페이지를 만든다.
- `timeZone` 은 정하지 않았다(서버 런타임 시간대). 날짜를 `useFormatter` 로 쓰기 시작하면 정해야 한다.

## 이유

- 쿠키 방식은 URL·라우트 구조·캐시 태그를 그대로 두고 문구만 언어별로 바꾼다(사용자의 요구는 다국어 문구이고 언어별 URL 이 아니다).
- 첫 방문을 `Accept-Language` 로 정하면 사용자가 고르기 전에도 영어·일본어 사용자에게 맞는 언어로 열린다. 첫 방문에 쿠키를 심지 않고 매 요청의 헤더로 정하므로 `proxy.ts` 를 고치지 않아도 된다.
- 정적 셸을 잃는 대가는 데이터 캐시(`read-cache.ts`)가 언어와 무관하게 유지되는 것으로 줄였다. 정적 셸을 되찾는 방법은 라우트 전체를 옮기는 별도 단위라 지금은 택하지 않고 대안으로 남겼다.

## 기각된 대안

| 대안 | 기각 이유 |
| --- | --- |
| 경로 접두사 `app/[locale]`(언어별 정적 셸 유지) | `src/app/**` 전체를 옮기는 별도 단위이고 캐시 태그를 다시 검토해야 한다. 정적 셸을 되찾는 경로로 남긴다 |
| next-intl `localePrefix: 'never'` + proxy 내부 rewrite + `next/root-params` | 위와 같은 라우트 이동이 필요하다 |
| 브라우저 `localStorage` 로만 언어 보관 | 서버 렌더가 언어를 알 수 없다 |
| react-i18next, Paraglide JS, LinguiJS, FormatJS | `frontend.md` 8.6절의 표에서 Next.js App Router 의 서버 컴포넌트·라우팅 통합이 필요한 경우는 next-intl 이다 |
| 첫 방문에도 쿠키를 심음 | `proxy.ts` 변경과 첫 요청의 이중 렌더. 헤더 기반 결정으로 충분하다 |
