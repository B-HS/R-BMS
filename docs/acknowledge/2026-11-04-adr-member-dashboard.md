# ADR: 로그인 회원의 `/` 는 15패널 대시보드

> 최종 갱신 2026-11-04 · 대응 커밋 2026-11-04 AI 훈련곡 작업(커밋 예정)
> 상태: 유효 · 결정일 2026-11-04 · 결정자 사용자(D9), 메인 추천(M19~M23·M26). 사용자 확인 전: 미확인 목록 38번(M 결정) · 커밋 예정.

## 배경

- 사용자 요청 3: 로그인한 사용자는 `/` 에서 대시보드를 본다. iidx-rank 처럼 보일 수 있는 내용을 최대한 보인다. 사용자 결정 D9: 손님 홈은 그대로, 로그인 사용자에게만 `/` 를 대시보드로, 구성은 설계가 정한다(최대한). 조사 [03](../reference/2026-11-04-ai-training-dashboard/03-dashboard.md).

## 결정

1. (D9) 손님 홈은 바꾸지 않고 로그인한 회원에게만 `/` 를 대시보드로 한다.
2. (M19) **분기는 서버에서 한다**(조사 03 §8.1 의 A안): `HomeBranch`(서버)가 쿠키가 없으면 DB 없이 손님, 있으면 세션을 읽어 회원이면 `MemberDashboardContent`. 로그인·로그아웃 뒤 `router.refresh()` 로 분기가 다시 돈다. 노트레이더 자리(웹에 레이더 값이 없다)는 **약점 패널**로 채운다.
3. (M20) 패널은 15개이고 첫 화면 5개(`usePlayer`·overview·stats·일별 플레이 시간·최근 판)만 서버 프리페치하며 나머지는 클라이언트 지연 로딩이다. AI 계열(약점·훈련곡·주간·목표·라이벌·AI 현황)은 뷰포트 진입 뒤에만 요청해 분당 30회 AI 한도와 DB 비용을 아낀다.
4. (M21) 대시보드의 날짜는 KST(이번 주도 KST 월요일 0시)로 하고, 주간 요약 digest 는 기존 UTC 를 유지한다(캐시 키 호환).
5. (M22) 커뮤니티 최근 활동·서버 현황을 맨 아래 패널 한 개로 남긴다("최대한" 요청, 캐시된 데이터라 비용이 없다).
6. (M23) `USER_SCOPED_QUERY_KEYS` 에 `DASHBOARD.ALL` 과 `DAN.MINE` 을 더해 로그아웃 뒤 다음 계정에 남는 누수를 막는다.
7. (M26) 최근 플레이는 판 단위 20행에 훈련곡 표지를 더하고(DJ 등급 라벨은 활동 행에 노트 수가 없어 생략), 곡당 최신 보기는 넣지 않는다. 판정 습관·게이지 조언 한 줄은 AI 현황 패널에 결정론 GET 으로 보인다. 리포트 헤드라인은 넣지 않는다(공급자 호출이 생기기 때문).
8. **종합 순위는 SQL 경쟁 순위(공동 순위 1, 1, 3)다**: 기존 목록의 정렬은 동률 순서가 정해지지 않아 새로고침마다 흔들리므로 대시보드 숫자는 공동 순위로 정한다(목록 화면은 바꾸지 않는다). 범위는 종합 순위 화면 기본값(SCRATCH AUTO 포함).
9. **패널 폭은 3열·4열 조밀 배치에서 빈 칸이 0 이 되는 조합으로 고정한다**(넓음 7, 채움 3, 꽉 1, 한 칸 4). 시험이 구멍을 잡는다.

## 이유

- 서버 분기는 기존 선례(`table-snapshot-session`)와 같고 깜빡임이 없다. 첫 HTML 비용은 캐시 적중 시 DB 0회가 기준이다.
- 지연 로딩과 뷰포트 진입 조건은 새로고침을 연달아 해도 AI 한도에 닿지 않게 한다.

## 기각된 대안

- B 프록시 재작성: 쿠키가 있어도 유효한 세션은 아니고 모든 홈 요청이 프록시를 지난다.
- C 클라이언트 분기: 하이드레이션 전에 viewer 를 몰라 깜빡이고 서버 프리페치와 섞기 어렵다.
- 최근 플레이를 곡당 최신으로: 기존 `/players` 최근 목록과 단위가 달라 "전체 보기" 와 이어지지 않는다.

## 영향과 관련 파일

- 정본: [web 아키텍처 §17-6](../web/architecture.md), [components.md §13](../web/components.md), [api-spec.md §12](../backend/api-spec.md)(대시보드 읽기 여섯).
- 코드: `web/src/app/(app)/page.tsx`, `web/src/widgets/home/{home-branch,member-*}.tsx`, `features/dashboard/*`, `entities/dashboard.*`, `server/{route,service/domain,compose}/dashboard*`, `service/dashboard-reads.ts`, 캐시 태그 `player-dashboard:{loginId}`.
- 알려진 것: 회원 `/` 의 첫 HTML 에 프리페치 다섯이 얹히고 `readPlayer*` 의 `requireUserId` 때문에 PK 조회가 3~4회 더 든다(운영 응답 시간은 배포 뒤 측정). 손님도 소개 패널이 스트리밍으로 온다(최종 DOM 은 같다). 최근 1년 최고 연속은 최근 371일 판 시각을 한 번 읽는 방식이라 판이 매우 많은 사용자의 캐시 미스 비용이 늘 수 있다.
