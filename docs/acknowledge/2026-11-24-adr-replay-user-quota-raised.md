# ADR: 리플레이 사용자별 저장 한도를 20,000개·4GiB 로 올림

> 최종 갱신 2026-11-24 · 대응 커밋: 이 문서와 같은 커밋(`fix(web)`: 리플레이 사용자별 저장 한도 상향)
> 상태: 유효 · 결정일 2026-11-24 · 결정자 사용자(세 안 가운데 1번 선택)

## 배경

- 2026-11-23 02:19 부터 리플레이 업로드가 전부 413 `IR_PAYLOAD_TOO_LARGE` 로 거절됐다(62건). 원인은 본문 크기가 아니라 사용자별 개수 한도 2,000개 도달이다. 진단과 근거: [버그 기록](../bug/2026-11-24-replay-upload-413-user-quota.md).
- 한도 2,000개·512MiB 는 2026-10-15 S19 에서 메인이 정했고 사용자 확인을 받지 않은 값이었다([테스트 부채](../quality-assurance/2026-10-14-test-debt.md) 3.34). 그때의 가정은 7K 한 판 약 60KB, 실제 평균은 약 148KB 다.
- 모든 판을 저장하고 보내는 원칙([피드백](../feedback/2026-10-15-do-not-exclude-runs.md)) 아래 11월 업로드는 하루 약 26개, 약 3.8MiB 였다.

## 결정

1. `REPLAY_USER_QUOTA` 를 `{ COUNT_MAX: 20_000, TOTAL_BYTES_MAX: 4GiB }` 로 올린다(`web/src/server/dto/replay.ts`).
2. 한도를 세는 방식은 그대로다: 새 리플레이를 만들 때만 세고, 이미 연결된 리플레이의 재업로드는 세지 않으며, 넘으면 413 으로 거절한다.
3. DB 마이그레이션은 없다(상수만 바뀐다. `replay.size` 는 행마다 `int`, 합계는 JS 수로 읽는다).

## 이유

- 가장 작은 변경으로 지금 막힌 업로드가 풀린다. 현재 속도로 개수 한도까지 약 2년, 바이트 한도까지 약 2.7년이다.
- 서버의 리플레이를 지우지 않는다.

## 기각된 대안

| 대안 | 기각 이유 |
| --- | --- |
| 서버 순환 삭제(한도에 닿으면 차트별 최고 기록·최근 N개 밖의 오래된 리플레이를 지움) | 다시 막히지 않지만 서버의 옛 리플레이가 사라진다. 사용자가 고르지 않았다 |
| 개수 한도만 없애고 512MiB 유지 | 약 3,600개(현재 속도로 약 2개월 뒤)에서 바이트 한도로 다시 막힌다 |

## 영향과 관련 파일

- `web/src/server/dto/replay.ts`(`REPLAY_USER_QUOTA`). 쓰는 곳은 `replay.service.ts` 의 `findReplayQuotaExceeded` 하나이고 시험(`web/tests/service/replay.test.ts`)은 상수를 읽으므로 값에 매이지 않는다.
- 문서: `docs/backend/api-spec.md` 8절, `docs/backend/data-model.md`, `docs/backend/endpoint-tasks.md`, `docs/web/tasks.md` IR-15, `docs/reference/ai-features/{server,client}.md`.
- 거절된 62건은 웹 배포로 서버 빌드가 바뀌면 다음 동기화에 다시 간다([거절 재전송 ADR](2026-10-15-adr-record-sync-refusal-resend.md) 결정 3).

## 남는 것

- 운영 DB 의 여유 용량은 확인하지 않았다(접속 정보를 읽지 않는다). 한 사용자가 한도까지 채우면 `replay.data` 가 4GiB 다. 테스트 부채 3.34.
- 저장 한도 거절이 본문 크기 초과와 같은 코드·문구("요청 본문이 허용 크기를 초과했습니다")를 써서 원인을 가린다. 이번에는 고치지 않았다(요청 범위 밖).

## 날짜와 사용자 원문

2026-11-24. 진단 보고의 세 안(1 한도 상향 20,000개·4GiB / 2 서버 순환 삭제 / 3 개수 한도만 제거)에 "1".
