# ADR: 훈련곡 생성과 전달 - LLM 구성안, 결정론 합성, 공개 zip, 내 폴더에서 바로 받기

> 최종 갱신 2026-11-04 · 대응 커밋 2026-11-04 AI 훈련곡 작업(커밋 예정)
> 상태: 유효 · 결정일 2026-11-04 · 결정자 사용자(D1·D2·D3·D5·D7·D8), 메인 추천(M8~M10·M12~M18·M25·M27·M30). 사용자 확인 전: 미확인 목록 36번(M 결정) · 커밋 예정. 운영 반영 전.

## 배경

- 사용자 요청 1: 약점을 단련하는 1분짜리 곡을 만든다. 사용자 질문 "클라이언트 수정도 필요한 거야?" 에 대한 답: 필요하다. 서버만 바꾸면 훈련곡은 내 폴더에 숫자로만 잡히고 사용자가 웹에서 zip 을 받아 풀고 다시 스캔해야 한다. "구동기에서 바로 받아 플레이" 는 내 폴더의 없는 곡 줄과 받기 모달 분기가 있어야 된다([조사 02 §7.3 의 P2](../reference/2026-11-04-ai-training-dashboard/02-training-chart-delivery.md)).
- 판이 공개 랭킹에 올라가므로 제목에 약점이 드러나지 않아야 한다.

## 결정

**사용자 결정**

1. (D1) 결정론 약점 프로필이 입력이고, LLM(기존 BYOK 어댑터 3곳)이 패턴 구성안을 쓰고, 서버가 결정론 합성기로 BMS 로 바꾼다. 키가 없으면 다른 AI 기능처럼 버튼을 막고 등록을 안내한다.
2. (D2) 산출물은 생성 → 사용자의 내 폴더 "훈련곡" → 구동기에서 바로 받아 플레이다. 클라이언트 변경을 포함한다.
3. (D3) 다운로드는 추측 불가한 무작위 id 경로의 공개 GET 이고 경로가 `.zip` 으로 끝난다.
4. (D5) 소리는 노트 키음으로 짧은 클릭 wav 를 zip 에 넣는다. 서버 TypeScript 가 PCM 으로 만들고 새 의존성은 없다.
5. (D7) 사용자당 20곡. 넘으면 생성 전에 직접 지우도록 안내하고 자동 삭제는 없다. 지울 때 함께 사라지는 것과 남는 것의 개수를 보인다.
6. (D8) 클라이언트 변경 뒤 `release.yml` draft 까지 만든다(게시는 사용자).

**메인 추천 세부**

7. (M8) 곡은 1분 = 카운트인 1마디 + 노트(+ 꼬리 1초). 기준 BPM 은 4의 배수 100~220이라 1분이 정수 마디로 맞고 Rust 시간 계산과 일치한다. 구간은 3~12개.
8. (M9) `#LNMODE 1` 고정, 지뢰 없음, 노트 키음 `hit.wav` 하나 + 카운트인 `count.wav`.
9. (M10) `#SUBTITLE` 에 id 를 넣어 md5 를 사용자·곡마다 다르게 하고 `training_chart.md5` 는 unique 다.
10. (M27) **공개 제목은 `R-BMS Training · 만든 날 · 강도` 고정**이다. 초점(약점) 이름과 LLM 문장은 넣지 않고 비공개 폴더 `note`·소유자 상세에만 둔다.
11. (M25) `PLAYLEVEL` 은 밀도(구간 최대 실제 NPS 의 정수)이고 난이도표 레벨과 무관하다. 상세 화면에서 설명한다.
12. (M12·M13) 다운로드 응답은 `Cache-Control: private, no-store` 이고, BMS 원 바이트를 DB 에 저장하고 zip 은 요청 때 조립한다(md5 는 BMS 바이트로 고정, wav 는 코드 상수).
13. (M14) "훈련곡" 폴더 이름은 만들 때 화면 언어(훈련곡 / Training / トレーニング)로 정하고 이후 고정한다. 클라이언트는 이름을 그대로 보인다.
14. (M15) 폴더 응답의 `download_url` 은 **폴더 주인이 만든 훈련곡일 때만** 넣는 선택 필드이고 주소는 요청 origin 으로 만든다. 다른 사람 곡의 주소가 새지 않고, 옛 클라이언트·기존 화면·시험과 호환되며, Preview 가 운영 주소를 내리지 않는다.
15. (M16) 클라이언트는 일반 폴더의 라이브러리에 없는 곡도 흐린 줄로 보인다(`show_missing_charts` 를 따름). 링크가 없으면 받기 버튼만 꺼진다. 표 레벨과 같은 규칙이다.
16. (M17) 생성 LLM 결과는 같은 digest 면 캐시를 재사용하고 곡은 시드(생성 시각)로 매번 다르다.
17. (M18) 보관 한도·폴더·프로필 검사를 공급자 호출 전에 한다(실패할 요청에 호출·사용량을 쓰지 않는다). 구현 중 AI 키 등록 확인을 그 사이에 넣었다.
18. (M30) 한도 20곡은 저장 트랜잭션에서 사용자 행을 `FOR UPDATE` 로 잠근 뒤 센다(캐시 적중 경로는 동시 실행 슬롯을 잡지 않아 슬롯으로는 막을 수 없다).

## 이유

- 공개 랭킹의 판 제목이 곧 공개 정보다. 약점은 소유자에게만 보인다.
- 받기·풀기·스캔 기계(`rbms-download`)는 이미 있어 재사용하므로 클라이언트 변경이 모달 분기와 폴더 줄에 그친다.
- 합성기를 결정론으로 두면 LLM 출력이 형태만 정하고 바이트와 md5 는 사양·시드가 정한다.

## 기각된 대안

- P0 웹에서 직접 받아 수동으로 풀고 다시 스캔: "바로 받기" 요구를 채우지 못한다(수동 경로는 그대로 쓸 수는 있다).
- P1 사용자별 비밀 주소의 난이도표를 클라이언트 Tables 에 등록: 표는 인증 헤더 없이 받아 주소에 비밀이 들어가고 수동 등록이 필요하다.
- 폴더 JSON 에 BMS 를 base64 로 인라인: 클라이언트에 파일 쓰기·배치·스캔·충돌 처리가 모두 새 코드로 필요하고 저장본이 커진다([조사 02 §7.2](../reference/2026-11-04-ai-training-dashboard/02-training-chart-delivery.md)).
- 제목에 초점을 넣는다: 판이 공개되어 약점이 드러난다.

- 동작 변화: 일반 폴더도 라이브러리에 없는 곡이 흐린 줄로 보이므로 릴리스 노트에 적는다. 서버가 클라이언트 draft 보다 먼저 나가는 창을 위해 폴더 저장본에 `version` 을 두어 옛 저장본은 한 번 모두 다시 받는다.
- 남은 위험: LLM 품질(Ollama 는 best effort 구조화)은 Zod·`refine`·서버 보정으로 형태만 보장한다. 같은 digest 캐시는 최근 3곡이 digest 에 들어가 연달아 만들면 거의 맞지 않는다. zip deflate 바이트는 런타임에 따라 다를 수 있다(내용·CRC 는 같다).
