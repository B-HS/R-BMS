# ADR: NOTES RADAR 6축의 정의, 곡 DB 저장, 스킨 노출

> 최종 갱신 2026-10-24 · 대응 커밋 66b9e63
> 상태: 유효(질문 1~6 의 추천안은 사용자 확인 2026-10-24 "18번까지 전부 추천안대로". **IIDX 와 수치가 다를 수 있다**: 세 축의 정의와 스케일 상수는 가설과 이 라이브러리 분포로 정한 임시값이다) · 결정일 2026-10-24 · 결정자 사용자(요청과 결정 묶음)와 메인(세부, 통합 결정 M6) · 커밋 `0e74d08`(계산), `54ff02c`(곡 DB 저장·참조 이미지 칠하기·CLI), `d75b819`(분석 작업자·스킨 값), `90d57d1`(기본 스킨 6각형)
> 관계: 확장 id 는 [확장 id 공간 ADR](2026-10-24-adr-rbms-extension-id-spaces.md), 화면은 [선곡 IIDX 식 ADR](2026-10-24-adr-select-iidx-layout.md).

## 배경

- 사용자 요청(2026-10-24): "곡선택에서, NOTES RADAR 구현도 가능하게해줘 CHORD, NOTES, PEAK, SCRATCH, SOF-LAN 이렇게해서 6각형 표시야". 참고 화면(IIDX 선곡)에는 여섯 번째 축 CHARGE 도 있다.
- 조사 보고서 [2026-10-24-notes-radar-survey.md](../reference/2026-10-24-notes-radar-survey.md): IIDX 의 레이더 계산식은 공개되지 않았고, 커뮤니티가 역공학한 구간표와 가중치(UkiyoAmeto/iidx33-notesradar `docs/algorithm.md`)가 한 출처로 있다. 선곡 UI 보고서가 따로 제안한 0~100 자체 레이더는 버렸다(통합 결정 M6).
- 당시 `rbms-skin` 의 문들은 원본에 없는 숫자·그림 id 에 답하지 않아 스킨에 값을 줄 길이 없었다(확장 id ADR).

## 결정

### 1) 축과 정의

화면 위에서 시계 방향: NOTES, PEAK, SCRATCH, SOF-LAN, CHARGE, CHORD(사용자가 적은 다섯 축과 참고 화면의 CHARGE). 제목은 "NOTES RADAR", 축 이름은 번역하지 않는다(용어집 1절).

모든 지표는 같은 "누름 이벤트"를 센다: 일반 노트와 롱노트 머리(꼬리는 종류와 관계없이 세지 않고 지뢰는 노트가 아니다). 그래서 값이 LN MODE(LN·CN·HCN·정의 안 됨)와 무관하다(시험이 `#LNMODE` 없음·1·2·3 에서 여섯 값이 비트까지 같음을 확인). 이 점이 `counts_as_playable_note`(CN·HCN 꼬리까지 셈)와 일부러 다르다.

| 축 | 원시 지표(`RadarRaw`) |
| --- | --- |
| NOTES | 누름 이벤트 / 초 |
| PEAK | 누름 이벤트에서 시작하는 4초 창 안의 최대 누름 수 |
| SCRATCH | 스크래치 레인 누름 / 초 |
| SOF-LAN | 속도(BPM 과 스크롤 배율의 곱의 절댓값, 스톱 구간 0)가 바뀐 뒤 2초 안의 노트를, 변화율(0.01~1.26로 자름, 최솟값이 0 이면 1.26)과 선형으로 줄어드는 창(다음 변화에서 닫힘)의 곱으로 가중한 합. 첫 타임라인의 속도는 변화로 세지 않는다 |
| CHARGE | 롱노트마다 머리 3점 + 같이 눌린 노트 3점씩 + 잡고 있는 동안 지나간 노트 4점씩의 합 / 초 |
| CHORD | 동시 누름(같은 시각 2개 이상)의 가중 합 / 초, 가중은 `(n-1)(n+6)/40` |

- 시간은 첫 누름에서 마지막 누름까지이고 1초를 하한으로 한다(노트 1개나 한꺼번에 치는 차트에서 0 으로 나누지 않는다). 모든 값은 유한하다(시간은 포화 연산, 변화율은 `clamp`).
- 모드: 5키·7키는 SP 구간, 10키·14키는 DP 구간, 9키·24키·그 밖은 레이더가 없다(`radar_raw` 가 `None`). 노트가 0개인 차트는 `None` 이 아니라 전부 0 이다.
- 표시값 0~200: `radar_display(raw, mode) -> [f32; 6]`. 원시 값에 축별 배율을 곱한 뒤 공개 구간표(SP·DP, 축마다 네 구간점 `p0..p3`)의 선형 곡선으로 100·150·175·200 에 대응시키고 `p3` 이상은 200 으로 자른다(질문 4). 반올림하지 않는다. 정수 id(21020~21025)는 버림이다.
- 구간표는 원문(`algorithm.md` 2.1절)을 받아 SP 6축·DP 6축 12칸씩 코드와 대조해 모두 일치했다. DP PEAK 의 세 번째 구간점은 원문 표와 파라미터 메모리가 122, 원문의 교차검증 문장과 커뮤니티 측정이 125 라고 적어 어긋난다. **원문 표의 122 를 따랐다**(`DOUBLE_CURVES` 의 `///` 에 적었다).
- 곡 DB 에는 원시 값을 저장하고 스케일은 표시 단계에서 곱한다(`AXIS_SCALE`). 스케일을 조정해도 DB 를 다시 만들 필요가 없다. 지표 정의가 바뀔 때만 `RADAR_VERSION`(지금 1)을 올린다.

### 2) 세 축은 가설과 임시 스케일

원문이 단위를 공개하지 않는 SOF-LAN·CHARGE·CHORD 는 가설 정의(보고서 4.1절)와 이름 있는 임시 상수다: `RADAR_SOFLAN_SCALE` 13.0, `RADAR_CHARGE_SCALE` 3.0, `RADAR_CHORD_SCALE` 300.0. 값은 `/Volumes/SSD/bms` 의 차트 10,443개(5·7키 SP 8,366개)를 읽기 전용으로 재어 정했다. 규칙은 "값이 0 이 아닌 차트의 90번째 백분위가 표시 150 근처에 오게"이고(구현 단위가 정했다, 근거 자료 없음) 결과는 SP 기준 CHORD 중앙 80·p90 146(포화 1.9%), CHARGE 0 초과 구간 p90 150, SOF-LAN 0 초과 구간 p90 146, DP CHORD 중앙 54·p90 124 이다. 원시 분포는 보고서의 수치(7키 차트 7,903개, CHARGE p50 2.65·p90 105.3·p98 288.4)와 맞는다.

**IIDX 값과의 대응은 검증하지 못했다.** 이 스케일은 이 라이브러리의 분포에 맞춘 추정이라 IIDX 의 실제 레이더와 수십 % 달라도 이상하지 않다. 이 라이브러리는 밀도가 높아 SP 의 NOTES 18.4% 가 200 에 닿는다(다른 사용자의 라이브러리는 분포가 다를 수 있다). 선곡 화면을 사람이 보고 상수 셋을 조정해야 한다(테스트 부채 3.115·3.116).

### 3) 저장(질문 2)

- 곡 DB 표 `song_radar`(`path` 기본키, `song(path)` 참조 `ON DELETE CASCADE`, `version`, `applies`, 원시 6열). `migrate()` 가 매 연결마다 `CREATE TABLE IF NOT EXISTS` 를 돌리므로 옛 DB 에도 표가 생긴다. `SCHEMA_VERSION` 1 과 `PARSER_VERSION` 5 는 올리지 않았다(전체 재스캔을 강제하지 않는다). 9키·24키는 `applies = 0`.
- 스캔이 새 차트와 바뀐 차트에만 `DetailRow` 와 같은 배치로 쓴다(`.bms`·`.bmson` 모두). 이미 저장된 차트는 행이 없고, 증분 스캔은 낡은 버전 행을 건드리지 않는다(시험).
- 행이 없거나 버전이 다르면 선곡에서 커서가 150 ms 머문 차트를 **분석 작업자 스레드**가 재서 저장한다(`library::keep_radar`). 프레임 스레드에서 파싱하지 않고(계획 R2 와 달리 `chart_detail` 이 낡은 값을 다시 재지 않는다), 낡은 요청은 버린다. DB 에 현재 버전 행이 있으면 즉시 쓴다. 값은 한 출처(`analysis.rs` 의 `notes_radar`)만 거쳐 정수·Float·참조 이미지가 서로 어긋나지 않는다.
- `rbms-cli` 의 차트 요약에 `radar ver`, `radar raw`, `radar disp` 세 줄(레이더가 없는 모드는 한 줄).

### 4) 스킨 노출(질문 5, 6)

- 정수·Float 21020~21025(표시값), 참조 이미지 목적지 id `"-21020"`(256x256 CPU 픽셀맵의 흰 불투명 육각형. 스킨의 색·알파가 입힌다). 한 화면에 이 id 를 쓰는 객체가 여럿이면 객체마다 텍스처를 따로 만든다. 값이 없으면 그리지 않는다. 값이 서로 다르면 다각형이 볼록하지 않으므로 줄마다 가장자리 교차점을 정렬해 짝수 번째 구간을 채운다. 세로 4배 표본으로 앤티앨리어싱하고 값이 같으면 다시 칠하지 않는다. 값이 하나뿐이거나 마주 보는 두 값뿐이면 면적 0 이라 칠해지지 않는다(의도).
- 기본 스킨(`lua/select/radar.lua`): 격자는 회전 사각형 9개(축선 3, 외곽선 6), 다각형은 노랑 반투명(`theme.radar.fill` (244, 236, 72), 알파 176. 참고 화면 다각형의 실측 (169, 173, 66) 에 맞춘 값), 축 라벨 6색(`theme.radar.axis`), 값 정수, 가장 큰 축의 꼭짓점에 별(동률이면 화면 순서의 앞 축). 256 그림을 화면에서는 144 정사각으로 줄인다. 9키·24키처럼 레이더가 없는 차트는 격자 대신 `-`.
- 내장(스킨 없는) 선곡 화면은 육각형을 그리지 않는다(질문 6).

## 이유

- 공개된 구간표를 그대로 쓰면 IIDX 의 앞 세 축(NOTES·PEAK·SCRATCH)은 근사로 맞을 수 있고, 가설 세 축은 이름 있는 상수 하나씩으로 조정할 수 있다.
- 저장은 원시 값으로 해서 스케일 조정이 DB 재생성을 요구하지 않는다. 스캔 때 계산하는 비용은 한 곡당 마이크로~밀리초 단위로 추정했고(계산 시간 전체 측정 예제는 파싱을 포함해 10,443개에 약 35초), 이미 저장된 곡은 커서가 머물 때 채운다.
- 확장 id 로 값을 주고 그림은 스킨이 그리게 해 외부 스킨도 같은 값을 쓸 수 있다.

## 기각된 대안

| 대안 | 기각 이유 |
| --- | --- |
| 선곡 UI 보고서의 자체 0~100 레이더 | 두 정의가 공존하면 안 된다(M6) |
| 표시값을 DB 에 저장 | 스케일 조정마다 재생성 |
| `PARSER_VERSION` 을 올려 전체 재스캔 | 설치된 모든 사용자에게 긴 재스캔을 강제 |
| `chart_detail`(프레임 스레드)에서 낡은 레이더를 다시 계산 | 프레임 스레드 파싱 금지. 모든 기존 DB 의 첫 차트마다 일어난다 |
| 내장 선곡 화면에도 육각형 | 질문 6, 범위 밖(새 렌더러 코드) |
| 꼬리까지 노트 수로 세는 IIDX 식 CN 처리 | LN MODE 에 따라 값이 달라진다. 보고서의 엣지 "Undefined 와 CN·HCN 이 같은 값"을 따랐다 |

## 영향과 관련 파일

- 코드: `crates/rbms-chart/src/radar.rs`(시험 43개), `crates/rbms-library/src/{lib,scan,songdb,songdb/rows,songdb/schema.sql}`, `apps/rbms-cli/src/main.rs`, `crates/rbms-render/src/skin_render/{refs,graphs/radar}.rs`, `apps/rbms-player/src/{library,stage/select/analysis,skin_host/chart,skin_host/overview}.rs`, `assets/skins/rbms-default/lua/{theme,select/radar,select/info}.lua`.
- 외부 스킨: 선곡에서 원본 id 350~353(종류별 노트 수)·92(주 BPM)·`judgegraph`·`bpmgraph` 가 값을 낸다(같은 분석 결과). 원본과 같아지는 변화이고 외부 스킨에서 보이는 것이 "지금 R-BMS 대비 바뀜"이다.
- 알려진 위험(테스트 부채 3.115~3.117): IIDX 대조 자료 없음, 세 축 가설과 스케일, NOTES 연주 시간·PEAK 창 이동·BSS 포함·스톱 처리·CN 꼬리의 노트 수 포함 여부는 확인하지 못한 가정, `#RANDOM` 분기가 있는 차트는 파서가 고른 한 갈래의 값(기존 밀도와 같은 한계), 레이더 계산과 분석 작업자의 프레임 비용은 재지 않았다(선곡 문서의 Lua 프레임 평균은 W3 전 0.23 ms 에서 W4 뒤 0.49 ms, 번역 뒤 영어 0.63 ms 로 늘었고 예산 초과는 0), 육각형의 방향과 축 각도는 하니스 캡처(CPU 캔버스)로만 확인했고 실제 GPU 창에서는 보지 못했으며 2P 레인(10·14키)과 큰 값 모양은 샘플 곡이 없어 캡처로 보지 못했다.
