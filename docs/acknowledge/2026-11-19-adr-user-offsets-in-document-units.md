## 배경

- 사용자 요청 요지(2026-11-19): 10 판정 표시 위치가 해상도에 따라 달라진다. 사용자가 이어 "절대좌표를 쓰는건가?" 라고 물었다(U5 보고에 인용됨).
- 조사 시점(10절)에는 원인을 읽기만으로 특정하지 못했다. 판정 글자는 이미지이고 문서 좌표(1920x1080)로 놓이는데, 오프셋(LIFT, Judge Position = 스킨 오프셋 100, `JUDGE_1P`)이 얽혀 있었다.

## 측정(2026-11-19, 구현 단위 U5)

앱 전체 경로(기본 스킨 팩, `FieldRun`, `HeadlessCanvas` CPU 렌더러. 픽셀 중심 샘플링이라 GPU 와 같다)로 7키 판을 직접 쳤다. 콤보 648, GREAT 를 40 ms 빨리 쳐 FAST 가 뜨게 하고 0.2 초 뒤 프레임을 그려 판정 글자·콤보·목표 차이·FAST 의 잉크 중심을 문서 좌표(1920x1080)로 환산했다. 크기: 1280x720·1600x900·1920x1080·2560x1440·3840x2160, 1728x972(16:10 레터박스 켬, 헤드리스에서는 뷰포트 크기와 같음), 1728x1117(레터박스 끔, 늘림).

### 오프셋 0(기본)

판정 글자·콤보 세 자리·목표 차이 숫자·판정선은 모든 크기에서 0.5 문서 화소 안에서 같았다. 예: 판정 글자 중심 y 가 646.07(1280x720)·646.19(1920x1080)·646.24(2560x1440)·646.18(3840x2160). 판정선 y 는 907.3~907.8, 판정선에서 글자까지의 간격은 261.1~261.7. LIFT 0.15 와 COVER 0.3 을 켜도 글자·숫자·판정선이 문서 단위로 같이 136 올라가고 간격은 260.98(1080)·261.47(720)·261.35(1440)였다. 남는 차이는 장치 화소 격자 안(720p 의 반 장치 화소 = 0.75 문서 화소)이다. 결론: 오프셋이 0 이면 이미지인 판정 글자·콤보·차이 숫자와 판정선 기준 상대 위치는 해상도에 무관하다.

### JUDGE POSITION Y = 30

판정 글자 잉크 중심의 이동량(문서 화소, 위로). 오프셋 0 일 때의 중심은 1280x720 646.07, 1920x1080 646.19, 2560x1440 646.24, 1728x972 646.13, 1728x1117 646.18 이다(U5 의 별도 측정에서는 647.49). 고치기 전 값은 U5 와 U9 가 각자 쟀고(1600x900 과 3840x2160 은 U5 만 쟀다) 고친 뒤 값은 U9 가 쟀다.

| 크기 | 고치기 전 이동 | 고친 뒤 이동 |
| --- | --- | --- |
| 1280x720 | 45.00 | 30.00 |
| 1600x900 | 36 | 고친 뒤에는 재지 않음 |
| 1728x972(레터박스 켬) | 33.33 | 30.00 |
| 1920x1080 | 30.00 | 30.00 |
| 1728x1117(레터박스 끔, 늘림) | 29.01 | 30.00 |
| 2560x1440 | 22.50 | 30.00 |
| 3840x2160 | 15 | 고친 뒤에는 재지 않음 |

고친 뒤 글자 중심은 616.07·616.19·616.24·616.13·616.18 이고 판정선은 모든 경우 907.4~907.8 로 그대로다. 1600x900 과 3840x2160 은 시험 시간 때문에 회귀 시험의 크기 목록에서 뺐다(메인 수정). 확인 실험으로 `DocumentOffsets::offset` 의 환산을 1:1 로 바꿨을 때 모든 크기에서 정확히 30 문서 화소였다.

## 원인

### 원인 1(주원인): 사용자 오프셋이 대상 화면 화소 단위로 저장·환산됐다

Judge Position(스킨 오프셋 100)과 엔진의 Judge offset·Judge Detail offset 을 포함한 모든 스킨 오프셋은 저장값이 대상(뷰포트) 화소이고, 프레임마다 `authored / target` 을 곱해 문서 단위로 바꿨다(`DocumentOffsets::drawn_at` / `offset`). 설계 문서가 "단위는 대상 픽셀"이라고 적었고 기존 시험(`the_default_pack_moves_its_judgement_by_its_position_and_hides_it_when_told_to`)이 화면 화소 이동을 고정하고 있었다. 대상 크기는 물리 화소(`canvas.native().size()`)라서 macOS Retina 2배 화면에서는 같은 창이어도 이동량이 반이 됐다. 같은 저장값이 1280x720 에서는 1.5배, 2560x1440 에서는 0.75배, 3840x2160 에서는 0.5배로 움직였다. 한편 `docs/skin.md` 는 Judge Position 을 "스킨의 1920x1080 기준"이라고 적고 있어 코드와 어긋났다.

### 원인 2(부원인, 작음): 스킨 TTF 글자의 장치 화소 맞춤

FAST/SLOW 는 텍스트다. `crates/rbms-render/src/skin_render/text.rs` 가 글자 원점을 장치 화소로 반올림하고 글리프를 장치 크기로 래스터해 폭과 위쪽 메트릭이 정수로 떨어진다. 그래서 FAST 중심이 16:9 크기 사이에서 x 1.4, y 1.5 문서 화소까지 흔들리고 왼쪽 모서리는 한 장치 화소 안에서 고정된다. 레터박스를 끈 16:10(1728x1117)에서는 이미지는 비균등으로 늘어나는데 글자는 세로 배율로 가로세로 비가 유지돼 FAST 폭이 59 에서 67.8 문서 화소로 15% 넓어진다(시작점은 그대로). [UI 글자 장치 화소 ADR](2026-10-22-adr-ui-text-device-pixels.md) 4)(a) O5 가 일부러 미룬 항목이다(테스트 부채 3.87).

| 의미 | 오프셋 하나는 그것이 더해지는 문서 레이아웃의 단위 그만큼 움직이고, 그림은 문서 전체와 함께 대상에 축척된다. 그래서 같은 숫자가 창 크기·해상도·표시 배율과 무관하게 화면의 같은 자리에 놓인다. 1280x720 으로 만든 문서는 자기 1280x720 단위로 읽는다 |

| 시험 | 기존 `the_default_pack_moves_its_judgement_by_its_position_and_hides_it_when_told_to` 의 기대 이동량을 `JUDGEMENT_MOVED_BY * HELD_SIZE.1 / 문서 높이` 로 바꿨다(960x540 에서 100 → 50 화소). `skin_screen/tests.rs` 의 화면 화소 기준 시험은 `a_nudge_is_answered_in_the_documents_own_units` 로 바꿨다. `judge_sizes.rs` 에 `Stance`(Plain·Lifted·Raised)와 `the_default_pack_raises_its_judgement_by_the_same_document_pixels_at_every_size` 를 더했다(JUDGE POSITION 30 이 모든 크기에서 같은 문서 좌표). 외부 스킨은 `stage/play/tests.rs` 의 `a_nudge_is_read_in_the_units_of_a_document_laid_out_at_another_size`(1280x720 문서를 1920x1080 대상에 그리면 nudge 50 이 75 대상 화소만큼 움직이고 예전 규칙의 50 화소 자리에는 그려지지 않음) |

## 레퍼런스와 달라지는 점

레퍼런스(beatoraja)는 이미 스케일을 마친 사각형에 오프셋을 더한다(`SkinObject.prepare`, `LaneRenderer.java:521-524`). 그래서 같은 숫자가 작은 창에서는 더 멀리, 큰 창에서는 덜 움직인다(출력 화소 단위). 이 플레이어는 오프셋을 문서 단위로 읽어 레퍼런스를 스킨 제작 해상도로 실행했을 때와 같은 결과를 낸다. 그 스킨을 레퍼런스에서 제작 해상도와 다른 크기로 쓰며 맞춘 값을 옮겨 오면 결과가 다를 수 있다. 확인한 소스는 U9 의 주석이 인용한 위치뿐이고 이 문서를 쓰며 레퍼런스 소스를 다시 열지 않았다.

## 이유

- 사용자가 본 문제는 같은 설정이 해상도·창 크기마다 다르게 보이는 것이다. 문서 단위로 읽으면 이 문제의 원인이 근본적으로 사라진다.
- 기본 스킨의 오프셋만 문서 단위로 바꾸면 규칙이 둘이 되어 외부 스킨과 엔진 오프셋이 따로 논다.
- 이 플레이어는 문서를 대상 크기로 축척해 그리므로 오프셋도 같이 축척하는 것이 일관된다.

## 영향과 관련 파일

- 코드: `apps/rbms-player/src/skin_screen.rs`(`DocumentOffsets`), `skin_screen/{preview,tests}.rs`, `stage/capture/play_parts.rs`·`play_parts/judge_sizes.rs`, `stage/play/tests.rs`, `text/menus/skin_menu.rs`.
- 설정 파일: 형식은 바뀌지 않는다. 같은 저장값의 뜻이 바뀐다.
- 알려진 위험(테스트 부채 3.173~3.175, 실기 QA 3.29 G9):
  - 이전 저장값을 옮기는 코드는 없다. 1920x1080 물리 화소가 아닌 화면(1280x720 창, 4K, Retina)에서 맞춘 오프셋은 이번 변경 뒤 한 번 다시 맞춰야 한다. 사용자의 실제 저장값과 화면은 보지 못했다.
  - 외부(beatoraja) 스킨의 오프셋을 레퍼런스에서 다른 크기로 맞춘 값을 옮기면 결과가 다를 수 있다.
  - 실제 창(GPU, Retina 배율)에서 JUDGE POSITION 을 움직여 보는 실기 확인은 하지 않았다. 측정은 헤드리스 CPU 캔버스로만 했다.
  - 원인 2(FAST/SLOW 장치 화소 맞춤)는 그대로다: 16:9 크기 사이 최대 1.5 문서 화소, 비 16:9 늘림에서 FAST 폭 +15%.
  - `judge_sizes` 시험이 기본 팩을 열 번 불러 CPU 로 그려 디버그 빌드에서 약 35 초 걸린다(CI 3 OS 의 시험 시간).
  - 사용자 설정이 오프셋 0 이라면 사용자가 본 현상은 원인 2 정도일 수 있다. 확정하지 못했다.
