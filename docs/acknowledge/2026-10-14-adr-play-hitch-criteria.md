# ADR: 플레이 중 렉의 기준 — 프레임 스레드에 막는 일 없음, 프레임 처리 p99 1 ms 미만, 언더런 0

> 최종 갱신 2026-10-15 · 대응 커밋 ea698a9
> 상태: 유효 · 결정일 2026-10-14 · 결정자 사용자(S19 결정 3, 추천안 A) · 커밋 `f81d499`, `4cc72d0`, `1676c57`, `c81eda1`(이 기준으로 고친 것)

## 배경

S19 지시 "플레이시에 렉걸릴 가능성 이런것들을 포함해서 고도화 및 최적화도 제대로 잘 해놔" 에는 "렉이 없다"의 측정 가능한 정의가 없었다. 메인이 기준을 추천안으로 냈다.

## 결정

플레이 중 렉이 없다는 것은 다음을 모두 만족하는 것이다.

1. 플레이 중 프레임 스레드에 디스크 I/O, 큰 할당(256 KB 이상), 잠금 대기, 동기 네트워크가 없다.
2. 헤드리스 계측에서 그리기(래스터화·화면 표시)를 뺀 플레이 단계 프레임 처리(갱신 + 그리기 큐 작성)의 p99 가 1 ms 미만이다.
3. 오디오 언더런이 0 이다.
4. 로딩·결과 화면으로 들어갈 때 끊김이 없다.

## 이유

- 판정은 입력 시각으로 하지만([입력 시각 ADR](2026-10-15-adr-event-time-judging.md)), 프레임 스레드가 막히면 키음·판정 표시·화면이 늦는다. 막는 일(I/O·잠금·네트워크)은 길이를 예측할 수 없으므로 "없음"으로, 계산 비용은 p99 로 잰다.
- 1 ms 는 120 Hz 프레임(8.3 ms)의 작은 몫이라 화면 표시·OS 몫을 남긴다.

## 기각된 대안

선택지 원문은 저장소에 남아 있지 않다(`docs/history/2026-10-15-process-archive.md` 의 S19 에는 사용자가 고른 A 만 적혀 있다).

## 영향과 관련 파일

- 계측 방법과 결과의 정본: `docs/reference/frame-cost.md`(조건, 표), `docs/development.md` 의 "Frame cost". 1차 결과: 같은 길이 합성 차트의 렌더 계측 p99 0.08~0.09 ms, 1 ms 초과 0, 결과 진입 프레임 8~9 ms → 0.3 ms(`docs/history/2026-10-15-process-archive.md` 의 S19).
- 이 기준으로 한 결정: 기록 저장을 저장 스레드로(`apps/rbms-player/src/save_worker.rs`), BGA 상주([BGA 상주 상한 ADR](2026-10-15-adr-bga-resident-texture-cap.md)), 화면 대기 분리([키보드 시각 ADR](2026-10-15-adr-keyboard-input-timing.md)).
- 남은 확인: `docs/quality-assurance/2026-10-14-test-debt.md` 3.38~3.40(실제 창·실기 측정, 한 번 생기는 큰 할당).
- 같은 결정 묶음의 다른 항목(작업 방식: Workflow 사용, 영역별 찾기→재현→수정→회귀 반복, 판정·점수 의미가 바뀌는 수정은 고치기 전에 확인)은 작업 규칙이라 ADR 로 두지 않는다(`docs/history/2026-10-15-process-archive.md` 의 S19). 판정 의미를 확인받은 9건은 각 ADR 에 있다.
