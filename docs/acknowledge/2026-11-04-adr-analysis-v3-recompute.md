# ADR: 분석 엔진 v3, 버전 두 개를 함께 올리고 운영에서 다시 계산한다

> 최종 갱신 2026-11-04 · 대응 커밋 2026-11-04 AI 훈련곡 작업(커밋 예정)
> 상태: 유효 · 결정일 2026-11-04 · 결정자 사용자(D6), 메인 추천(M2·M7·M24·M33). 사용자 확인 전: 미확인 목록 35번(M 결정) · 커밋 예정. 운영 재계산은 아직 실행 전.

## 배경

- 사용자 결정 D6: 분석 고도화 뒤 `PLAY_ANALYSIS_VERSION` 을 올리고 기존 판 전체와 발광 표 곡 특징을 다시 계산한다. 운영 실행은 개수 확인 뒤 사용자 `!` 이고 읽기 count 와 쓰기를 분리한다.
- 조사 01 5.1: 고정 1초 창은 경계에서 밀도를 쪼개 순간 대 지속을 가르지 못한다.

## 결정

1. **국소 밀도 정의**(M2): 판정 노트마다 중심 2초 창의 NPS 를 잰다. 문맥은 1초·8초 창의 비로 `burst`(순간)와 `sustained`(지속)로 가른다. 창의 끝은 판 길이가 아니라 **마지막 판정 노트 + 1 µs** 로 자른다(판 길이에는 곡 끝 뒤 5초가 더해져 끝 노트의 밀도가 최대 절반으로 낮게 읽히기 때문이며, 판과 곡 특징이 같은 함수를 쓴다).
2. **버전 둘을 함께 올린다**(M7): 곡 특징 `ANALYSIS_VERSION` 1 → 2(`nps`·`combos`·`bpm_main_band`), 판 요약 `PLAY_ANALYSIS_VERSION` 2 → 3(국소 밀도·태그별 오차·손·실패 구간·게이지 꺾임 문맥·조합·구간 결과). 추천·연습 폴더가 프로필과 같은 단위로 곡을 고르게 하려는 것이고, 재계산은 한 번에 끝낸다.
3. **재계산 경로는 새 서비스 메서드 없이 기존 공개 메서드만 쓴다**(M24): `web/scripts/analysis-recompute.ts <count|apply>` 가 `chartPatternService.coverage`·`recomputeStale` 과 `traceService.adminUsage`·`recomputeStale` 을 부른다. 배치 100, 시간 상한 8분(Actions 작업 제한 10분보다 짧게), 상한에 닿으면 멈추고 같은 동작을 다시 실행하면 이어진다. Actions 로그가 공개이므로 출력은 숫자뿐인 고정 문장 셋이다. `web-db.yml` 에 읽기 `analysis-recompute-count` 와 쓰기 `analysis-recompute`(세기 → 계산 → 세기)를 분리해 더했다.
4. **운영 반영 순서**(M33): 버전을 올린 코드는 재계산 경로가 든 코드와 함께 푸시하고, 그 직후 메인이 count 를 실행해 남은 수를 보이고, 쓰기는 사용자가 `!` 로 실행한다. 나머지 코드(W3~W5)는 분석 버전을 바꾸지 않아 재계산이 다시 필요 없다. 0014 마이그레이션은 그보다 먼저 적용한다.
5. **재계산이 끝날 때까지의 동작을 알려진 동작으로 둔다**: 판 기능은 한 번의 읽기에서 낡은 판 최대 10개만 다시 계산하고 나머지는 `stale` 로 빼 표본 부족 안내가 늘 수 있고, 약점 프로필은 `stale` > 0 이면 저장하지 않아 요청마다 계산하며, 점수 기반 기능은 낡은 곡 특징으로 밀도·조합 일치를 0 으로 둔다. 오류는 나지 않는다.

## 이유

- 읽을 때 지연 재계산만으로는 프로필이 매 요청 300판을 계산하고 표본이 줄어든 채로 오래 남는다. 일괄 재계산은 이미 있는 관리자 재계산과 `dan-recompute` 선례를 따른다.
- 공개 로그에는 사용자 식별자·수치 외의 내용이 나가지 않아야 하므로 출력을 숫자로 고정한다.

## 기각된 대안

- 읽을 때 재계산만 하고 일괄 경로를 두지 않는다: 위와 같다.
- 곡 특징과 판 요약 버전을 따로 올려 재계산을 두 번 한다: 같은 날 두 번의 운영 작업이 된다. 요약이 두 버전을 함께 저장하므로 어느 한쪽만 올려도 다시 계산되지만, 이번에는 한 번에 끝낸다.
- 서비스에 일괄 재계산 메서드를 새로 만든다: 같은 웨이브 단위와 파일이 겹친다.
