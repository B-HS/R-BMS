## 요약

U1 블루투스 출력 지연을 구현했습니다. (1) `rbms-audio` 에 새 모듈 `latency.rs` 를 만들었습니다. macOS 에서만 `coreaudio-rs`(cfg 로 나눔, `unsafe` 없음)로 열린 장치의 `ltnc + saft` 프레임과 전송 종류(blue/blea)를 읽고, 그 밖의 OS 에서는 None 을 돌려줍니다. 조회는 `host::output_device_latency` 가 호스트 스레드(`ask`)에서만 합니다. (2) 엔진은 스트림을 열 때(`open_first_rung`) 장치 지연을 읽어 `AudioOpenReport.output_latency` 에 담습니다. `set_output_latency_compensation`·`refresh_output_latency` 로 정해진 보정값은 스냅샷을 읽는 쪽(`snapshot_of`)에서 콜백이 낸 `playback_ahead` 에 더합니다. 200 ms 검사는 콜백 안에서 백엔드 값에만 걸리고, 보정값 상한은 `MAX_OUTPUT_LATENCY_MS = 1000` 입니다. `ClockSnapshot.output_latency`, `AudioClocks.output_latency_us`, `AudioClocks::run_anchor_us` 를 더했습니다. (3) 예약 경로를 코드로 확인했습니다. scheduled_us(프레임 축)는 지연과 무관해 예약 위치는 그대로입니다. 다만 `start_play` 가 가청 위치에 판을 고정하면 차트 앞부분(지연만큼)의 BGM·키음이 이미 지나간 프레임으로 예약돼 늦게 시작되는 결함이 있었습니다. 이를 `anchor = audible + 보정값`(run_anchor_us)으로 고쳤고, 곡 위치는 지연만큼 0 에 머문 뒤 진행합니다. OFF 에서는 보정값이 0 이라 지금과 같은 시계입니다. (4) 설정은 `AudioOptions.compensate_output_latency`(기본 true, serde default)와 AUDIO 탭 OUTPUT 구획의 OUTPUT LATENCY(AUTO/OFF) 행입니다. `SettingId::OutputLatency` 를 열거 끝에 더해 `SETTING_COUNT` 가 101 이 됐습니다. 스트림을 다시 열지 않고, 차트가 스트림을 쥔 화면(Decide·Loading·Play·Result) 밖에서는 다음 프레임에 바로 반영됩니다. (5) 지연값은 스트림을 열 때와 `load()`(판 시작 전 로딩)에만 다시 읽고, 판 도중에는 바꾸지 않습니다. (6) 보정값이 30 ms 이상이면 스트림을 연 뒤 한 번 알립니다(일반·블루투스 두 문구, 세 언어, 출력 지연·판정 오프셋 행 이름 사용). 디버그 오버레이에 `OUTPUT LATENCY ... COMPENSATED ...` 한 줄을 더했습니다. (7) Info.plist 에 `GCSupportsGameMode`·`LSSupportsGameMode` true 를 넣었습니다. 이 Mac 실측: AirPods Pro 2 7,680 프레임(48 kHz 160 ms, bluetooth true), MacBook Pro 스피커 108 프레임(2.25 ms). rbms-player 를 스크래치 HOME 으로 실제로 띄웠을 때 stdout 에 `audio: <AirPods Pro 2 장치명> adds 7680 frames (160.0 ms) over Bluetooth, compensating 160.0 ms` 와 블루투스 알림 문구가 찍혔습니다(판은 플레이하지 않았습니다).

## 결정한 것

- 보정값은 콜백이 아니라 게임 스레드가 스냅샷을 읽을 때(`snapshot_of`) 더합니다. 콜백은 새로 읽는 값이 없습니다. 이유: 로딩 직후 바로 start_play 하는 경로(디코드할 것이 없는 차트)에서 콜백 한 번을 기다리지 않아도 새 값이 바로 반영되고, 이전 콜백 기록과 섞여 판 도중 가청 위치가 튀지 않습니다. 효과는 계획의 '콜백이 내는 playback_ahead 에 더한다'와 같습니다.
- 판 시작 기준점은 `AudioClocks::run_anchor_us = audible_us + output_latency_us` 입니다. 이렇게 하지 않으면 160 ms 장치에서 차트 첫 160 ms 의 BGM(곡 전체가 든 BGM wav 포함)이 지난 프레임으로 예약돼 늦게 시작됩니다. 엔진 시험이 이 결함과 해결을 함께 보입니다.
- 설정 행 `SettingId::OutputLatency` 는 행 인덱스가 밀리지 않게 열거 끝에 두었습니다. 표·탭·구획에서는 AUDIO 탭 OUTPUT 구획의 POLYPHONY 다음에 나옵니다. 값 표기 AUTO/OFF 는 용어집대로 세 언어 모두 원어이고, 행 이름은 OUTPUT LATENCY / 출력 지연 / 出力遅延 입니다.
- 토글 반영은 `poll_audio_reopen`(매 프레임, app_play.rs)에서 `audio_reopen_blocked` 와 같은 조건으로 합니다. `stage/settings.rs`(소유 밖)를 고치지 않고도 설정 화면에서 바로 반영되고, 판 도중에는 바뀌지 않습니다.
- 판 시작 전 재조회 위치는 `AppShared::load()` 의 `ensure_audio()` 바로 뒤입니다. 연습 구간 재시작(`start_practice_slice`)은 load 를 거치지 않아 재조회하지 않습니다(설정 토글은 따름).
- 프레임 → 시간 변환은 스트림 샘플레이트를 씁니다. cpal 이 장치 nominal rate 를 스트림 rate 로 맞추므로(cpal device.rs:751) 같습니다.
- 알림 임계 30 ms 는 이름 있는 상수 `OUTPUT_LATENCY_NOTICE_MIN` 입니다. 블루투스 여부에 따라 알림을 `OutputLatencyCompensated`·`OutputLatencyCompensatedBluetooth` 두 개로 나눴습니다.
- 선택자는 objc2-core-audio 를 직접 의존하지 않고 `u32::from_be_bytes(*b"ltnc")` 형태의 이름 있는 상수로 두었습니다. 조사 1.2 의 16진 값과 같은지 시험으로 확인합니다.

## 계획과 달라진 점

- 계획 U1-2 의 '콜백이 내는 playback_ahead 에 더한다'를 '스냅샷을 읽을 때 더한다'로 구현했습니다(이유는 decisions 첫 항목). 공개 결과(`ClockSnapshot.playback_ahead` 에 지연 포함)는 같습니다.
- 소유 범위('오디오 열기·다시 열기 부분')를 조금 넘어 app_play.rs 의 `start_play`(기준점), `load()`(재조회 한 줄), `poll_audio_reopen`(토글 반영), `debug_audio_lines`(한 줄)를 고쳤습니다. 과업이 명시한 '예약 경로 확인 뒤 못 하면 고친다', '판 시작 전 재조회', '디버그 한 줄'에 필요한 범위입니다.
- `crates/rbms-config/src/tests/audio.rs`(설정 오디오 시험 파일)에 시험 하나를 더했습니다. 병합 주의 목록의 `tests.rs` 의 하위 모듈입니다.
- 설정 계약 시험 `app_result::record_tests::contract_requests::a_settings_upload` 가 실패합니다. 설정 문서에 `compensate_output_latency: true` 가 늘었기 때문이고, 지시대로 contract/ 를 다시 만들지 않았습니다. 메인이 `RBMS_UPDATE_CONTRACT=1` 로 다시 만들어야 합니다.

## 남은 위험

- Windows·Linux 컴파일은 로컬에서 확인하지 못했습니다(타깃 미설치). CI 결과로 확인해야 합니다.
- 실제 판에서 체감 확인(AirPods 로 BGM·노트·판정이 맞는지)은 하지 않았습니다. 실기 점검 항목이 필요합니다. 기준점 이동으로 판 시작 직후 곡 위치가 보정값만큼(160 ms) 0 에 머뭅니다. READY 다음의 정지 화면이 그만큼 길어지는 모양이고, 스킨 PLAY 타이머 기준 애니메이션은 차트 시간보다 그만큼 앞섭니다.
- 디버그 지표 'CLOCK quantised gap'(보간 시계 대 렌더 프레임 시계)과 soak 기록의 interp-quantized 평균이 보정값만큼 커집니다(지표 의미 변화, 판정 영향 없음).
- 보정이 켜지면 예약이 최대 지연만큼 더 앞서 걸려 대기 중인 보이스가 늘어납니다(400 ms·초당 60건이면 약 24개, 상한 512 대비 작음).
- macOS 에서 시험이 실제 오디오 장치를 열면(기존 ensure_audio 시험들) 기본 출력이 블루투스일 때 보정이 켜집니다. 이 Mac 에서는 전체 player 시험이 통과했습니다.
- macOS Game Mode 에 들어가고 나올 때 지연이 바뀌어도 판 도중에는 반영하지 않습니다(M5). 다음 로딩에서 다시 읽습니다. 연습 구간 재시작은 load 를 거치지 않아 다시 읽지 않습니다.
- 키음은 눌린 뒤 예약되므로 여전히 장치 지연만큼 늦게 들립니다(조사 1.4, 설명 문구에 적음).
- 새 일본어·한국어 문구(행 이름·설명·알림)는 모델 초안입니다.
