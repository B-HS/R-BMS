## 요약

U3 구현 완료: 패드/키보드 보조 Esc 와 조작·단축키의 2키 조합(키보드·패드).

1) ESC: `ControlAction::Escape`(화면 이름 `ESC`, 설정 키 `ESCAPE`, ControlBinds.escape 기본 빈 값, 패드 기본 없음, ALL 21개). 키보드는 공통 래퍼 `Stage::handle_key` 가 ESC 단일 키의 누름·뗌·반복을 `KeyCode::Escape` 로 바꿔 옵션 오버레이→화면 순으로 넘긴다. 패드는 `PadTarget::event` 가 ESC 만 뗌도 내고, 프레임 루프가 이벤트마다 `PadMark{pressed, made_a_chord}` 를 `HeldKeys` 큐에 넣으면 `Stage::handle_pad` 가 하나씩 꺼내 Escape 누름/뗌 KeyInput 으로 바꿔 넘긴다(IMMEDIATE·HOLD·DOUBLE TAP 모두 키와 같은 경로). 물리 Esc 고정 키 규칙은 그대로. ESC 는 모든 단축키·레인·조작과 read_with=true.

2) 조합: `keyconfig/chord.rs` 에 `KeyBind{Single, Chord}`(토큰 `A+B`, 표기 `A + B`, 순서 무관 비교), 순수 함수 `held_chords_with`·`keys_in_held_chords`, 편집기용 `ChordCapture<T>`(키보드·패드 공용). `KeyConfig::control_bind`/`shortcut_bind`/`bind_keys`/`chords`/`clash_of`/`chord_overlap`, `control_key`/`shortcut_key` 는 단일 키만(조합이면 None). 패드는 `PadConfig.control_chords`·`shortcut_chords`(둘째 요소 표, serde default)와 `bind_chord`/`control_chord`/`chord_of`, 매퍼는 단일/쌍 계획(`PadPlan`)으로 쌍 완성 시 1회 발사, 완성시킨 누름의 단일 조작·단축키 억제(레인은 발사+mark), held 는 쌍이 눌린 동안 참이고 쌍에 묶인 요소의 단일 조작/단축키(START 등)는 빠진다. 키보드 쪽은 `note_key` 가 ChordEvent(만든/깬 조합)를 HeldKeys 에 기록하고, 래퍼가 조합 조작은 `handle_pad(PadEvent::Control)` 로(ESC 는 Escape 키로) 먼저 넘긴 뒤 원래 키를 넘긴다. `control_for` 는 조합 완성 누름에서 None, `shortcut_for`/`is_shortcut` 은 조합 단축키를 돌려주고 단일은 억제, `control_held`·`control_repeating`·`shortcut_held`·`fine_pressed`·`keyboard_index_pressed` 는 조합 이해 + 조합에 묶인 키는 단일로 세지 않음(명시 조합이 START·SELECT+레인 내장 조합보다 우선). 레인: PLAY 화면에서는 완성 누름도 판정, 그 밖의 화면에서는 조합의 것(lane_input_for None, 패드 Lane 누름 버림). 포커스 잃음은 기존 release 경로로 조합·ESC 가 풀린다.

3) 충돌: `clash_among` 이 KeyBind 를 받아 같은 화면 같은 조합(순서 무관) 거절, 고정 키 포함 조합 거절, 조합의 한 키가 다른 대상의 단일 키이면 거절하지 않고 `overlap_among`/`chord_overlap`/`pad_overlap` 로 편집기가 안내(ChordKeyAlone/KeyInChord, warn 색). 같은 조합 거절은 ChordTaken 문구.

4) 편집기: 조작·단축키 칸은 한 키 눌렀다 떼면 단일, 첫 키를 누른 채 둘째 키를 누르면 조합(패드도 `PadCapture` 가 누름/뗌을 전달, 16개 상한), 레인 칸은 첫 누름 확정. 편집기는 키를 있는 그대로 읽고(`reads_keys_as_they_are`), 패드 칸이 요소를 기다리는 동안은 패드 ESC 를 받지 않는다(`takes_pad_escape`). 표기 `A + B`/`BUTTON 4 + BUTTON 5`. 힌트 문구 2개·알림 3개·ESC 라벨 세 언어 추가.

5) 키 가이드(H): 조합을 `A + B` 로, 플레이 중 ESC 줄에 ESC 에 준 키를 `ESC / BACKSPACE` 로 표시.

시험: 조합 상태 기계(순서 무관, 반복, 단일 억제, 레인 통과, 포커스 잃음, START 우선순위), 옛 키 설정 파일(단일 토큰·escape 없음·패드 둘째 요소 표 없음) 읽기와 조합 왕복, 패드 쌍(순서·억제·held·디바운스·ESC 누름/뗌·캡처), ESC 패드 버튼의 IMMEDIATE·HOLD·DOUBLE TAP 이 PLAY 를 키와 같게 떠나는 시험, 편집기 캡처·거절·안내, 가이드 표기.

## 결정한 것

- ESC 키보드 치환·조합 해석은 공통 래퍼 Stage::handle_key 에서, 패드 ESC 는 Stage::handle_pad 에서 Escape KeyInput 으로 바꿔 deliver_key(옵션 오버레이→화면)로 넘긴다. 화면별 코드는 건드리지 않았다.
- 패드 이벤트가 화면 밖(lib.rs)에서 분배되므로 PadEvent enum 은 바꾸지 않고, 이벤트별 부가 정보(PadMark: 누름/뗌, 조합을 만든 누름의 레인인지)를 poll_pad 가 HeldKeys 큐에 이벤트 순서대로 넣고 Stage::handle_pad 가 하나씩 꺼낸다. 큐가 비면 '누름'으로 본다(직접 handle_pad 를 부르는 기존 시험 호환).
- AppShared(lib.rs)는 소유 밖이라 조합 이벤트(ChordEvent)와 패드 mark 큐를 이미 AppShared 안에 있는 KeyConfig.held(HeldKeys, serde skip)에 두었다. 조합 이벤트는 래퍼가 키 하나를 처리하는 동안만 살아 있다.
- 키보드 조합 조작은 control_for 로 돌려주지 않고 래퍼가 handler().handle_pad(PadEvent::Control) 로 먼저 넘긴다. PLAY 의 handle_key 는 조작이 맞으면 레인 처리 전에 반환하므로, 이렇게 해야 stage/play 를 고치지 않고도 완성 누름의 레인이 판정된다. 조합 단축키는 shortcut_for/is_shortcut 이 조합 단축키를 돌려주는 방식(키 경로)이라 설정 화면·옵션 오버레이처럼 패드 단축키를 안 읽는 화면에서도 키 조합이 동작한다.
- 레인 통과 규칙: PLAY 화면(StageId::Play)에서만 조합 완성 누름의 레인을 판정으로 보내고, 그 밖의 화면에서는 그 누름의 레인 의미(키 인덱스)를 조합의 것으로 막는다. 선곡에서 START+레인 조합을 명시로 묶었을 때 레인 키가 '플레이 시작' 같은 키 인덱스로 새지 않게 하기 위함(M12·위험 U3 '명시 조합 우선').
- 조합이 눌려 있는 동안 그 키들은 단일 대상(START·SELECT·단축키 held, 키 인덱스)으로 세지 않는다. 패드도 같다(레인 held 는 유지).
- 편집기 안내: 조합의 한 키가 다른 대상의 단일 키이거나 단일 키가 다른 대상의 조합에 들어 있으면 양쪽 줄 모두 안내(ChordKeyAlone / KeyInChord). 두 조합이 키 하나를 공유하는 것은 안내하지 않는다(단독 동작이 없으므로).
- 편집기는 키보드를 항상 날것으로 읽는다(ESC 에 준 키도 편집기 안에서는 그 키, 예: BACKSPACE=기본값). 패드 ESC 는 패드 칸이 요소를 기다리는 동안만 받지 않고 그 밖에는 저장 후 나가기.
- PadCapture 는 프레임 루프가 편집기 밖에서도 모든 변화를 기록하므로 보관 개수를 CAPTURE_EVENTS_KEPT=16 으로 제한했다. 축은 CAPTURE_AXIS_THRESHOLD 를 넘을 때 누름, 안으로 돌아올 때 뗌.
- 한 키를 두 번(A+A), 이름 없는 키, 아날로그 턴테이블, 패드를 못 받는 단축키(OptionsPin/Hold/RefDetail)는 조합으로 묶이지 않는다. 패드 단일 지정·해제는 둘째 요소도 지운다.

- PadMapper::resolve_changes 는 소유 밖 시험(stage/play/input_time_tests.rs)이 (PadEvent, i64) 를 기대해서 #[cfg(test)] 래퍼로 남기고, 프레임 루프는 새 resolve_changes_marked(마크 포함)를 쓴다. PadState::poll_now 반환형은 (PadEvent, Instant, PadMark) 로 바뀌었고 호출자는 소유 파일 app_input.rs 의 poll_pad 뿐이다(lib.rs 는 그대로).
- 소유 밖이라 고치지 않은 표시: stage/settings.rs:965(PLAY MENU·SKIN MENU·KEY CONFIG 단축키 안내)와 app_options.rs:298(옵션 오버레이 PIN 키 안내)은 shortcut_key(단일)를 읽어 조합으로 묶으면 키 없음으로 표시된다. 동작은 정상(조합으로 열림), 표기만 빠짐.
- 스킨 바닥 표기(select/controls.lua 의 HINT_KEYS)는 고정 키(ENTER·ESC·H 등) 정적 문구라 조합이 나타날 자리가 없어 바꿀 것이 없었다(U3 계획 5항의 '스킨 바닥 표기'는 해당 없음).
- 계획서 U3 3항 문구 '조합이 완성된 누름은 그 키의 단일 조작·단축키를 누른다'는 M12 에 따라 '누르지 않는다'로 구현했다.
- contract/client-requests/settings-blob.json 은 고치지 않았다(설정 업로드 본문의 keyconfig 에 controls.escape 와 pad.control_chords·shortcut_chords 가 늘어 a_settings_upload 시험이 실패 — 메인이 RBMS_UPDATE_CONTRACT=1 로 다시 만들어야 함).

## 남은 위험

- 설정 계약(a_settings_upload)이 재생성 전까지 실패한다. 웹 쪽 client-requests 시험도 메인이 함께 확인해야 한다.
- 옛 빌드가 새 파일을 읽으면 조합 토큰(A+B)은 단축키는 기본 키로, 조작은 키 없음으로 읽힌다(앞으로의 호환은 보장하지 않음). 패드 control_chords 는 옛 빌드가 무시해 첫 요소 단일로 동작한다.
- 패드 mark 큐는 lib.rs 가 poll_pad 결과를 빠짐없이 순서대로 handle_pad 에 넘긴다는 전제에 기댄다(현재 코드는 그렇다). 이 루프를 바꾸면 ESC 누름/뗌 판단이 어긋날 수 있다.
- PLAY 밖 화면에서 조합 완성 누름의 레인 의미를 막으므로, 레인 키를 조합에 쓴 사용자는 선곡에서 그 누름이 키 인덱스로 쓰이지 않는다(의도). LAYOUT PICK·결과 등 레인을 읽는 다른 화면도 같은 규칙이다.
- ESC 에 준 키가 짝 없이 뗌만 화면에 갈 수 있다(조합 완성 누름으로 억제된 뒤 뗌). PLAY 의 HOLD 는 뗌을 취소로 보아 해가 없고 다른 화면은 뗌을 무시한다.
- 설정 화면·옵션 오버레이의 키 안내 문구는 조합을 표시하지 못한다(소유 밖, deviations 참조).
- 포커스를 잃을 때 편집기가 키보드 조합 캡처 중이면 첫 키의 뗌이 단일 지정으로 확정된다(드문 경우).
