# 긴 빌드 전에 시크릿·환경 값부터 확인

최종 갱신 2026-10-15 · 대응 커밋 ea698a9

## 무엇을 지적받았나

릴리스 워크플로가 macOS 서명 인증서를 유니버설 빌드(10분 넘게)가 끝난 뒤에야 풀어 보아, 인증서 값이 틀린 것을 세 번의 실행에서 매번 빌드 뒤에 알았다. 사용자 발언(2026-10-13): "signcheck등 env를 먼저 체크하는 step을 build 시작전에 먼저 체크해 자꾸 빌드뒤에 처넣어서 오래걸리잖아". 이어서 "로컬에서도 미리 테스트를 해봐야할듯한데 taide 같은 프로젝트보면 스크립트있으니 한번가져와봐".

## 왜 틀렸나

값만 맞으면 되는 확인(시크릿의 꼴, 인증서 암호, 공증 계정 로그인)을 그 값을 쓰는 단계 바로 앞에 두었다. 실패 비용이 빌드 시간만큼 커졌고, 값을 볼 수 없는 시크릿이라 오류 문구(`base64: error decoding base64 input stream`)만으로는 무엇이 틀렸는지도 몰랐다.

## 어떻게 고쳤나

- `release.yml` 의 macOS 잡 첫 두 단계에서 인증서를 키체인에 넣고 공증 계정으로 로그인해 본다(빌드 전).
- 빌드 없이 시크릿만 보는 `signing-check.yml` 을 두고, 값 대신 꼴(바이트 수, base64 밖 바이트의 값과 위치)을 알린다.
- 로컬 검증 스크립트 `scripts/verify-signing-cert.sh`(`--set-secret`), `scripts/verify-notary-credentials.sh`.

## 언제 적용하나

CI·릴리스·배포 파이프라인을 새로 쓰거나 고칠 때. 오래 걸리는 단계가 있고 그 뒤에서 외부 자격 증명·환경 값을 쓰는 경우에 한한다. 같은 원칙은 운영 DB 작업(web-db 의 status 를 먼저)에도 썼다. 관련 결정: `docs/acknowledge/2026-10-14-adr-release-policy.md`.
