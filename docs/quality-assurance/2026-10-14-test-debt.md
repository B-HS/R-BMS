# 테스트 부채 (2026-10-14)

최종 갱신 2026-10-14(2절 교차 테스트 완료, S18-4) · 대응 커밋 7095ef7 · 근거: `docs/ci-release.md`, `docs/bug/2026-10-14-score-submit-400-large-seed.md`, `docs/quality-assurance/2026-10-11-default-skin-manual-check.md`

이 문서는 지금 하지 않은 검증과 그 이유를 적는다(`ai-process.md` 8절: 재현 조건, 생략 이유, 남은 위험, 실행이 필요해지는 시점). 1절은 이번에 부채가 사고로 터진 기록이고, 2절은 그 재발을 막는 교차 테스트의 설계이며, 3절은 나머지 공백의 목록이다. 각 항목은 "실행이 필요해지는 시점"에 닿으면 이 문서에서 지우고 해당 테스트나 QA 항목으로 옮긴다.

## 1. 사고: v0.1.2 의 모든 판이 점수 서버에서 400 으로 거절됨

| 항목 | 내용 |
| --- | --- |
| 증상 | v0.1.2 로 한 판을 쳐서 보내면 서버가 400 으로 거절한다. 일반 판, SCRATCH AUTO 판, 리플레이 업로드가 같다(시드를 보내는 본문 전부). 로컬 기록은 정상이다 |
| 원인 | 클라이언트는 새 판의 배치 시드를 시계의 나노초(약 1.79e18, 예 `1_791_970_074_354_000_000`)로 만들었다(`apps/rbms-player/src/app_play.rs`, 초기 구현 2026-05-31 `39fdebc` 부터 `d.as_nanos() as u64`). 서버의 `seed` 검증은 `z.number().int()` 였고(`web/src/server/dto/score.ts`, `replay.ts`, 2026-09-09 `a2b2534` 부터) Zod 4.5.4 의 `int()` 는 안전한 정수(절댓값이 `2^53 - 1 = 9_007_199_254_740_991` 이하)만 받는다. JSON 에서 읽은 큰 수는 정밀도도 잃는다(`JSON.parse` 가 `1791970074354123456` 을 `1791970074354123500` 으로 읽는다) |
| 수정 | 서버: `seedSchema`(`web/src/server/dto/common.ts`)가 안전한 정수가 아니면 0 으로 저장하고 기록은 받는다(`d733a8f`). 클라이언트: 새 판의 시드를 시계의 아래 53비트로 만든다(`fresh_layout_seed`, `LAYOUT_SEED_MASK = (1 << 53) - 1`, 0 은 1 로, `7095ef7`). 리플레이와 다시 하기가 넘겨받는 시드는 기록된 그대로 쓴다. 두 쪽 모두 필요하다: 서버만 고치면 옛 클라이언트의 리플레이 시드가 0 으로 남고, 클라이언트만 고치면 이미 나간 빌드가 거절된다 |
| 확인 | 서버 쪽은 `web/tests/dto/ir-contract.test.ts`(2^53 을 넘는 시드는 0, `2 ** 53 - 1` 은 그대로)와 `web/tests/service/replay.test.ts`. 클라이언트 쪽은 `app_play.rs` 의 `a_fresh_layout_seed_fits_what_the_score_server_reads_exactly`. 운영 서버에서 실제 판이 `IR: RANK` 로 돌아오는지는 사용자가 한 판 쳐서 확인하는 일이 남아 있다(QA 항목 X3, W3) |

### 1.1 왜 테스트가 못 잡았나

두 쪽의 계약 테스트가 같은 틈을 갖고 있었다. 각자 사람이 손으로 적은 작은 값으로 본문을 만들었고, 실제 판이 만드는 값은 한 번도 상대 쪽 검증을 통과해 본 적이 없다.

| 테스트 | 위치 | 쓴 시드 | 다른 손으로 쓴 값 |
| --- | --- | --- | --- |
| 서버 스키마 테스트 | `web/tests/dto/ir-contract.test.ts` | `0` | 해시 `'abc123'`, `'def456'`(실제는 32자·64자 16진수), `played_at: 1700000000000` |
| 클라이언트 계약 테스트 | `crates/rbms-ir/src/contract_tests/fixtures.rs` | `42` | 해시 `"0a1b2c3d"` 8번 반복(64자), `green_number: 310.0` |
| 실서버 왕복 | `crates/rbms-ir/tests/e2e_local.rs` | `42` | `RBMS_IR_E2E_URL` 이 없으면 건너뜀. 로컬 서버를 가리켜도 시드는 42 |
| 서버 DB 통합 | `web/tests/db/scratch-auto-ranking.test.ts` | 작은 값 | `RBMS_DB_E2E` 가 없으면 건너뜀. 웹 CI 에는 MySQL 이 없어 CI 에서는 항상 건너뜀 |

- Rust 쪽 테스트는 직렬화한 본문이 서버가 약속한 모양인지만 본다(`serde` 가 만든 JSON 문자열에 필드가 있는가). 값의 범위가 서버 스키마를 통과하는지는 보지 않는다.
- 웹 쪽 테스트는 `scoreSubmissionSchema.parse()` 가 통과하는 입력을 사람이 적었고, 실제 판이 만드는 값(`fresh_layout_seed` 의 결과, 실제 해시 길이, 실제 f32 값)을 쓰지 않았다.
- 2026-05-31 에 시드 생성이, 2026-09-09 에 서버 스키마가 이미 있었다. 둘이 한 번도 만나지 않다가 2026-10-14 에 클라이언트가 처음으로 운영 서버에 로그인해 제출하면서(웨이브 18, `8b11a17`) 만났다.
- 서버의 `seedSchema` 는 이제 벗어난 시드를 조용히 0 으로 바꾼다. 같은 종류의 클라이언트 회귀(나노초 시드로 되돌아감)는 400 이 아니라 시드 0 의 기록으로 나타나 더 늦게 드러난다. 교차 테스트는 입력과 파싱 결과가 같은지(`parsed.seed === input.seed`)까지 단언해야 한다(2.3절).

해소 기록(2026-10-14, S18-4): 위 표의 틈은 2절의 교차 테스트로 막았다. 실제 판이 보낸 본문 14개가 `contract/client-requests/` 에 있고, Rust 테스트가 그 파일과 지금 클라이언트가 보내는 본문을 비교하며, 웹 테스트가 같은 파일을 서버 스키마·라우트 검사·서비스에 통과시킨다(2.7절). 서버 DB 통합 테스트는 `web.yml` 의 `db` 잡이 임시 MySQL 로 돌린다(3.6). 위 표의 손으로 적은 테스트들은 그대로 두었다(각자 다른 것을 본다).

## 2. 부채 1(최우선): 실제 판이 만든 요청 본문을 서버 스키마로 통과시키는 교차 테스트

상태: 완료(2026-10-14, S18-4). 구현과 설계에서 달라진 점은 2.7절에 있다. 2.1~2.4 는 설계로 남긴다. 같은 종류의 사고(한쪽이 만든 값이 다른 쪽 검증을 못 넘음)를 값 범위 전체에 대해 막는다. 반대 방향(2.5)은 아직이다(3.12).

### 2.1 설계

1. Rust 가 뽑는다. 실제 판의 코드 경로가 만든 요청 본문을 `serde_json` 으로 직렬화해 JSON 파일로 쓴다. 본문을 만드는 코드는 `apps/rbms-player/src/app_result.rs`(`ScoreSubmission`, 143행 근처), `apps/rbms-player/src/course_ir.rs`(`build_course_submission`), `apps/rbms-player/src/ir_replay.rs`(`to_ir_replay`)에 있고, `rbms-ir` 의 제출 워커(`crates/rbms-ir/src/worker.rs` 의 `run_submit`)가 `clamp_to_server_bounds()` 를 부른 뒤 보낸다. 가장 좋은 지점은 워커가 본문을 보내기 직전이다: 앱 테스트가 `ScoreServer` 를 구현한 기록용 가짜(`ir_session.rs`, `ir_ranking.rs` 의 테스트용 가짜와 같은 방식)를 주입하고, 실제 `run_submit` 이 보내는 값 그대로를 받아 쓴다.
2. 파일은 저장소에 커밋하는 한 폴더에 둔다(제안: `contract/client-requests/<이름>.json`. 두 언어가 함께 읽는 자리라 `crates/` 나 `web/` 밖의 루트 폴더가 낫다). Rust 테스트는 기본으로 커밋된 파일과 방금 만든 본문이 같은지 비교만 하고(다르면 실패), 환경 변수(제안: `RBMS_UPDATE_CONTRACT=1`)를 줄 때만 파일을 다시 쓴다. 이렇게 하면 클라이언트가 본문의 모양이나 값을 바꾸면 Rust 테스트가 파일의 갱신을 요구하고, 그 갱신이 웹 테스트를 거치게 된다. 실행 시각, 난수, 경로처럼 매번 달라지는 값은 고정 시계와 고정 시드로 막는다(시드는 `fresh_layout_seed(고정한 큰 나노초 값)` 의 결과를 쓴다. 나노초 값 `1_791_970_074_354_123_456` 은 `app_play.rs` 의 기존 테스트가 쓰는 값이다).
3. 웹이 통과시킨다. `web/tests/dto/` 에 새 테스트를 두고 그 폴더의 모든 파일을 읽어 서버가 실제로 쓰는 스키마(`scoreSubmissionSchema`, `courseSubmissionSchema`, `replayUploadSchema`, `settingsBlobSchema`, 인증 본문 스키마)로 `parse` 한다. 파일 이름에 어느 스키마인지 드러낸다(제안: `score-*.json`, `course-*.json`, `replay-*.json`).
4. 더해서 서비스 계층까지 한 번 태운다: 같은 파일을 `web/tests/service/score-submit.test.ts` 의 방식(`ScoreServiceDb` 를 인라인 객체로 대체)으로 제출 서비스에 넣어 거절 없이 저장되는지 본다. 스키마를 통과해도 서비스의 두 번째 검사에서 걸릴 수 있다(예: `resolveReplayChartSha256` 의 차트 확인).

### 2.3 단언 규칙

- 모든 파일이 해당 스키마의 `safeParse` 를 통과한다. 실패하면 이슈 경로(`error.issues[].path`)를 메시지에 낸다.
- 파싱 결과가 입력과 같은 값을 갖는다. 변환이 값을 바꾸는 필드(`seed`: 안전하지 않으면 0, `title`/`artist`: 255자로 자름, `level`: 범위 밖이면 null)는 `parsed.seed === input.seed`, `parsed.chart.title === input.chart.title` 로 비교해, 서버가 조용히 값을 바꾸는 입력을 클라이언트가 만들고 있지 않은지 잡는다. 이 단언이 없으면 `seedSchema` 때문에 같은 종류의 회귀가 400 대신 시드 0 으로 숨는다.
- 숫자 필드 모두에 `Number.isSafeInteger`(정수 필드), `Number.isFinite`(실수 필드)를 파일 단계에서 단언한다. 파일의 `null` 은 Rust 의 `Option::None` 이거나 `NaN`/무한대가 `null` 로 직렬화된 것이라 구분이 안 되므로, 서버 스키마가 `null` 을 받는다고 명시한 필드(`nullish`)만 `null` 을 허용하는 목록을 테스트에 둔다.
- Rust 쪽은 JSON 에서 `null` 이 나오면 안 되는 필드 목록(실수 필드 전부)을 같은 방식으로 단언한다.

### 2.4 값 범위가 달라지는 필드의 목록

코드에서 뽑았다(`crates/rbms-ir/src/dto/{score,chart,replay}.rs` 의 Rust 타입, `web/src/server/dto/{common,score,course,replay}.ts` 의 Zod 규칙). "방어"는 지금 이미 있는 대책이다.

| 필드 | Rust 타입 → JSON | 서버 규칙 | 벗어나면 | 방어(현재) |
| --- | --- | --- | --- | --- |
| `seed` (점수, 리플레이) | `u64` → 정수 | `seedSchema`: 안전한 정수가 아니면 0 | 0 으로 저장(기록은 받음). 레이아웃이 RANDOM 인 리플레이는 다시 내려받으면 다른 배치가 될 수 있다(3.8절) | 클라이언트가 2^53 미만을 만듦(`7095ef7`). 리플레이가 넘겨받는 옛 시드는 그대로 |
| `gauge_value` (점수, 코스) | `f32` → 실수, 유한하지 않으면 `null` | `z.number()`(null·NaN·무한대 거부) | 400 | `clamp_to_server_bounds()` 가 비유한 값을 0.0 으로 고침(`worker.rs`, 코스는 `course_ir.rs`) |

| `options.lift`, `lane_cover` | `f32` → 실수 | `z.number()` | 400 | 막지 않음 |

| `chart.level` | `Option<u32>` | 0~1000 정수가 아니면 null | 400 아님 | — |
| `client_build_sha256` (리플레이) | `Option<String>` | 점수는 아무 문자열, 리플레이는 정확히 64자 | 리플레이만 400 | `compute_build_hash()` 가 SHA-256 16진수 64자 또는 `None` |

| 코스 `trophy` | `Option<String>` | 32자 이하 | 400 | — |
| 코스 `assist` | `Vec<String>` | 16개 이하, 각 32자 이하 | 400 | 태그는 `AUTO_SCRATCH`, `CUSTOM_JUDGE` 정도 |
| 리플레이 `events[].t_us` | `i64`(µs) → 정수 | `int()`, 음수 허용 | 400 | — |
| 리플레이 `events[].lane` | `u32` | `int().min(0)` | — | — |
| 리플레이 `duration_us` | `Option<i64>` | `int().min(0)` 또는 null | 음수면 400 | 플레이어는 `최대 - 최소` 를 보내 음수가 없다 |
| 리플레이 `size`, `event_count` | `Option<u64>`, `Option<u32>` | `int().min(0)` 또는 null | — | 플레이어는 `size` 를 보내지 않는다(null) |
| 리플레이 본문 크기 | 이벤트 수 × 약 40바이트 | `REPLAY_MAX_BYTES` 기본 4 MiB(`web/src/server/lib/env.ts`), Vercel Functions 요청 본문 한도 4.5 MB | 413 | 일반 곡은 한참 아래. 계약 파일 `replay-long`(이벤트 1,596개, 65,017바이트)으로 재면 이벤트 하나가 약 40.4바이트라 4 MiB 에 약 10.4만 개가 들어간다. 웹 테스트가 10만 개 이상 들어가는지 단언한다(2.7절). 곡이 길어 `t_us` 의 자릿수가 늘면 이벤트당 1바이트쯤 늘어난다 |

표에 없는 것: JSON 의 `-0`, 유니코드 이스케이프, 문자열 안의 널 문자. 이번 판단에서는 위험이 낮다고 보고 목록에 넣지 않았다.

### 2.5 반대 방향(서버 응답을 Rust 가 읽는 쪽)

같은 틈이 반대로도 있다. `crates/rbms-ir/src/contract_tests.rs` 는 서버 응답을 손으로 적은 JSON 문자열로 만든다(`ok(r#"{"api_version":1,"server":"rbms-web","commit":"c6f0885"}"#)` 식). 서버가 실제로 주는 본문(제출 응답, 순위 행, 리플레이 메타, 폴더 목록, 표 헤더)을 웹 테스트가 파일로 뽑고 Rust 테스트가 `serde` 로 읽는 대칭 테스트는 아직 없다. 위험은 앞쪽보다 낮다(Rust 쪽 필드 대부분이 `#[serde(default)]` 라 빠진 필드에 관대하다). 다만 정수 자리에 실수가 오면(예: `rank`) 디코딩이 실패한다. 우선순위는 2.1~2.4 다음이다.

### 2.6 갱신이 필요해지는 시점

- 두 테스트는 CI 에서 늘 돈다. Rust 쪽은 `ci.yml` 의 `cargo test`(세 OS), 웹 쪽은 `web.yml` 의 `bun run test`(`contract/**` 가 바뀐 푸시에서도 돈다).
- 클라이언트가 보내는 본문의 모양이나 값을 바꾸면 Rust 테스트가 실패하고 갱신 방법을 메시지로 낸다: `RBMS_UPDATE_CONTRACT=1 cargo test -p rbms-player --locked contract_requests` 로 파일을 다시 쓰고, `web/` 에서 `bun test tests/dto/client-requests.test.ts` 를 돌린 뒤 파일을 변경과 함께 커밋한다.
- `web/src/server/dto/*` 나 라우트 검사를 바꾸면 웹 테스트가 커밋된 파일로 새 규칙을 확인한다.
- 새 요청 종류(새 엔드포인트의 본문)를 클라이언트에 더할 때 `contract_requests.rs` 의 `CONTRACT_FILES` 와 테스트, 웹 테스트의 스키마 대응(`REQUEST_SCHEMA`)에 이름을 더한다.

### 2.7 구현(2026-10-14, S18-4)

파일: `contract/client-requests/*.json` 14개, Rust 테스트 `apps/rbms-player/src/app_result/record_tests/contract_requests.rs`(와 `contract_requests/wire.rs`), 웹 테스트 `web/tests/dto/client-requests.test.ts`.

설계(2.1)와 달라진 점:

- 본문을 받는 자리는 기록용 가짜 `ScoreServer` 가 아니라 테스트 안에서 루프백에 뜨는 작은 HTTP 서버다. 앱은 그 주소로 로그인한 상태(`rebuild_server`)이고, 파일은 `HttpScoreServer` 가 실제로 보낸 바이트에서 만든다. 가짜 서버는 구조체를 받으므로 JSON 으로 다시 써야 하는데 `rbms-player` 에는 `serde_json` 의존이 없고(새 의존성을 넣지 않음), 설정 업로드는 보내기 전에 `SettingsPutRequest` 로 바뀐다. 와이어를 받으면 둘 다 문제가 아니다.

- 설정 본문은 라우트가 실제로 쓰는 `settingPutSchema` 로 검사한다(`settingsBlobSchema` 는 라우트가 쓰지 않는다).

Rust 쪽 단언: 정수는 절댓값 2^53-1 이하, 실수는 유한, `null` 은 Rust 의 `Option` 칸에만 있다(실수 칸의 `null` 은 NaN·무한대가 직렬화된 것이라 실패). 이 검사가 나노초 시드와 `null` 게이지를 잡는지 두 테스트로 확인한다. 폴더에 목록 밖 파일이 있거나 목록의 파일이 빠지면 실패한다.

웹 쪽 단언(2.3절): 모든 파일이 스키마를 통과한다. 실수 칸 목록(`gauge_value`, `options` 의 `hispeed`·`lift`·`lane_cover`·`total_override`·`green_number`)은 `Number.isFinite`, 나머지 숫자는 `Number.isSafeInteger` 다. `null` 은 서버가 `nullish` 로 받는 칸과 서버가 읽지 않는 칸(리플레이 `id`)에만 있다. 파싱 결과의 모든 값이 입력과 같다(서버가 조용히 바꾸거나 버리는 값이 없다. 버려도 되는 칸은 리플레이 `id` 하나). 종류별로 더 본다.

- 점수: 라우트 검사(`api_version`, `guest` 가 아닌 player, `isPlayedAtPlausible`, `isSha256Hash`, md5 길이, `isJudgeCountConsistent`)를 모두 통과하고, `score-submit.test.ts` 방식의 `createScoreService` 가 거절 없이 저장하며 시드가 그대로다. 빌드 해시가 없는 본문은 `score-sync-resend` 하나다(`REQUIRE_BUILD_HASH` 가 켜진 서버는 이것만 거절한다).
- 코스: 라우트 검사, 코스 해시와 곡 해시가 온전한 SHA-256·MD5, 서비스가 받음.
- 리플레이: `score_id` 가 있고, 서버가 처음 보는 차트도 본문의 SHA-256 으로 찾을 수 있으며(`resolveReplayChartSha256` 의 대체 경로), `event_count`·`duration_us` 가 이벤트와 맞고, 본문이 `REPLAY_MAX_BYTES` 기본값 안이며 같은 모양이면 이벤트 10만 개가 들어가고, 서비스가 이벤트를 모두 저장한다.
- 설정: 본문과 내용이 `SETTING_MAX_BYTES` 안이고 서비스가 충돌 없이 저장한다.

웹 테스트가 실제로 잡는지는 파일 하나를 일부러 깨뜨려(시드를 나노초 값으로, `gauge_value` 를 `null` 로, 모르는 키 추가) 7개 테스트가 실패하는 것으로 확인했다.

발견:

- 서버 계약 위반: 없다. 14개 파일 모두 S18-1 의 서버 코드에서 통과한다.
- `score-empty-poor-exceeds-poor` 는 이번 사고를 재현한다. HEAD(`e2c5a38`)의 옛 식(`pgreat+great+good+bad+max(poor-empty_poor,0)+miss`)으로는 29+0+0+0+0+28 = 57 > 32 라 거절되고, 새 식으로는 29+3 = 32 라 통과한다.
- 클라이언트 쪽 값 차이(계약 위반은 아니다): 기록 DB 행에서 다시 만든 본문은 `judge.avgjudge` 의 부호를 잃는다. 기록 DB 가 `avgjudge` 를 절댓값으로 저장하고(`scoredb_store.rs` 의 `avg_judge_us.abs()`) `rebuilt_submission` 이 그 값을 보낸다. 같은 판이 결과 화면 본문에서는 `-14655`, 다시 만든 본문에서는 `14655` 다. 다시 만든 본문의 `fast`·`slow` 가 0 인 것은 설계대로다(`mark_reconstructed`).
