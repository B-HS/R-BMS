# Architecture

Last updated 2026-10-23 · matches 76e026a (2026-10-23: the song browser's folder stack and Stella and Satellite as default tables, charts the library does not hold and getting them, COURSE GAUGE with every gauge carried between stages, an Esc that ends on the result screen, and on the website the daily table copy, the course catalog and the dans; 2026-10-22: text rasterised on the target's own pixels, the assist grade of a light-assist lamp and the course stage's gauge, colour rows, the option panels' extension ids; 2026-10-20: the play trace, steps 2 and 4 below)

R-BMS is a BMS rhythm game made of two parts that meet at one wire contract. The **player** is a Rust port of the reference implementation's PLAY core: a Cargo workspace of 16 library crates and 2 apps (`rbms-player`, the desktop game, and `rbms-cli`, a headless inspector). The **score server and website** is `web/`, a Next.js app that answers the player's IR calls and serves the public site at `https://bms.hyuns.uk`. The single source of truth for *behaviour* is the code + its tests; this document is the map.

## End-to-end data flow (disk → pixels + audio)

1. `.bms` bytes → `rbms_parser::parse_with` → `BmsSource`.
2. `rbms_chart::detect_mode` + `to_model` → `Model` (raw objects become absolute `Micros` here).
3. `rbms_chart::shuffle::apply` (optional note option; the layout seed comes from `fresh_layout_seed`, below).
4. `rbms_play::PlaySession::new` → `Player` → `JudgeEngine::from_model`. With SCRATCH AUTO on, the turntable notes are taken off the chart the engine judges (`Player::with_auto_lanes`) and kept only to be drawn and heard.
5. `rbms_audio::decode_bytes` + `AudioEngine::load` (keysounds, decoded on background threads).
6. Per frame: `PlaySession` state + `rbms_chart::scroll` offsets → `rbms_render` playfield/HUD/skin objects → `Gpu` (wgpu).

Everything drawn lowers to the `Renderer` primitives: `fill_rect` for the built-in screens, and for a skin additionally registered textures (`register_texture`, `release_texture`), `draw_textured_quad` (rotation, blend, filter), `draw_distance_field_quad` (bitmap fonts of type 1 and 2) and `push_clip` / `pop_clip`. Text is shaped with cosmic-text once, in the renderer's own units, and each glyph is rasterised into a swept cache of run-length-merged pixels that goes out as `fill_rect` runs; the glyph atlas (`glyph_atlas.rs`, textured quads) exists but only tests call it. On a target larger than the 1280×720 the built-in screens are laid out in, the glyphs are rasterised at the target's own pixel size and placed with `fill_rect_device`, not drawn small and enlarged (`Renderer::device_scale`: `ScaledRenderer` and the player's `Canvas` report their factor; a stretched or letterbox-off target whose axes differ more than rounding explains keeps the old enlarged path). A skin's TTF text takes a path of its own (`font/block.rs`), which already rasterises for the skin's viewport and so did not change; its BMFont pages and movie frames arrive as textures.

### Screen flow and who draws it

| From | To | When |
|---|---|---|
| Select | Decide | a chart is picked and a decide skin is drawable (`has_decide_scene`) |
| Select | Loading | a chart is picked and there is no decide scene |
| Decide | Play | the scene ends and a skin draws the play screen (its own PRELOAD waits for the decodes), or everything is already in |
| Decide | Loading | the scene ends with files still decoding or the skin never drew |
| Decide | Select | cancelled (Esc, or START with SELECT) |
| Loading | Play | every keysound and image has decoded |
| Play | Result | the run ends: cleared, failed, or left with Esc after a note was judged (2026-10-23; a run that judged nothing, an autoplayed one and a replay go back to Select with nothing kept) |
| Play | Play | in a course, the next stage starts without a result screen (only the first stage has a decide scene) |
| Play | CourseResult | the last stage of a course ends, or the course fails (a stage left with Esc and notes still to come fails the course) |
| Result | Select, Play | the player leaves, or runs the same chart again (R), again on the same lane layout (a blue key held with START), or the next song (N) |
| CourseResult | Select | the player leaves |

- **Select → Decide → Play → Result.** Picking a chart in the browser opens `Decide` over it, but only when a decide skin is drawable; without one the chart goes straight to `Loading` as it always did. The chart parses when it is picked and its keysounds and images decode on the worker pool while the decide scene plays; a scene that ends early hands the outstanding decodes to `Loading` (or to the play skin's own loading state). Cancelling the decide scene (Esc, or START with SELECT) returns to the browser exactly as it was left. A chart named on the command line skips Select and Decide.
- **Play** runs PRELOAD → READY → PLAY → FAILED or FINISHED → fade, then `Result` (`CourseResult` after the last stage of a course). What happens to a finished run is the next section. A watched replay runs on the SCRATCH AUTO, gauge and arrangement it was recorded with; the player's own are what the settings file is written with meanwhile and are put back when it ends (`AppShared::end_replay`).
- **Result, again on the same layout.** START pressed while a blue key is held (`stage/result.rs` `blue_keys`: keys 2, 4, 6 of seven; 2, 4 of five; 4, 6 of nine; either side in doubles) leaves with `RunSameLayout`: the next load takes the finished run's seed (`retry_seed`) and the options as they stand. The blue key confirms when it is let go, so START can be pressed beside it. It works for any run the player played, assisted or not; autoplay, a watched replay and a chart outside the library offer no retry (`offers_retry`).
- **Who draws each screen.** For every screen type (`SkinType`) the app asks `SkinLibrary` for a document: the one the player chose by hand, else the one the effective skin pack declares for that type, else none. A drawable document draws the screen alone; with none, the built-in screen (`render_select`, `render_playfield_view` + `render_hud`, `render_result`, …) draws it. Key config, 24-key play and a skin that fails to load always end up on the built-in screens. The effective pack is `RBMS_SKIN_PACK`, else `skin.pack` from the settings, else the installed default pack (`<config dir>/skin/rbms-default/`, written on every start from the copy embedded in the binary). `skin.md` documents the selection rules, the failure messages and the default pack.
- **Scene clock.** Each skinned scene has a `SceneClock` (`scene_clock.rs`) that restarts at 0 when the scene starts, stops while a document is still being read, and is carried over `Transition::Open` / `Back`. Skin timers are microseconds against it; `input`, `scene` and `fadeout` from the document header drive `stage/scene_life.rs`.

## From a finished run to the website (play → record DB → score server → web)

One ended run takes one path, in `apps/rbms-player/src/app_result.rs` `enter_result` (the storing part is `record_run`; a run left with Esc after a note was judged goes through `enter_result_of_a_left_run`, the same `show_result` with the notes not reached let pass, and so to the result screen, whose submission is its one send (2026-10-23, before it Esc kept the run without a screen and a records sync sent it); a run the app was quit in through `keep_run_cut_short_by_quitting`, which sends nothing and leaves it to the next start's records sync, and a course left between two stages through `abandon_course`; a course stage left with Esc fails the course and ends on its result), and the rules for which run goes where are written once, in `docs/play-options.md` §10.

1. **The run is summarised.** `PlaySession::summary()` gives the counts, EX, combo, gauge, lamp, early/late split; `scratch_auto_played` says whether SCRATCH AUTO took any note off a lane (a chart with no turntable note, or the 9-key mode, is played wholly by hand whatever the switch says); `is_custom_judge` says whether a judge width or the LN margin was set above 100%. The assist level (`rbms_ir::mapping::assist_level`: 0 none, 1 SCRATCH AUTO, 2 widened judge) demotes the lamp (`assisted_lamp`: LIGHT ASSIST, id 3; ASSIST, id 2). A LIGHT ASSIST lamp is graded by the gauge the run finished on (`rbms_judge::assist_grade`: ASSIST EASY, ASSIST CLEAR, ASSIST HARD, ASSIST EXHARD, or none on the ASSIST EASY gauge); the finished gauge is `PlayRecord::finished_gauge`, so a course stage is stored and sent on the course gauge it ran on (`class`, `exclass`, `exhardclass`) and not on the gauge the settings name (`play-options.md` §10.13).
2. **The local record is written** (`scoredb_store::record_finished_play` into `scoredb.sqlite`: one `scorelog` row per run, the merged best `score` row, the day's `player_stat`; the in-memory `ScoreBook` the screens read gets the row too) for every run the player played by hand: not autoplay, not a watched replay, not a practice slice. The row and the submission body it is sent with are one transaction (`ScoreDb::record_play_kept`). A database that cannot be opened or written keeps the run on the side instead (`pending-runs/<ms>-<md5>.ron`, read in by `ScoreDb::import_pending_runs` the next time it opens; a play the history already holds is not read in twice, and one the database refuses is reported and left without holding back the files after it) and says so on screen. A failed run started again at once with START or SELECT is kept before the chart starts again (`record_retried_run`). A run left with Esc while notes remain is kept too, without a result screen, as a FAILED run whose notes not reached count as POORs let pass (`PlayState::leave_run` → `record_left_run`, `PlaySummary::left_unfinished`), however few notes it judged. A course left part-way with notes remaining keeps that stage the same way and is kept and sent as a FAILED course of the stages it played (`app_result::leave_course`); one left with nothing more to hit ends as a stage played to its end does. Signed in or not, server configured or not. The row carries the rule generation (`SCORE_RULE_VERSION` = 4), the reference's `avgjudge` (`PlayRecord::avg_duration_us`: every note's distance from its input, a note never hit counting a second) and `minbp` with the notes a run the gauge ended never reached (`PlaySummary::min_bp_with_unreached`), the assist level, the layout seed and whether it was handed over when it ended (`ir_submitted`, kept for reference only and never read as "the server has it"). The submission body the run is sent with goes beside it (`play_submission`, with the account it was played under), and so does its play trace (`play_trace`: every judged object of the chart as the run laid it out with its state and timing, the empty POORs, all nine gauges' histories, the scroll settings it started and ended on and each change between, the tempo; `play_trace.rs`; the frame thread copies out only what it is made of and the save thread lays it out, serialises it and writes it after the row, `SaveWorker::keep_trace` → `ScoreDb::keep_trace`, putting it on the side in the run's `pending-runs` file when the database does not take it; `play-options.md` §10.12; a run kept on the side carries it in its file; a run stored before traces were kept gets one after the next start when its replay, judged again on the EVENT clock, comes out exactly as its row and its kept submission: `trace_backfill.rs`, `play-options.md` §10.12). Whether the row may set a best is `rbms_store::sets_best`: assist 0 always, SCRATCH AUTO (1) from generation 3 on, a widened judge or a TOTAL of the player's own (2, `judged_wider`) never. A row of generation 2 with SCRATCH AUTO (the old rule, which counted the turntable as perfect greats) is history and a lamp; nothing is rewritten.
3. **The replay is saved** to `replays/<md5[:8]>-<ms>.ron` when AUTO REPLAY is on (the shipped default), for the same runs.
4. **The run is sent** (`ScoreSubmission` through `HttpScoreServer::submit_score`, `POST {server_url}/scores`, off the frame thread) for the same runs, when an account is signed in (`sends_to_primary_ir_server`; an extra IR profile carries its own token and is always sent to). Before sign-in nothing is sent at the time; every answer of the main server is written per run and server into `ir_sync` (accepted with its `score_id`, rejected with the error code, field and reason, retry, skipped). The records sync (`apps/rbms-player/src/record_sync.rs`, on sign-in, on a confirmed session at start, on `SYNC RECORDS NOW`, and for a run left with Esc or started again from its failure) sends every kept run that server does not hold, oldest first with the runs the server failed to answer behind the rest, paced under its rate limits on a worker thread, then the kept courses, then the play traces of the runs the server holds (`POST {server_url}/charts/{md5}/traces`, linked by `score_id`, only to a server whose `/health` lists `capabilities.traces` and while AUTO UPLOAD TRACE is on, `/health` being asked only when the sync has a trace to send; a run the result screen sent has its trace sent by a sync of that run once the score is taken), then the replays of the runs it took. The worker picks what to send through a read-only connection of its own (`ScoreDb::open_read_only`, WAL), so the frame thread only reads the newest ids; a refusal is written with the client and server builds it was given under, and a sync that starts on its own leaves a run refused under the same builds out (`SYNC RECORDS NOW` sends every refusal again; [`acknowledge/2026-10-15-adr-record-sync-refusal-resend.md`](acknowledge/2026-10-15-adr-record-sync-refusal-resend.md)); a run made before its body was kept is rebuilt from its row (`play-options.md` §10.9). The submission states `options.scratch_auto` and `options.assist` (`AUTO_SCRATCH`, `CUSTOM_JUDGE`), the layout `seed` and the chart's own title, artist and level (`SubmittedChart`), so the server can name a chart nobody has submitted before. AUTO UPLOAD REPLAY also uploads the replay, unless its judge widths cannot be stated on the wire (`ir_replay::wire_carries_judge`). A course is kept in the score database when it ends (`course_submission`, with its body), if every stage was a run that is sent, with the assist of its stages stated (`course_ir::CourseAssist`); it is sent at once when an account is signed in, the answer written to `course_sync`, and the records sync sends it again until the server holds it.
5. **The server decides what the run is** (`web/src/server/service/domain/score/ranked-policy.ts`). Flags: `AUTOPLAY`, `SCRATCH_AUTO`, `ASSIST`, `JUDGE_WIDTH`, `TOTAL_OVERRIDE`, `UNKNOWN_BUILD`, `GUEST`. `SCRATCH_AUTO` and `UNKNOWN_BUILD` do not stop a run from being ranked; a widened judge does (the row is kept, unranked). A ranked run updates `chart_best`, which is kept **per player, chart and `scratch_auto`** (migration `0002`), so a SCRATCH AUTO best and a hand-played best sit side by side. Runs are ranked by `(clear, assist_grade, EX, BP)`: `chart_best.assist_grade` (migration `0011`) derives from the run's `gauge` with the same table as the client (`web/src/server/service/domain/score/assist-grade.ts`), and the grade sits inside lamp 3, so it never lifts a run above EASY. A repeated `played_at` of the same player and chart is answered as a duplicate (`message: "duplicate submission ignored"` with the stored `score_id`), which is what lets the records sync send everything again safely. The reply (`SubmitResponse`: `rank`, `previous_best`, `flags`, `is_new_best`, `score_id`) comes back to the result screen (`ir_outcome.rs`: `IR: RANK #n`, `IR: RANK #n (SCRATCH AUTO)`, `UNRANKED: …`, `NEW BEST`; a refusal names the error code and, when the server gives them, the field and the reason: `IR ERROR: server error 400: VALIDATION_ERROR: judge (…`; [`acknowledge/2026-10-14-adr-ir-error-field-display.md`](acknowledge/2026-10-14-adr-ir-error-field-display.md)).
6. **The site shows it.** The server's rankings and leaderboard list ordinary runs unless the query asks for `include_scratch_auto` (the player never sends it, so its own rank panels stay as they were); the site's pages ask for SCRATCH AUTO runs by default (since 2026-10-19), and the "include SCRATCH AUTO" switch, kept in the page address as `include_scratch_auto=false` when it is off, leaves them out. They are marked A-SCR. A clear is every lamp but NO PLAY and FAILED (`MIN_CLEAR_LAMP_ID`), and a player's page lists every run of theirs by page (`GET /api/fe/players/{id}/recent?page&limit`). Charts, players, replays, courses, tables and the player's folders read the same database.

A seed travels as a JSON number, so a new layout seed is kept under 2^53 (`fresh_layout_seed`, `LAYOUT_SEED_MASK`, never zero; a seed carried from a replay or a retry is used as recorded), and the server reads one outside the safe-integer range as 0 instead of refusing the run (`web/src/server/dto/common.ts` `seedSchema`). Clients up to v0.1.2 sent the clock's nanoseconds and had their runs refused with HTTP 400 by the server's check, which is why both sides were changed ([`bug/2026-10-14-score-submit-400-large-seed.md`](bug/2026-10-14-score-submit-400-large-seed.md)).

### Difficulty tables, the default table and MY FOLDERS

- **Tables** are fetched once and read from a copy afterwards (`tablesrc.rs`, `TableStore`, `<config dir>/tables/<hash of the address>.json`). Nothing waits for a table's server; fetches run on a worker beside the frame loop, and the song list is rebuilt where it stood when one lands. A copy that is a day old, or that the binary planted and so has no date, is fetched again once per run in the background and replaces the copy only if it arrives; a failed refetch says nothing in the song list (the table manager shows why beside the source).
- **The default tables.** `rbms_config::DEFAULT_TABLES` names three tables: the 発狂BMS難易度表 (id `insane1`) at `https://bms.hyuns.uk/tables/insane1` (the original `darksabun.club` address counts as the same table), and since 2026-10-23 Stella (`stella-st`) and Satellite (`stella-sl`) at `https://stellabms.xyz/st/table.html` and `.../sl/table.html`, both of the root row `STELLA`. A build that ships a table puts it into a player's list once, right after the nearest earlier default table the list holds (in front when it holds none), so a new player's order is 発狂, Stella, Satellite and an older player's own tables follow them. `apps/rbms-player/src/tablesrc/seed.rs` plants the copy the binary carries of the insane table (`include_bytes!` of `web/data/tables/insane1/{header,data}.json`, 1,034 charts, 26 levels), so its folders exist at the first frame, offline too; the two Stella tables change every couple of weeks and are always fetched from the original site, so they carry none and their folders appear when the first fetch lands. The id is then written to `library.seeded_default_tables`, which is what lets a player remove the table for good. A player who has it at another address is not given a second one. The snapshot is refreshed by `web/scripts/snapshot-table.ts` (`--check` compares); the Rust CI also runs when it changes.
- **MY FOLDERS.** Folders of charts a player makes on the site (several per player, edited on the web only) are read by the game from the signed-in server (`ScoreServer::user_folders` / `user_folder`, `/players/{id}/folders`) and shown as one row at the top of the song list (`user_folders.rs`, `MY FOLDERS`). The folders are on show from the first frame from the copy kept in `<config dir>/user-folders/<hash of server and login>.ron`; a fetch on a worker refreshes them at the first frame of a signed-in run, at sign-in, on `F6` on the song select and on `R`/`A` in the table manager, asking only for folders whose stamp moved. A chart is matched by md5; one the library lacks is not a row. Signing out deletes the copy; another account sees nothing of them; a session the server no longer accepts hides them.
- **The folder stack.** The song browser keeps the folders it has opened as a path (`AppShared.select_path`), each with the bar the cursor was on when it was opened, as the reference's `BarManager` does (`dir`, `sourcebars`); leaving a folder by any route puts the cursor back on that bar, and the path survives a table landing, a scan, a cancelled load, the table manager and a search (`select_tree::ListPlace`). A folder and a bar are named by what they are -- a table by its address, a level by its name, a chart by its md5, a course by its id -- not by their place in a list. The top of the library is ALL SONGS, the tables (the tables of one `group` under a single row, `STELLA`) and MY FOLDERS; a table is its levels, titled by the symbol its header names (`st3`, `★12`), and a `COURSE` folder when it lists courses (the insane table's also holds the 44 GENOSIDE 2018 courses the build carries).
- **Charts the library does not hold, and getting them.** A level also lists the charts its table names that the library lacks, dimmed (`showNoSongExistingBar`; the setting is MISSING CHARTS). Choosing one opens a modal that says what the table's link is: a direct zip link (`rbms_download::classify_link`) can be fetched by the player, everything else (a page, a cloud folder, a rar or 7z, a lone chart file) is handed to the system browser (`open_url.rs`), and the modal says that a table's DL is the difference chart only, so the song's sounds and pictures still have to come from the song URL. A fetch (`download.rs`) is one job at a time on a worker: the zip goes to `.rbms-partial/` in the download folder, is unpacked under size, count and path limits, and is moved into a folder of its own; then only that folder is scanned (`ScanRequest::partial`, which does not record the parser version, under `LIBRARY_WRITE` so two scans never write the song database together) and the tables are matched again. Only the song list takes the result in, keeping its path and its cursor, which is on that chart from then on; a library under a chart being played is never replaced. A scan that began under another library generation, other table sources or another table generation (a counter `AppShared.table_generation` raises each time a table's slot is set, removed or replaced, so a scan cannot put an older matched copy over the one the song list holds) is not taken in and runs again, the chart waiting for its folder with it. `rbms_library::scan::DOWNLOAD_WORK_FOLDER` (`.rbms-partial`) is the one folder name a scan never walks into, so a full scan during an unpack cannot put a half-unpacked chart into the song database.
- **The server address.** `network.server_url` is `https://bms.hyuns.uk/api` for a new install (`Config::first_run`) and for a settings file of schema 5 or earlier that named none (`Config::adopt_default_server`, once); from schema 6 an empty row is the player's own choice to play offline. `Config::default()` keeps no server so no test reaches a network.

## The realtime play loop

- **Master clock is audio frames, not vsync.** `Mixer` increments an `AtomicU64` of mixed frames each callback; `AudioEngine::clock_us() = frames·1e6/rate`. `App::frame` computes `song_us = audio.clock_us() - anchor_us` (anchor captured at *play start*, after keysounds finish loading, so load time doesn't count against position).
- **Per frame** `PlaySession::tick(clock, sink)`: feed any due replay input, book keysounds ahead on the scheduling axis (`Player::update_schedule`), then judge on the audible axis (`Player::update_judge`) — flush BGM, autoplay/auto-lane actions, expire tap beams, and let `JudgeEngine::update` sweep unhittable notes to MISS and finalise over-held LNs.
- **The judgement does not depend on the frames.** `JudgeEngine::update(t)` does not settle everything at `t` in one step: it walks from one instant something falls due to the next (a mine, a hell-charge note's head or end, a hell-charge tick, a deferred release outlasting its margin, a plain long note held past its end, a note past its last chance) and settles each there, with the keys as they stood then. Every input first settles the engine up to its own instant, and the gauge auto-shift is taken after every instant that changed a gauge, ending the run at the instant the gauge emptied under NONE (`JudgeEngine::failed_at_us`; the engine takes nothing after that). A practice slice locks its gauge instead: NONE plays as CONTINUE there, so the slice is judged to its end (`PracticeSession::gauge_shift`), and a slice at another FREQUENCY is judged in the player's own time (`JudgeEngine::set_playback_rate`). The session samples the gauge history at its own half-second instants (`PlaySession::settle_until`) and records an input that arrived before what was already settled at the settled instant, so a replay reproduces the run at any frame rate (`crates/rbms-play/tests/replay_reproduction.rs`). The reference advances all of this once per frame; see `acknowledge/2026-10-15-adr-event-time-judging.md`.
- **Autoplay is not a hand on the keys.** `Player::update_judge` takes each autoplay note through `JudgeEngine::auto_press` / `auto_release` at the action's own time. They judge the note PGREAT and never raise the lane's key state, as the reference only sets `auto_presstime` (`JudgeManager.java:251-283`); a mine therefore costs an autoplayed lane nothing, and a scratch-lane charge note ends like any other (the back-spin rule is for a key that is pressed). A hell-charge note still pays out gauge because the engine is told the run plays itself (`JudgeEngine::set_autoplay`, `:289-293`).
- **Sound leaves through a trait.** `PlaySession` emits `SoundRequest`s into a `SoundSink`; the app's `PlayAudioSink` is the only code that maps them onto `AudioEngine` (source → bus, `#WAVxx` → play id namespace). With `NullSink` a whole run — including a replay — reproduces headlessly, which is how play is tested without a device.
- **Input** is judged at the instant the input carries (`FrameCtx::now`): a key at the instant `window_event` received it, and a key is received as it comes in: the wait for the display is on a thread of its own (`gpu/present.rs`, below), so between frames the event loop waits on nothing but the window, and only a frame the loop is busy updating and drawing holds a key back (`docs/acknowledge/2026-10-15-adr-keyboard-input-timing.md`; audit PERF-2). A lane key of the keyboard goes through KEY DEBOUNCE first (`stage/play/key_gate.rs`, `play.key_debounce_ms`, 16 ms), LR2's `inputinterval`: a press is played the instant it comes, never later; a release inside the window after the press is kept out and played at the instant the window ends, if the key still reads up then, by the next key, controller event or frame (`PlayState::take_opened_keys`); a press within LR2's poll gap (2 ms) of a release played is the switch bouncing and is not played. A controller button or two-key axis direction goes through the same state machine (`input_debounce.rs`, shared) under PAD DEBOUNCE (the key config's `pad.debounce_ms`, 16 ms, set on the settings screen's INPUT tab); a turntable direction keeps the reference's two-way lock. A controller change at the instant gilrs stamped it (`PadState::poll_now` resolves change by change, `PadMapper::resolve_changes`, so a tap inside one frame is a press and a release; the frame loop hands each event over with `FrameCtx::now` set to that instant). `AppShared::song_us_at` reads the audio clock at that instant (the audible position is a line through the last callback, so it reads back to an instant gone by). `PlaySession::press(lane, raw_us, sink)` records that time for the replay and judges there; the judge offset only moves where notes are drawn. Underneath, `Player::press(lane, now_us)`: lights beam, plays nearest keysound, `JudgeEngine::press` gates candidates by the active scaled windows, classifies by `dmtime = note_time - press_time`. 空POOR (far-early) does not consume the note or break combo. Input on a lane SCRATCH AUTO plays is ignored (no judgement, beam or keysound).
- **A frame costs what changed, not what the chart holds.** The play screen's copy of every note's state (`stage/play/trace.rs`, `RunTrace`) walks the chart once and then takes in only the notes the engine names as touched (`JudgeEngine::touched`). The judgement graph (`graphs/notes_dist.rs`) keeps its pixmaps in upload order (`Pixmap::upside_down`), writes only the columns of the seconds whose judgements changed (`Renderer::update_texture`), and keeps its cursor as one row stretched to the graph's height, since every row of the reference's cursor pixmap is the same. A background picture change paints into the canvas its role already has (`bga/pictures.rs`), and a large picture drawn as it is goes to the renderer from its own pixels, as does one exactly 256 x 256, which is its canvas already. Before the chart plays every look it shows is uploaded as a texture of its own until `RESIDENT_BYTES` (256 MiB, kept at that for the play frame's sake over memory: [`acknowledge/2026-10-15-adr-bga-resident-texture-cap.md`](acknowledge/2026-10-15-adr-bga-resident-texture-cap.md)) are held (`BgaTextures::preload`), and the looks past that have their pixels painted on the decode worker within `PREPARED_BGA_BYTES` (256 MiB, `assets.rs`); a picture past both is painted and uploaded the frame it is first shown, into its role's canvas and texture. Which looks are uploaded ahead of play is planned before any picture is decoded, from the sizes the files' headers give, in the order the chart first shows them and by the upload's own rule (`assets::plan_uploads_ahead`, `uploaded_ahead`): a look that will be a texture is not painted on the decode worker, the painting allowance goes to the looks that are not, and the plan travels with each picture (`BgaPrepared::ahead`) so the upload ahead holds those looks and no others whatever order the decodes finish in. The plan is the whole chart's, so a practice slice uploads in its own order instead (`BgaPreloadOrder::Part`, set by `PlayState::set_practice`): the planned looks it shows first, since nothing painted them, then its other looks while the allowance has room. Memory does not hold a picture twice. The GPU backend's texture registry (`gpu/registry.rs`) gives the slot of a texture let go of to the next one registered, under a handle of its own: a chart's pictures take the same slots from one play to the next, and a handle kept past its release names nothing. Keysounds are moved into the mixer's bank as the decoder made them (`DecodedAudio.samples: Arc<[f32]>`). The headless measurement that keeps this honest is described in `development.md`.
- **Invariants**: single `Micros = i64` everywhere (`measure_us(bpm) = 240_000_000/bpm`); `dmtime` sign convention (`>0` early/FAST); `early[i] + late[i] == counts[i]`; monotonic cursors (rewind only via replay re-simulation); `BPM <= 0` guards prevent NaN.

## Determinism & correctness

- **Chart identity** = MD5 + SHA-256 of **raw bytes** → flows to `Model.md5/sha256`, `ChartId`, score records, replays, table md5-joins.
- **`#RANDOM`** resolved by an LCG seeded from `random_seed`; same seed → byte-identical `BmsSource`.
- **Shuffle** uses a hand-rolled xorshift64 (no `rand` dep) → replay-reproducible. DP uses per-side seeds.
- **Replay** stores `seed + random + offset_ms + gauge` (and `scratch_auto`, the judge settings) to reconstruct the exact lane layout and re-judge. A replay of a SCRATCH AUTO run takes the same notes off the chart, so it reproduces the same figures.
- **Judge windows** are mode-aware (`JudgeWindows::note_for_mode` / `ln_end_for_mode`); LN-release windows scale with `#RANK` and JUDGE WIDTH just like note heads.
- **Judging-rule generations** (`SCORE_RULE_VERSION`, stamped on every record): 2 is the judge-parity pass; 3 changes SCRATCH AUTO alone (the turntable leaves the judged chart, such a run sets bests); 4 records a run as the reference does (`avgjudge` as the mean note distance, `minbp` with the notes never reached, a course stage's own combo, the full combo read off the combo standing at the end, a TOTAL override as an assist). A record is read by its generation, never rewritten: an older `avgjudge` never competes for a best and is sent again as 0, an older `minbp` is charged the notes it never reached when compared (`charged_minbp`). Submissions state the generation in `extra.rule_version`.

## Data-driven surfaces

- **Modes** are data (`Mode` + an `[i8;18]` channel map) — a new key mode is a constant, never an engine branch.
- **Built-in note-field layouts** (`SkinConfig`, RON, `assets/skins/{normal,wide}.ron`, or any file given to `--skin`): note-field geometry, palettes, gauge thresholds, key-bomb, DP layout. They draw the built-in play screen only (the fallback for 24-key play, for a play document that is missing or fails, and for a run started with `--skin file.ron`). A play skin document carries its own geometry in its `note` object.
- **UI theme** (`ThemeConfig`, RON): menu/chrome colours — see `docs/theme.md`.
- **Judge windows and gauges** are data: `rbms-judge/data/judge.ron` (six modes) and `data/gauge.ron` (`BEAT_7K`) are embedded with `include_str!` and can be overridden from disk. The in-code const tables stay for one release as the fallback *and* as the reference of a **parity guard test** that asserts the parsed data equals them field by field — the values Phase A matched to the reference cannot drift as the data path takes over.
- **Candidate selection** is a policy value (`JudgeAlgorithm`: Combo / Duration / Lowest / Score) rather than a hard-coded loop; the default stays `Duration`, which is what this engine has always done (see `acknowledge/reference-divergences.md` C-D1).
- **The score a run is paced against** is a value too: `ScoreTarget` (16 targets). A target that names a score (LOCAL BEST, IR BEST, RIVAL) answers only once that score exists; until then the run is paced against the player's TARGET FALLBACK (default RATE AAA), and IR BEST tries the local best first (`apps/rbms-player/src/target.rs` `settle`). RATE CUSTOM is a share of the chart's ceiling set by TARGET RATE (1–100%, default 85). The play HUD, the select list and the result screen all settle it the same way (`app_result::run_target`), and the skin names what it fell back to (`RATE AAA (NO RECORD)`). While a run goes on, a LOCAL BEST target, an IR BEST target whose run was played on this machine and the skin's BEST figures stand where that record run stood after as many notes as this run has judged, as the reference reads the `ghost` column of its score database (`ScoreDataProperty.java:114-118`); every other target, and a record run that cannot be judged again, is earned evenly over the notes (`pace_ex_at`). The score database keeps no such list, so the record run is judged again from its replay on a thread of its own while the chart loads (`apps/rbms-player/src/ghost.rs`: `ghost_sources`, `GhostJob`, `rejudge` over `PlaySession::play_out` and `JudgeEngine::vanished`; the LOADING screen waits for it, so nothing changes mid-run). A replay of another chart, one that comes out at another note, PGREAT or GREAT count than its record says, and one recorded on the old frame clock are no ghost. The result screen's figures are the final ones either way. See [`reference/record-target-pace.md`](reference/record-target-pace.md).
- **The settings screen is a table**: `rbms_config::SETTINGS` describes every row (tab, label, kind, range, help, visibility predicate) and the screen renders `tab_rows` → `display_value`, feeding keys back through `adjust`. Adding an option is one row, not nine edits across a runtime struct, a persisted struct, two converters, two matches and a tab array.
- **Configuration is one versioned document** (`settings.ron`, `schema_version` 6): play/judge/display/audio/network/library options in one `Config`. A pre-version file migrates on load and absorbs `folders.ron`/`tables.ron` **without deleting them**; a file from a newer schema is left untouched and the app starts on defaults, so a downgrade cannot destroy settings. Schema history: 1 one judge width, 2 the bundled-skin era, 3 letterbox never chosen, 4 judge offset added to the judged instant, 5 no default server, 6 the default server and the default-table record.
- **Keymaps** (`KeyConfig`, RON), **skins**, **themes**, **difficulty tables** and **replays** stay their own files under the config dir (every file `#[serde(default)]`, parse-fail → `.ron.bak` + defaults). The config dir resolves `HOME` → `USERPROFILE` → `.` for cross-platform parity (Windows lands in `%USERPROFILE%\.config\rbms`); `config_dir_from` is unit-tested. Every write goes through `rbms_store::write_atomic` (temp + rename; the temp name carries the process id and a per-process number, so two threads never share one); the settings file and its copies, which hold the bearer token, go through `write_atomic_private` (`0600` on Unix), and loading the settings closes a file and the copies an older build left readable by everyone (`rbms_config::io` `close_to_other_users` → `rbms_store::restrict_to_owner`, regular files only). The settings saves of a running app, its replays, a run kept on the side, the play trace of a stored run and the traces the backfill made for earlier runs are handed to one save thread (`apps/rbms-player/src/save_worker.rs`) so no frame waits on a disk flush; it writes in order, skips a settings save a later one replaces, reports a failure back to the frame thread, and is drained when the event loop ends (`ApplicationHandler::exiting` → `AppShared::finish_saves`; macOS Quit exits the process from inside the loop, so neither `run` nor a `Drop` gets another chance). A flush is a boundary: a settings save handed over after it does not replace one handed over before it, so what was handed over before a flush is on disk when it returns. The replay retention at start keeps a replay still to go up to the signed-in account's server (`UploadHold`), within the byte ceiling.
- **Launch arguments.** The first positional argument is a song folder or one chart. An argument the system added is not one the player typed: macOS can add `-psn_0_<serial>` when Finder opens the app bundle, and the launch reads it as nothing (`is_system_launch_arg`), so it is not mistaken for a chart path. The command line is read before anything else (`command_line::read`): `--help`/`-h` and `--version` print the usage or the version and end the process with success, and an option this build does not know, or one given without its value (or with another option in its place), prints the reason and the usage and ends it with exit code 2. Any other argument that starts with `-` (`-v`, `-version`, `-`) is such an option, never a chart: a chart or folder whose name starts with a dash is named with its folder in front (`./-name.bms`). None of these reads or writes the settings, installs the default skin, opens a database or a window, or asks a server anything (`main_tests.rs`, `asking_for_the_usage_or_the_version_answers_without_starting_the_app`; S19, after a `--help` run started the app on the real settings).

### Skins (`rbms-skin`, `rbms-render::skin_render`, `apps/rbms-player`)

A screen that has a skin is drawn by that skin alone; there is no mixing with the built-in layout. The system is specified in `docs/plan/2026-10-09-lua-skin-compat.md`. User-facing behaviour is in `skin.md`; this is where the pieces live.

| Layer | Holds |
|---|---|
| `rbms-skin` | `SkinDef` model; the loader (`loader.rs`, `loader/lua_skin.rs` two-pass `.luaskin` load, `loader/from_lua.rs` Lua table → model, JSON/json5 path, wildcard and random file selection, customisation merge); the Lua runtime (`lua/`); `property/host.rs` (`SkinHost`, `MapHost`); `dst.rs` interpolation; `timer.rs` (µs, OFF = `i64::MIN`); `resolve.rs` (skin-root-only paths) |
| `rbms-render::skin_render` | `SkinScreen::prepare` then `draw`; `FrameData` (notes, gauge, bars, series, images, bga) supplied by the app; objects (`notes`, `gauge`, `judge`, `songlist/`, `covers`, `graphs/`, `text/`, `bga/`, `text_input`, `input/` for clicks and drags); `textures/` (a pool that decodes only the sources a placed destination references, per-screen budget `SKIN_TEXTURE_BUDGET_BYTES` = 1 GiB) |
| `apps/rbms-player` | `skin_select.rs` (`SkinLibrary`: the effective pack, header scans with an mtime cache, per-screen document choice, loads and their failures, the skin menu's rows including the colour rows and their channels (`SkinRow::Color`, `ColorChannel`), what a document is drawn with -- the player's choices over the adjustments its pack came with -- and a row's value put onto the other screens that declare it; `skin_select/adjustments.rs` reads and writes a pack's `rbms-adjustments.ron` by name, `skin_select/export.rs` copies a pack with its adjustments into a new folder off the frame loop), `skin_screen.rs` (compiled screens, texture decode, the scene hold while a document is read), `skin_screen/movies.rs`, `skin_screen/preview.rs` and `skin_preview.rs` (one screen's document drawn with sample state inside a rectangle of the skin menu or the play menu, through `rbms_render::RegionRenderer`; silent, and blind to the player's library and scores. `skin_preview/target.rs` says what a preview shows -- the screen the skin menu configures, or the play screen and tempo the play menu names -- and works out what the scroll of that target comes to), `skin_host/` (`ScreenHost`, the `SkinHost` implementation, split into clusters by where a value comes from and routed by `ROUTES`; `skin_host/extension.rs` lists every event and option id this player answers beyond the reference's, events 21000 to 21099 and options 21100 to 21199: SCRATCH AUTO and KEEP GREEN NUMBER switches, the assist grade of a best or a result, the keys of an option panel a mode cannot reach), `scene_clock.rs`, `stage/scene_life.rs`, and `assets/default_pack.rs` with `build.rs` |
| `rbms-video` | movie frames for a skin's video sources, one thread per open movie |

Colour rows (2026-10-22) are the offsets' sibling: a document lists them in its header (`color`), a destination or a note lane names one with `tint`, and the value the player set lives in `SkinCustomisation.colors`. `ScreenHost` forwards `OffsetSource::color` to `DocumentOffsets` (the stored value as it is), so a changed colour reaches the next frame without the document being read again; only a colour coming to be set or ceasing to be set has the document read once more, because a Lua skin chooses at load whether a part is tinted (`skin.md` §1.4, §3.4.4; [ADR](acknowledge/2026-10-22-adr-skin-colour-rows.md)). The ids beyond the reference's are an R-BMS band of their own ([ADR](acknowledge/2026-10-22-adr-rbms-extension-ids.md)): a skin reads them with `main_state.option` inside a function field and the loader drops them from an `op` list, so the reference's own id tables and their checksum test are untouched.

Frame order for a skinned scene: the stage settles the scene time, builds the screen's state, `ScreenHost` answers property ids from it, every object is prepared (conditions, then timer, then value functions, in declaration order), drawn, and finally clicks from the previous frame run. `skin_host` collects effects (events, audio, writes) in interior-mutable queues because `SkinHost` methods take `&self`; the stage takes them after the frame (`skin_requests`).

The default pack is built into the binary: `build.rs` walks `assets/skins/rbms-default` into a sorted table with per-file SHA-256, and `install_default_pack` settles the installed folder against it on every start, keeping files the player changed (details in `skin.md` §3). Its images and sounds are generated by the pack's own `assets/skins/rbms-default/tools/*.py` (`uv run`; `build.rs` leaves that folder out of the binary) and committed.

## App UI state machine (`Stage`)

The thirteen screens: `Select` (song list: search `/`, sort `F3`, IR ranking panel and course tab, the `MY FOLDERS` row; with a skin, the skin's own bars, panels 1 to 3 on START / SELECT and buttons) · `Decide` (the scene between picking a chart and its run; exists only when a decide skin is drawable) · `Settings` (`Tab`: three columns over the descriptor table -- a rail of six groups with their row counts and changed-row marks, the rows of the open group under subheadings drawn by kind (switch, side-by-side choices, `< value >`, slider, text field, shortened path, `>` action), and a panel that says what the row under the cursor is for, holds, ships as and hears, following a number or text being typed, a list or the reset question while one has the keys; `Enter` turns a switch or takes a choice to its next value and never closes the screen (`Esc` does); incl. a **NETWORK** group that signs in and edits SERVER URL / PLAYER ID in place. The skin settings and the play options, TARGET and TARGET FALLBACK among them, are not here: three buttons at the foot of the rail open the play menu, the skin menu and the key config. Design: `docs/plan/2026-10-14-settings-screen.md`) · `SkinMenu` (`F12`: the pack folder, the per-screen document and the options, files and offsets it declares on the left, and on the right a live preview of that screen's skin drawn with invented sample data; a row that holds a number has a slider and can be typed into, as on every built-in screen: `number_row.rs`) · `PlayMenu` (`F8`: the play options in groups on the left -- speed, lane, judge offset, chart, and the options the play skin of the previewed mode declares -- and on the right a play screen of that mode drawn by its skin on a sample chart that never ends, at a tempo the menu chooses; the figures under it come from `rbms_config::held_speed` and the functions beside it, as the play screen's do. It is made of the same parts as the skin menu, `stage/preview_menu.rs`) · `KeyConfig` · `Tables` (difficulty-table manager, which also lists `MY FOLDERS` and its status: a table at an address is fetched once and read from the copy kept in `tables/` beside the settings file after that. No screen waits for a table's server: a table being registered is a row at once and is fetched on a worker beside the frame loop, a table that has no copy yet is fetched the same way once the song select is up, and `R` fetches the table under the cursor again and `A` every table. What lands is taken a frame at a time by whichever of the two screens is up, and its folder appears in the song list where it stands. Each row says what became of its table -- not fetched yet, being fetched, failed and why, or how long ago its copy was fetched; `F6` on the song select reloads every table the same way) · `Folders` (multi-folder library manager) · `Loading` (the folder scan, whose table step reads only the saved copies and the table files on disk, and the determinate keysound-decode progress bar) · `Play` · `Result` (a skin's result scene or the built-in one; the score server's answer, the replay slot, and the blue-key + START retry) · `CourseResult` · `Practice` (the slice of a chart to repeat and the terms it is repeated under: a START row and nine rows of the property, six of which hold a number and are set as on the three menus -- slider, typed figure, the finest step per arrow; a slice is a play screen opened over the panel that comes back to it).

How they are wired:

- **`App = { shared: AppShared, stage: Stage, suspended: Vec<Suspended>, launch_chart, startup_error, window }`.** A `Suspended` is a parked `Stage` with the skin scene (timers and clock) it was in. `AppShared` holds what outlives a screen change (config, library, scores, audio engine, GPU, skin, IR session, clocks, frame stats); each `Stage` variant holds only its own screen's state. That split is what lets `self.stage.update(&mut FrameCtx { shared: &mut self.shared, .. })` borrow-check — one struct holding both would not.
- **Each screen implements `StageHandler`** (`update` / `draw` / `handle_key` / `handle_mouse` / `handle_mouse_drag` / `handle_scroll` / `handle_ime` / `handle_pad` / `on_enter` / `on_exit` / `debug_lines` / `holds_keys`; `update`, `draw` and `handle_key` are required; the rest default to doing nothing). `Stage::handler()` / `Stage::view()` are the only two places that match on the variants — they hand back a `&mut dyn StageHandler`, and every dispatch method is a one-line call through it. The match is still exhaustive, so the compiler still catches a screen missing from any path; what it avoids is repeating a thirteen-arm match once per method. The large screens (`Select`, `SkinMenu`, `PlayMenu`, `Decide`, `Play`, `CourseResult`, `Practice`) are boxed so their size does not set every variant's; a test pins the size of `Stage`. Only the result screen implements `handle_pad`, so a controller does not drive the settings screen (a known gap).
  (The Phase C spec §2.3 called for a per-method match and no trait object; the single-match-plus-`dyn` form keeps that spec's stated guarantee — the compiler catches a missing variant — with one match instead of seven.)
- **One transition rule, in one place.** A screen returns `Transition::{Stay, Open, To, Back, Quit}` and `App::apply` runs `on_exit` → swap → `on_enter`. `Open` suspends the current screen and `Back` resumes it exactly as it was, which is how the settings screens return to the browser. The scattered `self.stage = Stage::X` assignments are gone.
- **`on_exit`/`on_enter` carry the ordering contracts** a screen change has to honour — the select preview is torn down on the way out of the browser before anything else touches the audio engine.
- **The browser's *list* state stays in `AppShared`**, not in `SelectState`: which folder is open, the filtered rows, the search text, the sort and the cursor. Every other screen returns to the browser and several act on the focused row while it is not the live screen (`Tables` and `Folders` rebuild the list, `Loading` resets it to the root, the debug overlay reports the cursor from anywhere), so the list is shared state that outlives the screen. `kc_edit_mode` is in `AppShared` for the same reason: the key-config screen is rebuilt on every visit and the mode it was editing has to survive that. The Phase C spec §2.2 assigned both to their screens; this is a deliberate departure, and it is the reason `AppShared` has over 100 fields (113 at ea698a9) rather than the ~40 the spec estimated.
- **`App` and `AppShared` live in the crate root** (`lib.rs`) rather than a module of their own. Every screen and `app_*` module is a *descendant* of the crate root, which is what lets them touch `AppShared`'s private fields; moving the two structs into a sibling module would force every one of those fields to `pub(crate)` and buy nothing but a shorter file. What did move out are the parts with no such coupling: `assets.rs` (bundled skins, theme template, file resolution, keysound/BGA decode, library scan) and `stage/select/{preview,scene}.rs`.
- **Frames are paced by the display, waited for off the event loop.** The event loop runs with `ControlFlow::Wait`. `Gpu` asks the presenter thread (`gpu/present.rs`, `Presenter`, thread `rbms-present`) for the image the next frame is drawn into; that thread blocks in `Surface::get_current_texture` (the vsync wait) and wakes the loop with a `FrameReady` user event once the image has come. The loop then runs `frame()` (`App::frame_if_ready`, `Gpu::frame_ready`), encodes and submits into that image, and hands it back to the presenter thread to present (on DX12 under Fifo the present is where the wait is), which then asks for the next. The presenter thread never calls a `Window` method (on macOS those are dispatched to the main thread synchronously); wgpu's own Metal acquire still reads two AppKit properties (`NSView.window`, `NSWindow.occlusionState`) off the main thread, a known risk kept on purpose and waiting on gfx-rs/wgpu#10627 ([`acknowledge/2026-10-15-adr-wgpu-metal-main-thread.md`](acknowledge/2026-10-15-adr-wgpu-metal-main-thread.md); why the thread exists at all: [`acknowledge/2026-10-15-adr-keyboard-input-timing.md`](acknowledge/2026-10-15-adr-keyboard-input-timing.md)); `pre_present_notify` and every surface reconfiguration stay on the loop, and the loop never waits for the presenter thread: a surface may not have an image out while it is configured, so a resize lets go of the image it holds and reconfigures at once if none is being asked for, and otherwise marks the surface to be reconfigured, which `Gpu::frame_ready` does as soon as the image asked for has come (letting it go, then asking for the next). While an image is being asked for the loop does not submit, poll the device or configure the surface: wgpu holds the device fence for reading for the whole acquire and a submit takes it for writing, so any of them would put the vsync wait back on the loop. A presenter thread that panics wakes the loop on its way out and the loop's next `take`/`request` panics. At exit `run` stops the thread and waits for it a bounded while (`Gpu::stop_presenting`, at most wgpu's 1 s acquire timeout), so the surface and window are released last on the main thread. An image that cannot be had still runs the frame. What happens next follows wgpu's own advice per answer (`Swapchain::image`, `Presenter::settle`): a surface that is `Outdated`, `Lost` or failed `Validation` is reconfigured and the next image asked for at once; a window that is `Occluded` (hidden, minimised, on another space, under another window) or a display that answered `Timeout` leaves the surface alone and holds the next ask back for `HIDDEN_FRAME_INTERVAL` (one 60 Hz frame). The loop sets `ControlFlow::WaitUntil` to that instant in `about_to_wait` (`Gpu::held_until`, `Gpu::resume_if_due`), and `WindowEvent::Occluded(false)` asks at once (`Gpu::resume`). Metal refuses an image for a hidden window immediately, so asking again at once, which the loop once did after a reconfigure, ran frames as fast as the processor allowed (about 100% CPU on a hidden window); held back, a hidden window runs one frame an interval (1-3% CPU), so a run that is not seen is still judged, its sounds still booked and its chart still ends. A frame that is held back or reconfigures still submits the texture and buffer writes it made (an empty `queue.submit`, `gpu::submit_pending_writes`, before the next image is asked for and never while one is), so a hidden window does not pile up the staging copy of every movie frame and picture it uploads (wgpu frees a write's staging memory only after a submission carries it). This is what keeps keys from waiting for the display.
- **The frame loop and the event handler are dispatches**: `frame()` is fps/RAM, the polls, `stage.update`, `stage.draw` and two app-wide overlays; `window_event` translates the winit keyboard, mouse-button (press and release), cursor-move (drag), wheel, focus and redraw events into `handle_key`/`handle_mouse`/`handle_mouse_drag`/`handle_scroll`/`frame` (a redraw the system asks for runs a frame only if its image has come). A window that loses focus is not told about the keys let go while it is away, and on macOS winit does not make the key-ups up as it does on X11 and Windows, so `Focused(false)` hands the screen that is up a key-up of every key still counted as down (`Stage::release_keys_lost_with_focus`, through the same `handle_key` a real key-up takes) before it clears the held-key set: a long note held when the focus left is released, recorded for the replay and judged as let go, instead of being held to its end by a key nobody is pressing.

## Testing and the lint gate

The last count is the CI run of ea698a9 (run 38698550145): `cargo test --workspace --no-fail-fast` passed 6,024 tests with 0 failures and 6 ignored on Ubuntu (`ci-release.md` §1); the S19 closing gate (51f3a1e) passed 653 web tests besides the database integration tests (`PROCESS.md`). At wave 20 (2026-10-14) the counts were 5,671 and 415. A few Rust tests are ignored (they need an audio or graphics device, wait five seconds, or read a copy of a player's own database). The counts are not a contract; CI is the judge. The tests cover boundaries, malformed input, invariants, round-trips, and determinism. The deterministic render backend `CpuCanvas` makes pixel-level rendering testable without a GPU — the player's screens are rendered onto a headless canvas in tests, and a whole run (replay included) reproduces through `NullSink` with no audio device.

A test does not lean on how long the machine takes. Without a sound device the song clock is the wall clock since `start_play`, and the skin's scene clock is a wall clock too; both read the machine's now through one function each (`AppShared::song_instant`, `AppShared::scene_instant`), which a test can stop. The capture harness (`stage/capture.rs`, `PlayClocks::frame_after`) stops both at the instant it hands each frame (`AppShared::stop_clocks_at`) and then puts them where its own count says, so every read inside that frame's update and draw sees that instant; before this, a runner that held the process up between a frame reading the time and drawing (or for longer than a key's light, a bomb's sprite or a judgement's last frame) drew the frame at another moment, and pixel comparisons failed now and then on loaded CI runners. `PlayClocks::machine_stall` holds a drawn frame up on purpose for the tests that pin this. A skin's Lua is a third clock: the calls of one frame share a wall-clock allowance (`FrameBudget::max_micros`), and a call past it answers the value of an earlier frame, so a runner held up inside one call drew the rest of the frame stale. A test build holds that clock (`SkinLua::hold_frame_clock`) for exactly as long as the scene clock is stopped (`AppShared::skin_runtime`), which leaves a frame held to its call count and its instructions alone; the shipped player keeps the wall-clock allowance. The other test frame helpers (`scene_frame_at`, `draw_on`, `draw_until_settled` in `stage/capture.rs`, and `frame` and `key` of the play screen tests) run each frame through `at_a_stopped_instant`, which stops the clocks that were running at the frame's instant and lets them run again once the frame is over, so a test that counts on its clock running between frames is unchanged; the operating time a document shows (`uptime_ms`) is read at the scene clock's instant too. A screen test that judges something shown for a while (the 1.5 s "NOT A NUMBER" of a number row) hands the key and the frame one instant (`Menu::key_at`, `Menu::frame_at`) and asserts against it. A client of the fake score server in `rbms-ir` waits `REPLY_WAIT` (10 s); only the tests of a timeout use `GIVE_UP_AFTER` (300 ms). A file a test writes into the shared temporary folder is named with the process id and a counter and is removed by a drop guard, so two runs of the tests side by side do not share it.

Skins are tested at three levels. `rbms-skin` and `rbms-render` test the loader, the Lua sandbox and every object against fixtures written for the tests. The default pack in the repository is held to a gate that needs no environment variable: a strict `skin-dump` of its nine documents, a draw of every screen it ships through the capture harness (`stage/capture/gate.rs`), a scan of its Lua for forbidden APIs and a check of each sprite sheet against its atlas (`crates/rbms-skin/tests/default_pack.rs`), and the install rules (`assets/default_pack/tests.rs`). A pack from outside the repository (ModernChic) is exercised only by opt-in tests that run when `RBMS_SKIN_PACK` names it; they pass on the default pack too, skipping what a pack does not carry. Built-in screens keep their golden signatures, so a change to a skin never moves them. `skin.md` §5 lists the harness environment variables.

The wire contract is tested across the two sides in one direction (S18, `e9aebae`): the player's tests take the request bodies it really sends off the wire of a loopback server (a plain run, SCRATCH AUTO, a widened judge, autoplay, a failed and an abandoned run, 空POOR past the POOR count, 14 keys on the second side, the records sync's resend, a normal and a SCRATCH AUTO course, two replays, a settings blob) and compare them with `contract/client-requests/*.json` (`app_result/record_tests/contract_requests.rs`; `RBMS_UPDATE_CONTRACT=1` rewrites them), and `web/tests/dto/client-requests.test.ts` passes every one of those files through the server's own Zod schemas, so a body the server would refuse fails a gate on one side or the other. That is the gap the 400 refusals of v0.1.2 (a seed above 2^53) got through. Each side also keeps its own tests (`rbms-ir` fixtures and a local HTTP mock, `web/tests/dto/ir-contract.test.ts`); the reverse direction, the server's answers checked against the client's parser, is still open (`quality-assurance/2026-10-14-test-debt.md` 3.12).

Lints are a gate, not a suggestion:

- The workspace defines the lint set once (`[workspace.lints]`: `unsafe_code = "deny"`, clippy `all` at warn) and **every crate opts in** with `[lints] workspace = true`.
- **Every crate root carries `#![forbid(unsafe_code)]`** — including the player, whose `bytemuck` derives turned out not to trip it. The single exception is `rbms-audio`'s `tests/rt_safety.rs`, which installs a counting global allocator to prove the mixer callback never allocates; that test crate root opts out with `#![allow(unsafe_code)]`.
- CI runs `cargo fmt --all --check` and `cargo clippy --workspace --all-targets --all-features -- -D warnings` as **failing** steps, so a new warning cannot land. Its test job is `cargo test --workspace --no-fail-fast` on Ubuntu, macOS and Windows, so one run shows every failure on a platform; after a push, `gh run list --branch dev` and `gh run view <id>` show the three results (details in `ci-release.md`).
- `rust-toolchain.toml` pins an exact toolchain version (1.95.0) rather than tracking `stable`, so a new release cannot break the gate with a new lint until the pin is moved deliberately. The CI and release workflows install the same version.

## Releases

A client release is cut by hand: `gh workflow run release.yml --ref dev -f bump=patch` (or the Actions form). The workflow raises the workspace version, commits `release: vX.Y.Z`, tags it, builds macOS (universal `R-BMS.app` in `R-BMS-macos-universal.dmg`, Developer ID signed and notarised, the ticket stapled to the app and to the dmg) and Windows (`rbms-windows-x64.zip`, not code-signed), and attaches both with their SHA-256 to a **draft** GitHub release. Publishing is the maintainer's. The macOS signing and notary credentials are checked before the build starts. The workspace version in `Cargo.toml` (0.1.4 at this commit) is the last release; v0.1.2 is the first that ships the app bundle and the dmg, and v0.1.4 the first with the app icon. The maintainer published v0.1.4 on 2026-10-15 (07:27 UTC); the v0.1.0 and v0.1.3 drafts are kept unpublished (`ci-release.md` §2.3).

### App icon

One picture, drawn by `assets/icon/tools/generate-icon.py` (`uv run`; `--check` compares the committed files with the script's output), reaches three places. The macOS bundle carries `R-BMS.icns` in `Contents/Resources` and names it in `Info.plist` (`CFBundleIconFile`, `scripts/macos-app.sh`, which stops if the file is missing). The Windows executable links the resource the release and the Windows CI job compile from `assets/icon/rbms.rc` with the SDK's `rc.exe` (`scripts/windows-icon-resource.ps1`, which names the `.res` in `RBMS_WINDOWS_RESOURCE`); `apps/rbms-player/build.rs` links it when that variable is set and links nothing otherwise, so no other build needs the SDK, and a name that leads to no file stops the build. The window itself takes the embedded 256 px PNG as its icon (`window_mode.rs` `window_icon`, used on Windows and Linux; macOS takes the bundle's), and a picture that cannot be decoded leaves the platform's default rather than keeping the window from opening. The site's favicon is drawn by the same script (`assets/icon/README.md`). Windows has no third-party resource crate for this on purpose (no new dependency): [`acknowledge/2026-10-15-adr-app-icon.md`](acknowledge/2026-10-15-adr-app-icon.md). A web change deploys by itself on a push to `dev` (Vercel), independent of this.
