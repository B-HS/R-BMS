# 플레이 화면의 프레임 비용 계측 (S19, 2026-10-15)

기준(사용자 결정): 헤드리스 계측에서 플레이 단계의 갱신과 그리기 합의 p99 가 1ms 미만이고, 플레이 단계 프레임 안에서 256KB 이상의 할당이 없다. 계측 방법은 `development.md` 의 "Frame cost", 남은 확인은 `quality-assurance/2026-10-14-test-debt.md` 3.38~3.40 에 있다.

## 1. 조건

- 릴리스 빌드(thin LTO, codegen-units 1), 이 Mac(18코어), 기본 스킨 1920x1080, 오토플레이, BGA 켬, 오디오 엔진 없음. 16ms 씩 장면과 곡 시계를 옮긴다.
- 그리기는 오프스크린 `Gpu` 에 큐를 쌓는 데까지다(스킨 평가, 쿼드, 텍스처 업로드). 래스터화와 화면 표시는 빠진다.
- 차트: 감사의 세 곡이 있는 `/Volumes/SSD/bms` 가 마운트되어 있지 않아 같은 길이·노트 수·BGA 수의 합성 차트를 썼다.
  - A: 110초, 2,011노트(감사의 `[A] MILK RAY` 자리)
  - B: 677초, 17,107노트, 256x256 그림 32장을 0.25초마다 교체(`[B] aciLbt3goddamn` 자리)
  - C: 248초, 51,379노트(`[C] sasoribi` 자리)
- 두 방식으로 쟀다.
  - 감사 방식: 감사의 계측 모듈 그대로. 오프스크린 대상은 제출을 하지 않아 GPU 쓰기가 큐에 쌓인다.
  - 실제 앱 방식: 매 프레임 그린 뒤 빈 제출과 `device.poll` 을 한다. 창이 있는 앱은 매 프레임 `render` 가 제출하므로 이쪽이 실제에 가깝다. 감사 방식의 수정 전 수치(p99 1.4ms)는 쌓인 쓰기 때문에 부풀어 있었다.

## 3. 무엇이 줄였나

- 판정 그래프(PERF-3): 픽스맵을 올리는 순서로 칠해 두고(`Pixmap::upside_down`) 뒤집는 복사를 없앴다. 판정이 바뀐 초의 열만 다시 쓰고(`Renderer::update_texture`), 커서는 모든 행이 같으므로 한 행 텍스처를 늘려 그린다. GPU 업로드는 행 패딩 복사 없이 `write_texture` 에 바로 넘긴다.
- 판정 추적(PERF-7): `RunTrace` 가 첫 번에만 모든 노트를 보고, 그 뒤로는 엔진이 건드렸다고 알려 준 노트(`JudgeEngine::touched`)만 읽는다. C 의 갱신 p50 이 161us 에서 1.3us 가 됐다.
- BGA(PERF-9): 그림이 바뀌어도 역할마다 둔 캔버스에 다시 칠하고, 그대로 그리는 큰 그림은 복사하지 않는다.
- 키음(PERF-8 일부): 디코드 작업자가 `Arc<[f32]>` 로 만들어 보내고 삽입은 옮기기만 한다. 오디오 엔진을 내린 이 계측에는 나타나지 않는다(단위 테스트로 확인).
- 판정 목록: 엔진이 판정 목록과 건드린 노트 목록을 노트 객체 수만큼 미리 잡아, 긴 곡의 플레이 중에 목록이 커지며 수백 KB~MB 를 옮기던 일(감사 방식 수정 후 B 의 갱신 max 186us)이 없어졌다.
