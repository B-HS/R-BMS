# 플레이 화면의 프레임 비용 계측 (S19, 2026-10-15)

> 최종 갱신 2026-10-15 · 대응 커밋 ea698a9. 아래 수치는 측정 당시의 기록이다. 2절의 "수정 후"(판정 그래프, 판정 추적, BGA 캔버스)는 커밋 `f81d499` 로, 판정 목록·리플레이 기록을 미리 잡는 것과 BGA 큰 그림 교체("수리한 작업 트리")는 `4cc72d0` 으로, "리뷰 수정"(계획 뒤 칠하기)·텍스처 슬롯은 `1676c57` 로 들어갔다. 상한 값은 코드가 정본이다: `RESIDENT_BYTES`·`PREPARED_BGA_BYTES` 256MiB, preload 프레임당 `BGA_PRELOAD_BYTES_PER_FRAME` 8MiB(`apps/rbms-player/src/stage/canvas.rs`). 이 설계가 어디에 놓이는지는 [architecture.md](../architecture.md) 의 "A frame costs what changed" 를 본다.

기준(사용자 결정, [ADR](../acknowledge/2026-10-14-adr-play-hitch-criteria.md)): 헤드리스 계측에서 플레이 단계의 갱신과 그리기 합의 p99 가 1ms 미만이고, 플레이 단계 프레임 안에서 256KB 이상의 할당이 없다. 계측 방법은 `development.md` 의 "Frame cost", 남은 확인은 `quality-assurance/2026-10-14-test-debt.md` 3.38~3.40 에 있다.

## 1. 조건

- 릴리스 빌드(thin LTO, codegen-units 1), 이 Mac(18코어), 기본 스킨 1920x1080, 오토플레이, BGA 켬, 오디오 엔진 없음. 16ms 씩 장면과 곡 시계를 옮긴다.
- 그리기는 오프스크린 `Gpu` 에 큐를 쌓는 데까지다(스킨 평가, 쿼드, 텍스처 업로드). 래스터화와 화면 표시는 빠진다.
- 차트: 감사의 세 곡이 있는 `/Volumes/SSD/bms` 가 마운트되어 있지 않아 같은 길이·노트 수·BGA 수의 합성 차트를 썼다.
  - A: 110초, 2,011노트(감사의 `[A] MILK RAY` 자리)
  - B: 677초, 17,107노트, 256x256 그림 32장을 0.25초마다 교체(`[B] aciLbt3goddamn` 자리)
  - C: 248초, 51,379노트(`[C] sasoribi` 자리)
- 두 방식으로 쟀다.
  - 감사 방식: 감사의 계측 모듈 그대로. 오프스크린 대상은 제출을 하지 않아 GPU 쓰기가 큐에 쌓인다.
  - 실제 앱 방식: 매 프레임 그린 뒤 빈 제출과 `device.poll` 을 한다. 창이 있는 앱은 매 프레임 `render` 가 제출하므로 이쪽이 실제에 가깝다. 감사 방식의 수정 전 수치(p99 1.4ms)는 쌓인 쓰기 때문에 부풀어 있었다.

- 감사 방식 수정 후의 바이트 max(4.6MB 등)는 제출하지 않은 큐가 커지며 wgpu 안에서 생긴 할당과, 이 실행에서는 아직 고치지 않았던 판정 목록의 증가(아래 3절 마지막 항목)다.
- 실제 앱 방식 수정 후에는 플레이 단계의 어느 프레임도 256KB 이상을 할당하지 않았다(프레임당 합계 max 176KB). 결과 화면으로 넘어가는 프레임(`enter_result` 의 `PlaySession::record`)과 준비 단계의 글꼴 측정(3.40)은 플레이 단계 밖이다.
- 이 표와 문장은 1절의 조건대로 **오토플레이**만 잰 것이다. 오토플레이는 입력을 기록하지 않고 空POOR 도 없어서, 손으로 친 판에만 생기는 두 증가를 밟지 않는다(2차 감사 R2-PERF-1). 수정 전 손으로 친 판에서는 리플레이 기록 목록(`PlaySession` 의 기록, 입력 하나에 24B)이 빈 채 시작해 8,193·16,385·32,769·65,537번째 입력에서 384KB~3MB 로 다시 잡혔고(C 의 1.57MB 복사가 최대 약 0.1~0.17ms), 空POOR 가 한 번이라도 난 판은 곡 끝 무렵 판정 목록(1.23MB → 2.47MB)을 다시 잡았다. 키 입력은 프레임과 같은 메인 스레드에서 들어온 순간의 시각으로 판정되므로, 그동안 들어온 다른 키의 처리만 그만큼 늦는다.
- 지금은 두 목록을 판이 시작할 때 미리 잡는다(3절 마지막 항목). 손으로 친 판을 헤드리스 계측으로 다시 재지는 않았다. 대신 "노트마다 空POOR 하나씩 낀 판에서도 기록·판정 목록이 옮겨지지 않는다"를 단위 테스트로 고정했다(`a_run_played_by_hand_never_grows_its_recording`, `a_run_with_an_empty_poor_beside_every_note_never_grows_the_engines_lists`). 그보다 空POOR 가 많은 판(노트 수보다 많은 헛누름)은 목록이 한 번 커질 수 있다.

## 3. 무엇이 줄였나

- 판정 그래프(PERF-3): 픽스맵을 올리는 순서로 칠해 두고(`Pixmap::upside_down`) 뒤집는 복사를 없앴다. 판정이 바뀐 초의 열만 다시 쓰고(`Renderer::update_texture`), 커서는 모든 행이 같으므로 한 행 텍스처를 늘려 그린다. GPU 업로드는 행 패딩 복사 없이 `write_texture` 에 바로 넘긴다.
- 판정 추적(PERF-7): `RunTrace` 가 첫 번에만 모든 노트를 보고, 그 뒤로는 엔진이 건드렸다고 알려 준 노트(`JudgeEngine::touched`)만 읽는다. C 의 갱신 p50 이 161us 에서 1.3us 가 됐다.
- BGA(PERF-9): 그림이 바뀌어도 역할마다 둔 캔버스에 다시 칠하고, 그대로 그리는 큰 그림은 복사하지 않는다.
- BGA(R2-PERF-2, 2차 감사 뒤): 그림 교체 때 남아 있던 복사·검정 키아웃·전체 업로드를 플레이 프레임에서 뺐다. 디코드 작업자가 차트가 그 그림을 보여 주는 모양(그대로, 레이어로 키아웃)대로 미리 칠해 두고(`BgaPrepared`, 차트당 `PREPARED_BGA_BYTES` 256MiB 까지), 곡이 시작되기 전 프레임들이 그 그림들을 프레임당 8MiB 씩 각자의 텍스처로 올린다(`BgaTextures::preload`, 합계 `RESIDENT_BYTES` 256MiB 까지). 플레이 중 교체는 이미 올라간 텍스처를 고를 뿐이다. 상한을 넘는 그림만 예전처럼 보일 때 올리고, 그때도 미리 칠한 픽셀이 있으면 칠하지 않는다. 그림 결과는 같다(같은 칠하기 함수, 단위 테스트로 픽셀 비교).
- 키음(PERF-8 일부): 디코드 작업자가 `Arc<[f32]>` 로 만들어 보내고 삽입은 옮기기만 한다. 오디오 엔진을 내린 이 계측에는 나타나지 않는다(단위 테스트로 확인).
- 판정 목록: 엔진이 판정 목록과 건드린 노트 목록을 노트 객체 수의 두 배(객체마다 그것을 끝내는 판정 하나와 空POOR 하나, `JUDGMENT_ROOM_PER_OBJECT`)만큼 미리 잡아, 긴 곡의 플레이 중에 목록이 커지며 수백 KB~MB 를 옮기던 일(감사 방식 수정 후 B 의 갱신 max 186us)이 없어졌다. 처음에는 객체 수만큼만 잡아 空POOR 가 하나라도 나면 곡 끝 무렵 커졌다(2차 감사 R2-PERF-1).
- 리플레이 기록(R2-PERF-1): 손으로 치는 판은 판정 노트 하나에 입력 네 개(누름·뗌, 그리고 같은 수의 헛누름·뗌, `RECORDED_INPUTS_PER_NOTE`)만큼 기록 목록을 미리 잡는다. 오토플레이와 리플레이 보기는 기록하지 않으므로 잡지 않는다. 51,379노트 차트에서 약 4.9MB 다.

## BGA 큰 그림 교체 (R2-PERF-2, 2026-10-15)

같은 하네스(`perf_audit_play_frames`, 실제 저장 스레드, 1920x1080, 오토플레이), 그림 48장을 베이스 30fps·레이어 15fps 로 바꾸는 합성 차트(`mkbga.py`, 하네스와 함께 세션 scratch 에만 있었고 저장소에는 없다). 전은 a13f6ce, 후는 수리한 작업 트리(뒤에 `4cc72d0` 로 커밋). 같은 기기에서 번갈아 쟀다. 갱신+그리기+렌더(인코드·제출), 플레이 단계.

## BGA 사본과 텍스처 슬롯 (R3-SCR-1·2, 2026-10-15)

3차 감사에서 미리 칠한 BGA 사본이 원본·상주 텍스처와 겹쳐 메모리가 늘었다는 지적(R3-SCR-1)과, 상주 텍스처를 판마다 새 슬롯에 올려 텍스처 레지스트리가 판마다 자란다는 지적(R3-SCR-2)을 고쳤다.

- 정확히 256x256 인 그림은 그대로 보일 때 칠하지 않는다. 캔버스와 바이트까지 같으므로 원본 픽셀을 그대로 넘기고, 칠하기 예산도 쓰지 않는다(`BgaPicture::needs_canvas`). 레이어(키아웃)는 픽셀이 바뀌므로 여전히 칠한다.
- 어느 모양을 상주로 올리고 어느 모양에 사본을 칠할지를 디코드 전에 한 번 정한다(리뷰 수정, `assets::plan_uploads_ahead`). 디코드 스레드가 먼저 그림 파일의 헤더에서 크기만 읽어(`image::ImageReader::into_dimensions`, 디코드와 같은 내용 기반 형식 판별) 차트가 처음 보이는 순서(`BgaPlayhead::first_looks`)로 preload 와 같은 규칙(`uploaded_ahead`: 남은 `RESIDENT_BYTES` 에 맞는 것, 맞지 않는 것은 건너뜀)을 적용한다. 상주할 모양은 칠하지 않고 칠하기 예산(`PREPARED_BGA_BYTES`)도 쓰지 않는다. 예산은 상주 밖 모양, 곧 플레이 중에 처음 보이는 그림에만 쓰인다. 계획은 그림마다 `BgaPrepared::ahead` 로 실려 가고, preload 는 계획이 있는 그림이면 계획이 고른 모양만 올린다. 그래서 디코드가 끝나는 순서가 달라도(작업자는 연속된 묶음을 나눠 맡는다) 두 쪽이 같은 집합을 본다. 상주할 모양은 preload 가 곡 시작 전에 칠해 올린다(프레임당 8MiB). 계획은 전체 차트의 순서로 세운 것이라 연습 구간에는 맞지 않는다. 연습의 `PlayState::set_practice` 는 preload 를 구간 자신의 순서로 돌린다(`BgaTextures::set_order(BgaPreloadOrder::Part)`, S19 4차 마감 R4-CLI-1). 계획이 고른 모양(사본 없음)을 먼저, 나머지를 남은 `RESIDENT_BYTES` 만큼 올린다. 고치기 전에는 256MiB 를 넘는 차트의 후반 구간에서 계획 밖 그림을 하나도 올리지 않아, 그 그림은 플레이 프레임이 올렸다.
- 그 전의 수정(상주로 올린 뒤 사본을 버림, `BgaPrepared::discard`)은 없앴다. 사본을 디코드 완료 순서로 칠하고 상주는 처음 보이는 순서로 채워, 사본이 곧 상주할 그림에 먼저 생겼다가 버려졌고(단편화 82MB), 버린 몫의 예산은 돌아오지 않아 정작 상주 밖 그림에는 사본이 없었다.
- GPU 텍스처 레지스트리(`gpu/registry.rs`)가 해제된 슬롯을 다음 등록에 다시 준다. 핸들은 슬롯 번호(20비트)와 그 슬롯을 받은 횟수(12비트)를 함께 담아, 해제된 핸들은 슬롯이 다른 텍스처로 다시 쓰여도 아무것도 가리키지 않는다(`TextureId` 는 여전히 두 번 주지 않는다). 횟수가 다 찬 슬롯은 다시 주지 않는다.

- 리뷰 전 수정: 실제로 쥔 malloc 은 167MB 줄었지만(Plain 256x256 사본 약 151MiB 없음, 상주한 Keyed 사본 297개 약 74MiB 버림) 버린 사본 자리가 단편화(82MB)로 남아 footprint 는 102MB 만 줄었다.
- 리뷰 수정: 상주할 모양에는 처음부터 사본을 만들지 않아 버릴 것도 단편화도 없다. a13f6ce 대비 MALLOC_SMALL +92MB 는 상주 밖 Keyed 모양(약 344개 x 256KiB)의 사본으로, 플레이 중 처음 보이는 레이어를 칠하지 않게 하려고 쥔 것이다. 측정 바이너리는 `CARGO_TARGET_DIR` 을 scratch 로 둔 release 빌드, HOME 은 scratch, `--server http://127.0.0.1:9`.
- graphics +271MB 는 상주 텍스처(`RESIDENT_BYTES` 256MiB)다. 상주는 플레이 프레임 p99 를 지키는 설계 비용이라 이번 수정은 건드리지 않았다. a13f6ce 수준(1142MB)으로 되돌리려면 상주 한도를 줄이거나, 상주한 그림의 CPU 원본을 버리고 연습 재진입·BGA 다시 켬 때 다시 디코드하는 경로가 필요하다.

같은 하네스(`perf_audit_play_frames`), HEAD(afa1e2f)와 이번 수정을 번갈아 쟀다. 갱신+그리기+렌더, 플레이 단계 p50 / p99 / max, 1ms 초과:

| 차트 | afa1e2f | 이번 수정 |
| --- | --- | --- |
| E1024 | 75.5 / 138.8 / 226us, 0 | 75.9 / 140.3 / 246us, 0 |
| E512 | 75.5 / 137.9 / 256us, 0 | 76.1 / 143.4 / 222us, 0 |
| YATA (2회) | 79.2·78.6 / 207.4·207.4 / 360·352us, 0 | 82.7·78.7 / 158.4·163.1 / 297·276us, 0 |

플레이 프레임은 3차 수정 수준(p99 약 0.14ms)을 유지한다. YATA 의 preload 단계 길이는 디코드 속도에 따라 94~608 프레임으로 흔들려 비교하지 않았다. 리뷰 수정(계획 뒤 칠하기) 뒤에는 이 하네스를 다시 돌리지 않았다: 상주 집합과 상주 텍스처의 크기는 같고, 바뀐 것은 상주 밖 모양에 사본이 생기는 쪽(플레이 프레임이 칠하지 않고 올리기만 함)이다.
