## 0. 먼저 읽을 결론

1. **[확인] 허용 범위 자체가 한계 아래에 있다.** 강도별 NPS 범위는 `build = [0.6c, 1.0c]`, `push = [0.8c, 1.0L]`, `over = [1.0c, 1.15L]`(c = 편한 밀도, L = 한계, `web/src/server/service/domain/training/training-constants.ts:50-54`). 기본 강도는 `push`(`web/src/entities/ai.type.ts:546`)라서 **LLM 이 상한을 골라도 집중 구간이 한계의 100% 를 넘을 수 없고, 하한은 편한 밀도의 80%(= 한계의 48~60%)까지 열려 있다.** 사용자 결정(기본 100~110%, 최고 115~130%)과 겹치는 곳은 `over` 의 꼭대기(100~115%)뿐이다.
2. **[확인·측정] 같은 범위에서도 실제로 나오는 밀도는 더 낮다.** 대표 프로필 3개 × 강도 3 × 종류 12 = 108 경우를 5시드씩 합성해 잰 결과, 집중 구간 실제 NPS 의 한계 대비 비율은 LLM 이 상한을 고르는 최선의 경우에도 `push` 0.85~0.96, `build` 0.66~0.78, `over` 0.88~1.09 이고, LLM 이 범위 가운데를 고르면 `push` 0.70~0.79 다(3.2절). 곡 전체 평균 NPS 는 한계의 0.53~0.94 다.
3. **[확인·측정] 밀도가 평평하다.** 한 구간 안의 행은 오차 확산으로 고르게 퍼지고(`web/src/server/service/domain/training/synthesize.ts:103-111`), 집중 구간은 모두 같은 목표 하나로 채워진다. 분석 엔진의 2초 창 국소 밀도(nps2)로 재면 곡 전체 `max / p50` 이 1.03~1.33 이고, 집중 구간 안에서는 p50·p90·max 가 같은 값(예: 16.5 / 16.5 / 16.5)으로 나온다. `burst` 종류도 1박(BPM 160 에서 0.375초)마다 1.6배·0.4배를 번갈아 놓아 1초·2초 창에서는 평균으로 뭉개진다. 분석 엔진은 `burst` 구간 노트의 90% 를 `sustained` 맥락으로 분류했다(3.5절).
4. **[확인] 한계 추정값은 아래로 치우친다.** `limit_nps_ex` 는 EX 가 기준보다 10%p 떨어진 첫 2-NPS 구간의 **아래 끝**이다(`web/src/server/service/domain/analysis/weakness-profile.ts:609,620`). 실제 한계가 [10, 12) 안 어디든 10 으로 적힌다(평균 −1 NPS 정도, 한계 11 인 사람에게는 −9%). 곡선이 10%p 까지 떨어지지 않으면 `null` 이 되어 "본 적 있는 가장 높은 구간의 아래 끝"(`max_seen_nps`)으로, 그것도 없으면 12 로 대신한다(`web/src/server/service/domain/training/spec.ts:148`).
5. **[확인·측정] 고정 비중과 상한이 더 깎는다.** 카운트인 1마디(BPM 160 에서 1.5초)와 꼬리 1초, 편한 밀도 이하로 묶인 워밍업(`spec.ts:169`)과 2 NPS 이하의 쿨다운(`rest`, `training-constants.ts:57-58`)이 60초 중 약 27%(16초)를 차지한다(LLM 가중치 2·3·3·3·1 가정). 격자 상한 `trainingMaxNpsOf`(`spec.ts:207-210`)는 BPM 160 에서 단타 종류를 21.33 NPS, `burst` 를 13.33 NPS 로 묶는다(한계 16 이상인 사람에게 `burst` 는 늘 한계 미만).
6. **[확인·측정] 종류별 배치 알고리즘이 목표를 못 채운다.** `stair` 0.71~0.79, `scratch_solo` 0.80(건반이 하나도 안 놓인다), `ln_release` 0.58~0.97, `scratch_run` 0.80~1.0, `jack`·`chord_jack` 0.86~1.0. 반대로 `ln_hold` 는 LN 머리를 행 계산에 넣지 않아 1.06~1.17 로 넘친다(3.3절).
7. **[확인] 표시 NPS 는 노트를 센다, 체감은 행을 따른다.** `actual_nps`·`PLAYLEVEL` 은 동시치기의 노트를 각각 세므로 `chord_stream`(3동시)은 표시 16 NPS 가 행 5.33/초(BPM 160 의 8분)다. 실제 BMS 에서 "NPS X" 는 대개 평균이고 그 안에 X 를 크게 넘는 순간이 있는데, 훈련곡은 X 가 곧 최고치다(4절).

### 1.7 격자 최대 행 속도 `trainingMaxNpsOf` (`spec.ts:176-210`)

```
cellsPerSecond(G, bpm) = G × bpm / (4 × 60)                                  // 204행

| 100 | 13.33 | 8.33 | 16.67 | 40 → CEIL 40 |

### 1.8 마디 분배와 고정 시간 (`spec.ts:233-257`)

```
A = 60_000_000 − 240_000_000/baseBpm − TRAINING_TAIL_US(1_000_000)            // 234행, 카운트인 1마디와 꼬리
m_i = max(1, round(A × w_i / Σw / M(bpm_i)))  → 넘치면 가장 긴 구간부터 1씩 빼고, 남으면 무게 큰 구간부터 1씩 더한다
```

카운트인은 BPM 100 에서 2.4초, 160 에서 1.5초, 220 에서 1.09초. 끝나면 `A − min M < Σ m_i M_i ≤ A` 이므로 마지막 노트 뒤 꼬리는 1초에 최대 한 마디가 더해진다. 그래서 **노트를 놓을 수 있는 시간은 최대 57.5초(BPM 160)** 이고, 그중 워밍업·쿨다운 몫은 LLM 의 `weight` 비로 정해진다. 서버는 그 비중에 상한을 두지 않는다 [확인].

### 1.9 합성기의 행 배치 (`synthesize.ts`)

```
rowsPerSec = target / notesPerRow × peak                                     // gridOf, 92-96행
grid       = grids 중 cellsPerSecond(G, bpm) ≥ rowsPerSec 인 가장 거친 것(없으면 가장 고운 것)
share      = min(1, target / notesPerRow / cellsPerSecond(grid, bpm))        // rowShareOf, 99-100행
비연속 종류: spreadCells — 칸마다 share 를 더해 1 이 모이면 행 하나(오차 확산, 균등)   // 103-111행
연속 종류  : runsOf — 런 길이 R(TRAINING_RUN_ROWS, training-constants.ts:85), 주기 cycle = max(R, ceil(R / share)) 칸,
             주기마다 앞 R 칸에 행                                             // 114-121행
burst     : 박 번호가 짝수면 share × 1.6, 홀수면 × 0.4 로 spreadCells          // 182-187행
```

연속 종류의 실효 비율은 `R / ceil(R / share)` 이라 `share` 보다 작다(올림 손실). 런 안에서는 격자 칸 속도 그대로(예: BPM 160, 24분 격자 = 16 행/초) 친다.

### 1.10 `actual_nps`, `PLAYLEVEL`, `#TOTAL`

```
playable(section) = 그 구간 tick 범위의 놓인 노트 수(일반 1, LN 1(머리만), 스크래치 1, 동시치기 k개면 k)   // synthesize.ts:516
actual_nps        = round2(playable × 1e6 / (to_us − from_us))                 // 534행
play_level        = clamp(round(max over 노트 있는 구간 actual_nps), 1, 25)    // 539, 546행, TRAINING_PLAY_LEVEL_MAX = 25

## 4. 원인 (영향이 큰 순서)

각 항목의 "영향" 은 사용자 결정(집중 구간 1.00~1.10 L, 최고 1.15~1.30 L)과의 거리로 매겼다.

### 4.1 강도 범위의 정의 — 영향 최대 [확인·측정]

- `TRAINING_INTENSITY_RANGE`(`training-constants.ts:50-54`)가 `build`·`push` 의 상한을 1.0 c·1.0 L 로 둔다. 기본 강도가 `push`(`web/src/entities/ai.type.ts:546`)라 **대부분의 생성이 한계를 넘는 구간을 원천적으로 가질 수 없다.**
- 하한이 편한 밀도 기준(0.6 c·0.8 c·1.0 c)이라 c/L 이 0.75 인 사람에게 `push` 하한은 0.6 L. LLM 이 어디를 골라도 받아들여진다.
- `over` 도 상한 1.15 L 이 사용자 결정의 최고 강도 범위(1.15~1.30)의 아래 끝이다.
- 측정: LLM 이 상한을 골라도 `push` 집중 0.85~0.96 L, `build` 0.66~0.78 L(3.1절).

### 4.2 LLM 이 범위 안에서 고르는 위치 — 영향 큼 [추측, 측정은 시뮬레이션]

- 프롬프트(`training-plan.service.ts:123-124`)는 "범위 안", "워밍업으로 시작, 집중 두 번 이상, 쿨다운으로 끝" 만 지시한다. 목표를 상한 쪽에 두라는 말도, 최고 구간을 두라는 말도 없다.
- 시뮬레이션: 가운데를 고르면 `push` 0.70~0.79 L(상한 대비 −0.15~−0.18 L), 계단(11/13/15)을 고르면 P2 push 집중 평균 0.79 L, 곡에서 16 에 한 번도 닿지 않는다(3.2·3.4절).
- 같은 프로필·같은 요청은 캐시된 같은 계획을 돌려받는다(`feature-runner.service.ts:100-104`). 사용자가 "다시 만들기" 로 더 어려운 곡을 얻을 길이 없다 [확인].
- 운영에서 실제로 고른 값은 보지 않았다(7절에 확인 방법).

### 4.3 한계 추정의 하향 편향 — 영향 중간, 사람마다 다름 [확인(코드), 크기는 미측정]

1. **아래 끝 표기**: `limit_nps_ex = curve[limitIndex].from_nps`(`weakness-profile.ts:620`). 실제 넘어가는 지점은 그 구간 [from, from+2) 안 어딘가이고 등위회귀 값은 구간 평균이라, 균일 분포로 보면 평균 −1 NPS(최대 −2) [추측: 분포 가정]. 한계 11 → 10(−9%), 16 → 16(0%), 17 → 16(−6%).
2. **떨어진 적이 없으면 `max_seen_nps`**: EX 맞춤이 기준 − 0.10 까지 떨어지는 구간이 없으면 `limit_nps_ex = null`(609, 620행) → `spec.ts:148` 이 `max_seen_nps`(가장 높은 "쓰는" 구간의 아래 끝)를 한계로 쓴다. 이 구간은 정의상 EX 가 10%p 떨어지지 않은 곳이라 **실제 한계 이하가 확실하다.** 자기 한계 근처 곡을 많이 치지 않는 사람일수록 여기 걸린다 [추측].
3. **표본 문턱**: 구간마다 150 노트·3곡 이상이어야 쓰인다(586행). 실제 곡에서 가장 진한 2초는 노트가 적어 잘리기 쉽다. 그래서 `max_seen_nps` 와 한계 곡선의 꼭대기가 아래로 잘린다 [추측].
4. **둘 다 없으면 12 고정**(`training-constants.ts:46`), 편한 밀도가 없으면 0.7 L(47행).
5. BP 한계(`limit_nps_bp`)와 `peak_seen_2s` 는 범위에 쓰이지 않는다(`spec.ts:148-149`).

### 4.4 평탄한 밀도 구조 — "단조롭다" 의 직접 원인 [확인·측정]

- 구간 안: 비연속 종류는 `spreadCells` 로 균등(`synthesize.ts:103-111`), 연속 종류는 일정 주기의 런(114-121행). 구간 안에서 밀도를 바꾸는 장치는 `burst` 의 박 단위 진동뿐이다.
- 구간 사이: 구간마다 `target_nps` 하나(`web/src/server/dto/training.ts:67`). 집중 구간 3개가 같은 목표면 곡의 40초 이상이 한 값이다(3.4절 시계열).
- `burst`: 1박 1.6× / 1박 0.4×(`synthesize.ts:182-187`, `training-constants.ts:99-100`). BPM 160 에서 한 박은 0.375초로 1초 창(nps1)보다 짧아, 분석에서 90% 가 `sustained`(3.5절). 2초 창 기준 국소 최고치는 평균의 1.0~1.1배.
- 측정: 곡 전체 nps2 `max/p50` 은 1.03~1.33, 집중 구간 안에서는 p50 = p90 = max 인 경우가 흔하다(3.6절의 16.5 / 16.5 / 16.5 등).
- 실제 BMS 의 오르내림과 비교한 수치는 없다(7절). 다만 실제 곡이 후렴·간주·끝 몰아치기로 2초 창 밀도가 크게 변한다는 점은 프로필이 `burst`/`sustained` 맥락을 따로 세는 이유이기도 하다(`weakness-profile.ts:335-363`) [추측].

### 4.5 워밍업·쿨다운·카운트인·꼬리 비중 [확인·측정]

- 카운트인 1마디(1.09~2.4초), 꼬리 1초 + 남는 마디(`spec.ts:234`, `training-constants.ts:20-21`).
- 워밍업은 편한 밀도 이하(`spec.ts:169`), 쿨다운 `rest` 는 3 NPS 이하(4분 격자, `training-constants.ts:83`). 비중은 LLM 의 `weight` 로만 정해지고 서버 상한이 없다.
- 측정(가중치 2·3·3·3·1): 워밍업 9초 + 쿨다운 4.5초 = 22~23%, 카운트인 포함 약 25%. 곡 평균 NPS 는 집중 밀도의 0.82~0.86배(3.1절 평균/L ÷ 실제/L). 워밍업·쿨다운이 없으면(focus) 곡 평균은 0.91~1.03 L 까지 오른다.

### 4.6 격자 상한 `trainingMaxNpsOf` [확인·측정]

- 단타 종류 상한 = 32 칸/마디 × BPM/240(1.7절 표). 기준 BPM 160 에서 21.33, 120 에서 16.
- `burst` 는 이를 1.6 으로 나눠 BPM 160 에서 13.33. P2(L 16)의 `push`·`over`, P3 의 모든 강도에서 `burst` 목표가 잘린다(3.6절). `tag:dense` 의 첫 종류가 `burst` 이고(`training-constants.ts:184`), `fatigue` 도 `burst` 를 둘째 종류로 허용한다(201행).
- 기준 BPM 120 이면 P3 `push` 0.71 L, `over` 0.74 L(3.1절). 기준 BPM 은 LLM 이 고르고 서버는 범위(100~220)만 본다(`spec.ts:213`).

### 4.7 종류별 배치 손실 [확인·측정]

3.3절 표 그대로: `stair` −21~29%, `scratch_solo` −20%(건반이 놓이지 않음), `ln_release` 고밀도에서 −25~42%, `scratch_run`·`jack`·`chord_jack` 의 올림 손실 최대 −13~20%. `ln_hold` 는 +6~17% 넘친다(표시 NPS 를 올려 체감과의 차이를 키움, 5절).

### 4.8 편한 밀도·한계 비율이 범위를 더 좁힌다 [확인]

`comfort` 는 위 끝, `limit` 은 아래 끝(`weakness-profile.ts:619-620`)이라 c/L 이 실제보다 1 에 가깝게 나오기도 하고(예: c 10, L 10), 반대로 편한 밀도 판정(기준 − 0.03)이 엄격해 c 가 낮게 나오면 `build` 전체와 `push` 하한이 함께 내려간다. 사용자 결정은 L 만 기준으로 삼으므로, c 에 매인 하한은 그 결정과 맞지 않는다.

## 5. "체감 밀도" 와 표시 NPS

### 5.1 무엇을 세는가 [확인]

| 표시 | 세는 것 | 위치 |
|---|---|---|
| 구간 `actual_nps`(웹 상세 띠 "목표 / 실제 NPS") | 구간 시간 안의 놓인 노트 수 / 구간 길이. 일반 1, LN 1(머리만), 스크래치 1, k동시치기 k. 지뢰 없음 | `synthesize.ts:516,534`, `web/messages/ko/pages.json:531-533` |
| `#PLAYLEVEL` / 상세의 PLAYLEVEL | 노트 있는 구간 `actual_nps` 최댓값의 반올림, [1, 25] | `synthesize.ts:539,546`, 문구 `pages.json:596` "구간 중 가장 높은 NPS" |
| 노트 수 `note_count` | `playable_notes`(일반 + LN 머리, LN 끝 제외) | `bms-writer.ts:52`, `pattern-document.ts` |
| 분석 nps2(프로필 한계의 단위) | 판정 노트(일반, LN 머리, CN 끝) / 2초 중앙 창(곡 시작·끝은 잘린 길이로 나눔) | `local-density.ts:59-76`, `pattern-tags.ts:87-88` |

표시와 분석은 같은 것을 센다(LN 모드라 LN 끝은 둘 다 안 센다). 그래서 "표시 NPS 가 부풀려진" 것은 `ln_hold`(LN 머리 몫) 정도이고, 어긋남의 대부분은 **노트 수와 손이 느끼는 부담의 차이**에서 온다.

### 5.2 체감과 어긋나는 지점

1. **동시치기는 노트로 센다** [확인·측정]. `chord_stream`·`chord_jack` 3동시는 행/초가 NPS 의 1/3(3.3절 행/NPS 0.33). P2 push 에서 표시 16 NPS = BPM 160 의 8분 3동시(5.33 행/초)이고, 같은 16 이 `stream` 에서는 24분 단타(16 행/초)다. `scratch_mixed` 는 0.74, `ln_hold` 0.94.
2. **표시 NPS 가 곧 최고치다** [확인·측정 + 추측]. 실제 BMS 의 "NPS X" 는 흔히 곡 평균(노트 수 / 길이)이고 그 안에 X 를 훨씬 넘는 2초가 있다. 훈련곡은 2초 창 max 가 표시값과 거의 같다(3.6절, p50 ≈ max). 같은 숫자라도 실제 곡보다 순간 부담이 낮다. 비교 대상을 사용자가 무엇으로 삼는지는 확인하지 않았다 [추측].
3. **리듬이 격자에 고정된다** [확인]. 한 구간은 한 격자(4·8·12·16·24·32 중 하나, `synthesize.ts:92-96`)에서 같은 간격으로만 놓인다. 실제 곡의 섞인 분할(16분 사이 24분 꾸밈, 붙은 동시치기)이 없다.
4. **단타 레인 선택이 반복을 피한다** [확인]. `createSingleLayer` 는 직전 두 행의 레인을 피하고(`synthesize.ts:157-169`), 그래서 `stream` 은 우연한 잭·트릴 없이 7레인을 고르게 도는 "읽기 쉬운" 단타가 된다.
5. **`scratch_solo` 는 스크래치만 남는다** [측정]. 표시 NPS 는 스크래치 연타로 채워지고, 의도한 "스크래치 + 가끔 건반" 이 아니다(3.3절).
6. **LN 은 몸통이 세어지지 않는다** [확인]. `ln_hold` 의 2박 홀드(`training-constants.ts:93`)는 1노트로 세어지지만 손 하나를 묶는다. 반대로 `ln_hold` 는 머리 몫으로 표시 NPS 가 목표보다 높다(1.06~1.17배).
7. **게이지는 넉넉하다** [확인, 체감 영향은 추측]. `#TOTAL = max(160, round(7.605 N / (0.01 N + 6.5)))`(`bms-writer.ts:42-49`): N = 813 → 423, 1,215 → 444. `#RANK 2`(`training-constants.ts:130`). 밀도와 별개로 "클리어가 쉽다" 는 느낌에 더해질 수 있다.
8. **PLAYLEVEL 이 집중 구간을 대표하지 않을 수 있다** [측정]. 최댓값 구간이 워밍업이면 그 값이 레벨이 된다(P1 build stair: 집중 5.88, 레벨 8). 25 에서 잘린다(P3 over chord_stream 27.6 → 25).

## 6. 고칠 방향 후보 (설계 아님, 선택지와 장단점)

목표를 측정 가능한 문장으로 두면: **집중 구간의 nps2 p50 이 1.00~1.10 L, 최고 구간의 nps2 max(또는 p90)가 1.15~1.30 L**(L 은 아래 6.5 에서 고친 한계). 이 문서의 스크립트를 그대로 다시 돌려 108 경우 모두에서 확인할 수 있다.

### 6.1 범위 식 (`TRAINING_INTENSITY_RANGE`, `trainingBoundsOf`)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. L 기준 두 띠 | 집중 기본 `[1.00 L, 1.10 L]`, 최고 `[1.15 L, 1.30 L]` 를 bounds 에 따로 둔다(`base_min/max`, `peak_min/max`). 워밍업만 c 기준 | 사용자 결정과 1:1 | 스키마·digest·화면 문구 변경 |
| B. 강도 3단계를 L 기준으로 다시 정의 | 예: build `[0.90, 1.00]·[1.05, 1.15]`, push `[1.00, 1.10]·[1.15, 1.25]`, over `[1.05, 1.15]·[1.20, 1.30]` | UI·요청 스키마 유지, 기본 push 가 결정을 만족 | build 의 "패턴 익히기" 의미가 바뀐다 |
| C. 강도 하나로 줄임 | 결정 범위 하나만 | 가장 단순 | 사용자가 고를 거리 없음, 요청 스키마·화면 정리 필요 |

공통: 하한을 c 가 아니라 L 에 묶어야 LLM 이 낮게 골라도 결정 아래로 내려가지 않는다(`npsRangeOf`, `spec.ts:167-171`).

### 6.2 목표값을 누가 정하나 (`correctTrainingPlan`, 프롬프트, 출력 스키마)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 프롬프트만 강화 | "집중은 기본 띠 상단, 마지막 집중 앞에 최고 구간 하나" 를 지시 | 변경 작음 | 따를 보장 없음(effort low), 같은 프로필이면 캐시 |
| B. 역할 + 정도 | 출력에 `role: 'edge' \| 'base' \| 'peak'` 와 `level ∈ [0, 1]` 을 받고 서버가 `띠_min + level × (띠_max − 띠_min)` 으로 계산 | 결정 범위를 서버가 보장, LLM 은 구성만 | 스키마·`TRAINING_PLAN_PROMPT_VERSION`(28행) 올림, 옛 캐시 무효 |
| C. 서버가 전부 | 구간 순서로 서버가 곡선(예: 워밍업 → base → base → peak → base)을 정하고 LLM 은 종류·레인만 | 결정론, 시험하기 쉬움 | LLM 이 밀도 배분을 설명할 여지가 줄어듦 |

### 6.3 밀도의 오르내림 (`synthesize.ts`)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 구간 안 프레이즈 변조 | 2~8초(2초 창이 잡는 길이) 단위로 base ↔ peak 를 오가는 share 곡선. 비연속 종류는 `spreadCells` 의 `shareAt`(103행, 이미 칸별 share 를 받음)으로, 연속 종류는 런 주기를 칸별로 바꿔서 | 2초 nps2 분포가 넓어져 실제 곡과 비슷해짐 | 연속 종류의 `runsOf` 를 고쳐야 함, 골든 변경 |
| B. `burst` 재정의 | 진동 단위를 1박이 아니라 1~2초 블록으로 | 분석의 `burst` 맥락(nps1 ≥ 1.5 nps8)과 맞음 | 블록 안 최고치가 격자 상한을 넘기 쉬움(6.5) |
| C. 최고 구간을 별도 구간으로 | 6.2 의 `peak` 역할 구간을 짧게(4~8마디) 둠 | 구현 단순, 기존 배치 재사용 | 구간 안은 여전히 평평 |

### 6.4 비중 (`distributeMeasures`, `npsRangeOf`)

- 워밍업·쿨다운 가중치에 서버 상한(예: 합계 ≤ 15%) 또는 고정 마디 수.
- 워밍업 상한을 c 가 아니라 0.9~1.0 L 로 올리거나 램프로.
- 쿨다운을 없애거나(60초 훈련곡에 회복 구간은 효과가 작다 [추측]) 1~2마디로.
- 장점: 곡 평균이 집중 밀도에 다가감(측정상 0.82~0.86배 → 0.9배 이상). 단점: 처음 몇 초의 적응 여유가 줄어든다.

### 6.5 격자 상한과 기준 BPM

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 기준 BPM 을 서버가 올림 | 최고 목표가 `trainingMaxNpsOf` 를 넘으면 `base_bpm` 이나 `bpm_ratio` 를 필요한 만큼 올림 | 틱 해상도 그대로 | 곡 BPM 이 사용자 의도와 달라짐 |
| B. 더 고운 격자 | `TRAINING_GRIDS` 에 48·64 추가, `TRAINING_MEASURE_TICKS` 96 → 192(`training-constants.ts:75-78`, 줄 해상도 상한 192 와 맞음) | 낮은 BPM 에서도 진함 | 32분 이상 연타는 치기 어려운 패턴이 된다, `GENERATOR_VERSION` 올림 |
| C. `burst` 상한을 블록 기준으로 | 6.3 B 와 함께, 1.6 을 "가장 고운 격자" 가 아니라 블록 평균에 적용 | `burst` 가 13.33 에 묶이지 않음 | 블록 안 실제 속도 확인 로직 필요 |

### 6.6 종류별 손실 보정 (`synthesize.ts`, `spec.ts:176-189`)

- 런 주기: `ceil` 대신 런 시작을 오차 확산으로 배치(실효 비율 = share). 연속 종류의 −5~13% 를 없앰.
- `stair`: 주기를 실제로 놓일 행 수(남은 레인)로 계산하거나, 끝에서 새 런을 바로 이어 붙임(−21~29% 해소).
- `scratch_solo`: 건반 칸이 없으면 격자를 한 단계 곱게 고르거나 `notesPerRow` 를 실제 배치로 맞춤.
- `ln_release`: 고밀도에서 손 번갈기를 유지하되 LN 길이를 줄이거나 레인 4개(가운데 키 포함)로.
- `ln_hold`: LN 머리 몫(`2박마다 1`)을 `notesPerRow`/행 비율에 포함해 넘침 제거.
- 동시치기: 목표를 노트 대신 "행 × 가중" 으로 잡거나, 화면에 행/초를 함께 표시(6.8).

### 6.7 한계 추정 (`weakness-profile.ts:576-629`)

## 7. 확인하지 못한 것과 다음 진단

1. **운영에서 LLM 이 고른 값.** 사용자 기록을 읽지 않았다. 확인하려면 `training_chart` 에서 곡별로 `request.plan.sections[].target_nps` 를 같은 행의 집중 구간 최대 목표, `spec.corrections` 의 `target_nps` 보정 건수와 함께 **집계만**(곡 수, 분포 백분위) 내면 된다. `bounds` 는 저장되지 않으므로(`spec` 에 없음) 정확한 범위 대비 비율은 지금 구조로는 복원되지 않는다. 앞으로 `spec` 에 `bounds` 를 남기는 것도 후보다.
2. **실제 BMS 의 nps2 분포 모양.** 저장소에 실제 곡 코퍼스가 없어 "실제 곡의 `max/p50`" 을 재지 못했다(저장소 BMS 는 골든 3개와 `samples/preview-demo/` 2개뿐). `rbms-cli chart-pattern` 으로 기본 난이도표 곡 몇 개의 패턴 문서를 뽑아 `localDensitiesOf` 로 같은 지표를 내면 6.3 의 목표 폭을 정할 수 있다.
3. **한계 추정 편향의 실제 크기.** 4.3 의 2·3번(떨어진 적 없음, 표본 문턱)이 실제 사용자에게 얼마나 걸리는지는 프로필 분포 집계(`limit_nps_ex` null 비율, `limit_nps_ex − max_seen_nps`)로 볼 수 있다. 읽지 않았다.
4. **기준 BPM 과 가중치의 실제 선택.** 측정은 BPM 160, 가중치 2·3·3·3·1 로 고정했다.
5. **`#TOTAL`·`#RANK` 의 체감 영향.** 계산식만 확인했고 플레이로 확인하지 않았다.
6. **`lane_hint`·`scratch_ratio`·`ln_ratio`·`bpm_ratio ≠ 1` 조합.** 측정하지 않았다. `left`·`right`(4레인)·`center`(5레인)는 `chord_stream` 의 "직전 행과 겹치지 않기"(`synthesize.ts:198`)와 `ln_*` 의 손 레인에서 손실이 더 클 수 있다 [추측].
